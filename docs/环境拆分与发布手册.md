# Ubuntu 环境拆分与发布手册

## 1. 目标拓扑

同一台局域网 Ubuntu 承担两个相互隔离的逻辑平面：

1. **本地生产采集平面**：现有 `xiansuo` Compose、四台 Windows VM、PostgreSQL、Redis、Celery Worker/Beat、LLM 清洗和到 `c.yfpoll.cn` 的事务发件箱同步。该平面继续承载真实采集，不因测试发布重建。
2. **测试管理平面**：独立 `xiansuo-staging` Compose，只默认运行 PostgreSQL、Redis、Backend，并由 `leads.yixiua.com` 的 SSH 反向隧道指向本机 `127.0.0.1:18000`。

云端 `c.yfpoll.cn` 是正式业务平面。Windows + Docker 是开发环境。测试管理平面不是采集源，也不是正式数据权威源。

## 2. 隔离不变量

- 测试与采集平面的容器、Compose project、网络、卷、数据库、Redis、凭据和主机端口不得相交。
- 测试 PostgreSQL/Redis 不发布宿主机端口；四台 VM 只能继续访问生产采集 Redis。
- 测试默认不启动 Celery Worker，不定义 Celery Beat。
- 测试镜像从干净 Git 提交构建，使用 `xiansuo-staging-app:<git-sha>`，不挂载 `/home/m/xiansuo` 的现场源码。
- 测试的 AI、LLM、调度、告警、备份、正式同步、同步接收和采集日志接收均硬关闭。
- 生产采集数据库只做一致性备份；测试恢复得到的是时间点快照，之后不与生产采集库双向同步。
- 切换测试域名只修改 SSH 隧道的本地目标端口；任一异常立即恢复到原端口 8000。

## 3. 发布前门禁

### 3.1 仓库

1. `git status --short` 不得夹带他人改动。
2. 构建提交已推送到 `origin/main`。
3. `.dockerignore` 已排除 `.env*`、`wxsearch/config/secrets.json`、日志、备份和临时产物。
4. 使用 `git archive` 导出部署包；不得从脏工作树或 `/home/m/xiansuo` 构建测试镜像。

### 3.2 现场基线

保存以下证据但不记录任何真实口令：

- 现有容器 ID、镜像 ID、启动时间、网络、卷和端口；
- `.env`、Compose 与 `leads-tunnel.service` 的 SHA256 和权限；
- 8000/5432/6379 的监听；
- 四台 VM 最新心跳；
- 最新文章、线索、同步 Outbox 各状态和最近成功时间；
- 内存、磁盘和 Docker 卷占用。

如果生产采集已异常、磁盘不足、无法确认卷或无法在 5 分钟内恢复原隧道，不得继续。

## 4. 构建与启动

以下命令在由干净 Git 提交导出的独立部署目录执行。真实 `.env.staging` 只保存在服务器并设置为 `0600`。

```bash
docker compose -p xiansuo-staging \
  --env-file .env.staging \
  -f docker-compose.staging.yml config --quiet

docker compose -p xiansuo-staging \
  --env-file .env.staging \
  -f docker-compose.staging.yml build backend

docker compose -p xiansuo-staging \
  --env-file .env.staging \
  -f docker-compose.staging.yml up -d postgres redis
```

全新空库先显式执行 `schema-init`，再执行 `migrate`。完整快照恢复时不要执行 `schema-init`，应先恢复，再执行 `migrate`。随后必须 provision 并以真实运行 LOGIN 复核，三步都成功后才能启动 Backend：

```bash
docker compose -p xiansuo-staging --env-file .env.staging \
  -f docker-compose.staging.yml --profile admin run --rm migrate

docker compose -p xiansuo-staging --env-file .env.staging \
  -f docker-compose.staging.yml --profile admin run --rm provision-runtime-role

docker compose -p xiansuo-staging --env-file .env.staging \
  -f docker-compose.staging.yml --profile admin run --rm \
  provision-runtime-role python -m wxsearch.runtime_db_role check

docker compose -p xiansuo-staging --env-file .env.staging \
  -f docker-compose.staging.yml up -d backend
```

`migrate/provision-runtime-role` 必须始终通过 `run --rm` 执行，不得常驻。Backend/Worker/Beat 只得到运行 `DATABASE_URL`；管理连接只存在于上述一次性任务。不得直接运行不带服务名的 `up -d`，以免误启 profile 或未来新增的服务。

## 5. 数据备份、恢复与安全复位

1. 对现有 `wxsearch_db` 执行 PostgreSQL 15 自定义格式 `pg_dump -Fc`。
2. 记录备份文件大小和 SHA256。
3. 把备份通过标准输入恢复到全新的测试数据库，使用 `--clean --if-exists --no-owner --no-acl --exit-on-error`。
4. 恢复后运行迁移器，并核对 `schema_migrations`、关键表行数和 sequence。
5. 在启动测试 Backend 前执行：

```sql
UPDATE production_sync_settings SET enabled = FALSE WHERE singleton = TRUE;
UPDATE keywords SET enabled = FALSE, status = 'pending';
TRUNCATE TABLE production_sync_outbox;
```

新测试 Redis 必须为空，绝不恢复生产 Redis 的 RDB/AOF。复制来的设备心跳仅是历史展示，不能作为真实在线状态。若测试用于第三方演示，还必须另行脱敏用户、联系人、备注、报价等业务数据。

## 6. 启动后自动/人工断言

必须同时满足：

- `http://127.0.0.1:18000/health` 的 PostgreSQL 与 Redis 均为健康；
- 运行容器只有测试 `postgres`、`redis`、`backend`，没有测试 Worker/Beat；
- Backend 的真实数据库 `current_user=session_user` 是 `.env.staging` 指定的运行 LOGIN；该角色非 superuser、无 BYPASSRLS、不是租户表 owner、不能在 `public` 建对象或写 `schema_migrations`；
- Backend 容器环境不存在 `MIGRATION_DATABASE_URL`、`STAGING_POSTGRES_PASSWORD` 或 `POSTGRES_PASSWORD`；一次性 migrate/provision 容器均已删除；
- 测试与生产采集 volume source、network、容器名和主机端口交集为空；
- 测试容器最终环境中 `LLM_CLEAN_ENABLED=false`、`PROD_SYNC_ENABLED=false`、`SCHEDULER_ENABLED=false`，同步 URL/Secret 与模型 Key 为空；
- 数据库 `production_sync_settings.enabled=false`，Outbox 为空；
- 测试 Redis 没有真实 VM 客户端和生产队列；
- 现有 `wxsearch_*` 容器 ID 和启动时间均未变化；
- 四台 VM 心跳、文章入库、LLM 清洗和正式同步继续推进，Outbox 没有新增 dead。

连续三个正式同步周期正常后，才允许切测试域名。

## 7. SSH 隧道切换与回滚

首选先用不同云端端口建立临时 canary 隧道。若云端只允许原 7080，则：

1. 备份 `leads-tunnel.service` 原文并记录 SHA256。
2. 再次确认本机 8000 和 18000 都健康。
3. 只把 unit 中的本地目标从 `127.0.0.1:8000` 改为 `127.0.0.1:18000`。
4. `systemctl daemon-reload` 并重启隧道。
5. 立即从外部验证 `https://leads.yixiua.com/health`、登录页、静态资源和关键只读页面。

任一失败立即恢复原 unit，重新建立 7080 → 127.0.0.1:8000。回滚只停止测试隧道/测试 Compose 并恢复原 unit，禁止对生产 `xiansuo` 执行 `down -v`、删除卷、清 Redis 或覆盖恢复生产数据库。

## 8. 停止条件

出现以下任一情况立即停止并回滚：资源交叉、测试外呼 LLM/正式同步、现有容器被重建、VM 新增离线、采集停止超过两个正常周期、Outbox retry/dead 增长、正式端出现测试事件、任一业务域名 5xx，或宿主机资源压力开始影响生产采集。
