# 坑位手册

> 合并了两个智能体各自踩出来的结论。**动 UIA / VM / 部署之前先读这里。**
> 踩到新坑立刻往这里加，别让另一边重踩。格式：现象 → 原因 → 做法。

---

## 一、微信 PC UIA 采集

### 1.1 合成鼠标点击对 Chromium 渲染层完全无效 ⭐最坑

- **现象**：guest 内 `auto.Click` 点搜索下拉框、点筛选项，**毫无反应，连 hover 高亮都没有**。
- **原因**：搜索下拉框/结果区是 Chromium 渲染层，不接受 SendInput 合成的鼠标事件。宿主真鼠标（经虚拟机控制台）可以，键盘也可以。
- **做法**：下拉框选择**一律走键盘**（`{Down}` 选中首条 → `{Enter}`）。不要浪费时间调坐标。

### 1.2 微信 4.1.x 主窗是 Qt 壳，UIA 树不透明

- **现象**：找不到"搜一搜"按钮控件，`GetChildren()` 返回空。
- **原因**：4.1.x 聊天主窗 ClassName 形如 `Qt51514QWindowIcon`，UIA 不暴露内部结构（4.0 还能读）。
- **做法**：只能盲点坐标。命中判据 = ClassName 含 `Qt` 且窗口名在候选列表内。坐标走 `config.json` 逐台标定。

### 1.3 4.1.12+ 搜索面板默认内嵌，UIA 读不到文档

- **现象**：搜索窗打开了，但 `DocumentControl` 找不到"搜一搜"文档。
- **原因**：新版把搜索面板内嵌进 Qt 主窗，不再是独立的 `Chrome_WidgetWin_0`。
- **做法**：先短等独立窗（约 2 秒）；没有则点面板右上"弹出独立窗口"方框图标（最大化下实测 `right-59, top+57`），脱离成独立窗后再等文档可读。见 `_open_search_via_qt_searchbox`。

### 1.4 搜索窗判定不能只看窗口存在

- **现象**：明明没打开搜索，代码却认为已就绪。
- **原因**：`Chrome_WidgetWin_0` 容器窗**常驻**（微信一直有），搜一搜只是它的一个标签页。
- **做法**：必须用 `DocumentControl` 名含"搜一搜"来判定（`_has_search_doc`）。

### 1.5 搜索框 Ctrl+A 全选不生效 → 新词追加到旧词后面

- **现象**：搜"月嫂"之后搜"评选征集"，实际搜的是"月嫂评选征集"，结果全跑偏。
- **原因**：该输入框对 `Ctrl+A` 无响应，键盘清空失败。
- **做法**：优先 `GetValuePattern().SetValue(keyword)` 直接设值；失败才退回 Ctrl+A/Delete/粘贴。

### 1.6 关键词命中联系人时，Enter 会误进聊天窗

- **现象**：搜"投票"，回车后打开了某个联系人的聊天。
- **原因**：下拉框第一条是联系人而非"搜索网络结果"。
- **做法**：调试标定时用**0 命中的冷门词**（如"月嫂"）。生产中靠 `{Down}` 选中建议项而非直接 Enter。

### 1.7 筛选未生效却继续采集 → 污染线索库 ⭐重要

- **现象**：配置了"最新/文章/最近一天"，实际采回来一堆视频、无关内容。
- **原因**：筛选点击未真正生效，旧实现"兜底按默认结果采集"，等于采了「全部」的混合结果。
- **做法**：**宁缺毋滥**。面包屑回读校验，任一项未确认生效就抛 `FilterNotApplied`（不是 `DriverError` 子类），由 `_open_and_filter` 重开搜索重试；重试耗尽则本轮跳过该关键词、下轮再来。

### 1.8 面包屑回读单次判定会漏判

- **现象**："最新/文章"其实已选上，却被记为未生效。
- **原因**：选项生效后列表**异步重排**，立即回读时面包屑还没更新。
- **做法**：回读改**轮询**（6 次 × 0.5s）。另注意"已选择"要用 `startswith` 匹配，不能 `== "已选择:"`。

### 1.9 筛选面板"收起"文本常点不到

- **做法**：改点分类标签行右侧的 `≡` 图标做二次点击切换收拢，并校验首行标签已消失。`≡` 无文本，用**几何定位**：取"全部"与右侧相邻分类标签的中点（比固定偏移抗布局差异）。

### 1.10 UIA 树遍历会撞瞬时 COM 错误

- **现象**：`-2147220991 事件无法调用任何订阅者` 之类，随机失败。
- **原因**：DOM 刷新期（搜索刚提交、列表重排中）遍历树。
- **做法**：整树重走最多 4 次，仍失败返回空集而非抛出，让上层流程兜底。

### 1.11 Ctrl+W 关文章标签可能误关搜一搜

- **现象**：关掉文章后，后续采集全部失败。
- **原因**：**背景标签不在 UIA 树中**，若搜一搜文档当前可见说明没有文章标签要关，此时发 Ctrl+W 会关掉搜一搜本身。
- **做法**：先判断搜一搜是否已在前台（是则直接返回）；发出 Ctrl+W 后**轮询校验**搜一搜回到前台，未生效则重新聚焦再发，避免标签堆积。

### 1.12 微信弹窗抢焦点，键盘命令时灵时不灵

- **现象**：用模拟键盘（Win+R 运行框）在 guest 里跑脚本，回车反复被吃掉。
- **做法**：别依赖键盘下发命令。改用文件/HTTP 通道（guest 内常驻 agent 拾取执行），键盘只用于**首次拉起 agent**。

### 1.13 `uiautomation` API 缺口

- 没有 `DoubleClick` → 用两次 `Click`
- `WindowPattern` 没有 `Maximize` → 用 `SetWindowVisualState(auto.WindowVisualState.Maximized)`
- 窗口未最大化时布局会变，盲点坐标全部失效 → **先最大化再点**

## 二、虚拟机与部署

### 2.1 KVM/libvirt（Ubuntu 宿主）

- `virsh list` 可能是**空的**但 VM 确实在跑 → 权限/连接 URI 问题，需 `sudo virsh` 或 `-c qemu:///session`。判断实况可直接看 `pgrep -f qemu-system-x86` 与 `/proc/<pid>/cmdline` 里的 `-name`。
- guest 网段 `192.168.122.0/24`（NAT），**宿主地址用 `192.168.122.1`**（virbr0 网关）最稳；切桥接/macvtap 后才用宿主局域网 IP。
- 键盘/截屏：`virsh send-key --codeset linux --holdtime 120`（**holdtime 必须给**，瞬时按键会被 Windows 安装程序/微信丢弃）、`virsh screenshot`。

### 2.2 VMware（Windows 宿主）

- 参数顺序：`vmrun ... runProgramInGuest <vmx> -interactive 'C:\x.bat'`（flag 在 vmx **之后**）。
- UIA/截屏必须 `-interactive`；后台常驻循环用 `-interactive -nowait`。
- guest 锁屏时报"指定的客户机用户必须以交互方式登录"。
- 曾遇 **VMware Tools 死锁**：vmrun 全超时且报 not powered on，但 `list` 显示 running → 只能强制电源重置。

### 2.3 UIA 必须有前台可交互桌面 ⭐

进程拉起来了 ≠ 能采集。会话被锁 / 无交互桌面时 UIA 全程失败，**看起来在跑其实一条都采不到**。
远程启动链必须绑定：**自动登录（AutoAdminLogon） + 禁空闲锁 + 交互式执行**。

### 2.4 链接克隆导致 ID 冲突 ⭐

多台 VM 从同一基础镜像链接克隆，`config.json` 完全相同 → 所有节点用**同一个 `vm_instance_id`** 上报：
监控页只见 1 行、领词租约互相抢。**克隆后必须逐台改 `vm_instance_id`。**

### 2.5 节点没上报 ≠ 节点没在跑

排查顺序：① `unattended.enabled` 是否为 true → ② `distributed.enabled` 是否为 true（否则文章落**本地 SQLite**，一条都不进 PG）→ ③ `broker_url` 指向对不对 → ④ guest 是否装了 `celery`/`redis` → ⑤ 网络可达性。

### 2.6 心跳节拍 vs 在线阈值错配

旧循环只在"每轮开始"和"每个词开始前"上报，而 `DEVICE_ONLINE_TIMEOUT` 默认 600 秒；
单个词超过 10 分钟时，正常工作的机器会被置离线。更隐蔽的是，关键词的
`last_claimed` 过去也只在领取时写一次，15 分钟后仍会被 stale recovery 回收，造成两台 VM 并发采同一词。

正确做法：

- VM 用独立守护线程按 60 秒心跳，不把心跳插进 UIA 采集步骤；`current_keyword` 只用于派生忙碌状态。
- 心跳携带本批仍活跃的 `(channel, keyword, lease_id)`；服务端只续租完全匹配的 owner。Redis 租约键必须包含渠道，同词的微信和搜狗任务不能共用 `wxsearch:kw:{keyword}`。关键词结束必须从集合移除，即使结果上报未知也不能永久续租。
- 连续心跳失败达到阈值后，允许已领取任务完成，但暂停领新批次。
- 不能只用“心跳线程仍 alive”判断可领词；producer 可能卡在网络调用。最近一次成功心跳超过 `3 × interval + result_timeout` 后也必须停领。
- Redis 丢失时只保护 `current_keyword` 不够：本地批次还可能有 B/C 尚未开始。每个词开始前必须重新确认剩余 lease；确认失败就终止本批，不能继续做注定会被 fencing 拒绝的采集和模型调用。
- 首次判离线只置状态和告警，不立即 `force_release_all`；v2 等续租到期后恢复，并用 `lease_id` 拒绝旧执行者迟到上报。legacy 节点没有代次，只能在滚动升级期间由在线心跳保护。
- required PG 调度状态必须先提交成功，才能删除 Redis owner；反过来的顺序会在 PG 故障时留下永久 `running`。
- Redis 建领取态失败时必须先补偿 PG，再删 marker；PG 补偿失败要保留 marker，并对账 `keyword_channel_state.running` 但 Redis 无租约的孤儿。历史坏租约逐条隔离，绝不能让一条脏记录阻断整批 stale recovery。
- 领取初始化失败的 legacy marker 必须标记 `recovery_only=1`；客户端根本没收到这次领取，不能因设备仍在线而永久保护。
- 在 Redis 生命周期锁内的 PostgreSQL 读写和 Redis socket 都必须设置短超时，批量 Redis 命令走 pipeline；stale recovery 还要有硬时间预算、单次操作预留、Redis/PG 独立配额、两侧持久游标及逐轮交换优先级，否则多条慢事务或头部毒记录会让 Redis 锁先过期或后续正常项永久饥饿。注意 `SSCAN COUNT` 只是提示，小 Set 可能一次返回全部且 cursor=0；失败 marker 还要写短退避，不能只依赖 cursor。`force_release_all` 也必须走同一有界批次。
- 迁移 008 和所有真实渠道的 `keyword_channel_state` **完整播种**是领取硬前置，检查必须覆盖每个启用关键词×所属渠道。缺失或部分回填时拒绝领词，不能再回退到没有 owner/last_claimed 的 `keywords.status`。
- 新增关键词与其 `keyword_channel_state` 必须同事务写入；先插关键词、事后异步播种会让完整性门禁把整个渠道停掉。逻辑渠道统一用 `souyisou/sogou`，不要把设备实现名 `wechat_pc` 混作队列渠道。
- 离线扫描的 UPDATE 必须重复携带时间条件，避免 SELECT 后刚恢复的心跳又被旧结果覆盖成 offline。

`heartbeat_interval_sec` 应显著小于服务端在线阈值（建议不超过三分之一）；现网默认 60 秒对 600 秒。
上线顺序必须是服务端兼容任务先更新并重启 worker、再单 VM canary、最后扩量。旧四参数心跳仍兼容，但不会使用 v2 主动续租；
legacy 领取继续写原始 keyword member/hash；只有 v2 写渠道键。回滚前必须先停 v2 canary、核对 v2 租约清空，且新旧 worker 不得混跑同一任务队列。
Redis marker 全丢时无法识别协议代次；若在线设备的 `current_keyword` 与 PG owner/keyword 完全匹配，先保守等待其完成，清空后再回收。
搜狗独立循环当前仍属后续治理入口，不能因为微信 canary 通过就宣称所有采集器已收敛。

### 2.7 优雅停止，别硬杀

正在采的词是**带租约领来的**，硬杀进程会留下 stale claim，只能等服务端 `recover_stale_claims` 到期回收（期间那些词没人采）。停止应在**关键词间隙**停。

### 2.8 现存 guest 文件通道仍是无鉴权任意命令执行器

- **现象**：宿主 `wxrecv.service` 在 `0.0.0.0:18765` 提供下载/回传，guest `agent.ps1` 轮询文本后直接 `Invoke-Expression`；现有部署命令还会 `Stop-Process -Force`。D-005 约定的鉴权、动作白名单和审计尚未真正落地。
- **风险**：能访问端口或写入 outbox 的主体可以在四台 Windows 上执行任意命令；强杀采集进程还会遗留租约。不能把“有 agent”误当成安全部署能力。
- **临时边界**：完成白名单 agent 前，只允许集成负责人向单台按 IP 命令文件投递固定、可审查、带唯一回执标记的只读探针或 canary 发布脚本；发布脚本必须先等待关键词边界，保留原文件并支持原子回滚，禁止沿用强杀脚本。每次操作前用 libvirt 域名/MAC 解析当前 IP，再核对 guest 内 `vm_instance_id`。

### 2.9 guest 探针不得让 PowerShell 回显整份配置

- **现象**：Windows PowerShell 5 用 `Get-Content | ConvertFrom-Json` 读取含中文或编码不一致的 `config.json` 时解析失败，错误通道会把整份 JSON 逐行回显到 `cmdout` 中。
- **风险**：即使探针只想读 `vm_instance_id`，回执也可能附带 broker/backend 连接串或其他配置；直接 `tail` 又会把它们复制到运维日志。
- **做法**：配置身份校验用候选 Python 以显式 UTF-8/UTF-8-SIG 读取，且只输出允许字段；更好的做法是在不打印值的发布脚本内做精确比较。探针失败只返固定错误码，不把原始文件或异常上下文回传；含配置回显的临时 `cmdout` 立即删除。
- **治理目标**：接收端只监听 libvirt 管理网并加共享密钥；guest 只接受 `status / stage_release / switch_release / rollback / restart_between_keywords` 等枚举动作，参数校验 SHA/路径，所有请求和结果写审计日志。未完成前不得把 18765 暴露给局域网或公网。

### 2.10 筛选配置正确不代表微信页面已实际生效

- **现象**：节点配置和服务端动态规则均为“最新 / 文章 / 最近一天”，但微信搜一搜页面的面包屑仍显示“最新、文章、最近七天”，历史文章会直接混入结果。
- **原因**：筛选状态保留在微信当前页面；节点进程未刷新动态配置、旧版客户端或一次点击未真正送达 Chromium 时，不能仅凭 `config.json` 或下发文件判断已修复。
- **做法**：默认值、示例配置和运行时 dataclass 必须统一为“最近一天”；每台 canary 都以页面面包屑 `已选择：最新、文章、最近一天` 为验收证据。KVM 上若 guest 内合成鼠标无效，使用虚拟控制台的硬件级按下/释放点击并截图复核；未读到正确面包屑时，驱动必须抛 `FilterNotApplied` 并跳过本词，绝不能采集当前混合结果。

### 2.11 页面筛选正确不等于搜索结果具有业务相关性

- **现象**：文章确实是“最近一天”的微信文章，但宽泛关键词仍返回干部公示、人物事迹、赛事和娱乐资讯；采集量很大，DeepSeek 最终有效率却很低。
- **原因**：微信搜索按文本相关性召回，“全国、先进、推荐、参与”等普通词不是评选系统商机信号；旧采集规则只检查广告、长度、乱码和时效，服务端又在入库前完全信任节点载荷。
- **做法**：页面面包屑校验继续负责“搜对范围”；采集端与服务端入口质量门禁负责“内容至少像业务”；DeepSeek 负责最终商机判断。三层不能互相替代。关键词按 `raw / llm_done / useful` 观察，低有效率词先暂停再改写，禁止用增加普通正向词的方式硬放行。

## 三、终端与编码

### 3.1 PowerShell

- 中文输出常花屏：Python 脚本里显式 `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8", errors="replace")`。
- `.NET` 格式化字符串 `"{0,-26}" -f` 遇中文/宽字符会报 `InvalidOperation` → 复杂格式化改用 Python。
- `@{u}` 之类 git 语法会被 PowerShell 当 hash 字面量解析 → 避开或加引号。
- 不要用 CMD 的 `rmdir`/`del`，用 `Remove-Item`。

### 3.2 SSH / 远程执行

- Windows 原生 `ssh.exe` **无法非交互喂密码**（没有 sshpass/plink 时）→ 用 Python `paramiko`（密码认证 + SFTP），全程非交互。
- 内联复杂 SQL/命令可能被终端安全策略误拦 → 写成 `.py`/`.sql` 文件再执行。
- psql 连库要显式 `-d wx_search`，否则默认连与用户同名的库并报"database admin does not exist"。

## 四、数据与去重

### 4.1 SimHash 阈值定为 1.0（仅汉明距离=0）

同质公文（征集/评选通知）区分度不足，阈值 0.9/0.95 都出现大量误杀（194 篇实测误杀率约 12%）。
真转载实测均落在距离 0，故收紧到 1.0；部分改写的转载由第②层 SHA256 精确兜底。

### 4.2 评估误杀率不能只统计库内现存记录

存活者偏差：被误杀的根本没入库，只看库内会严重低估。

### 4.3 `DatabaseConnector` 事务行为

`execute_query` **不提交**，用它跑 INSERT/UPDATE 会被回滚（曾造成"假成功"Bug）→ 写操作必须用 `execute_write`。

## 五、服务端连接池与部署

### 5.1 连接池异常路径未归还连接会让采集“假在线”

- **现象**：PostgreSQL 仍可连接，但 worker 连续报 `connection pool exhausted`；设备心跳、领词和入库全失败，Celery 任务却因异常被吞掉而显示已完成。
- **原因**：`DatabaseConnector.execute_query` / `execute_write` 仅在成功路径 `putconn`。任意 SQL/网络异常都会遗失一条借出的连接；Celery 多进程会很快耗尽本进程池。
- **做法**：连接归还放进 `finally`，异常前回滚；连接已经断开时丢弃而非放回。Web 进程使用线程安全连接池，并用 `DB_POOL_MAX` 限制每个进程的连接上限，不能靠盲目增加 PostgreSQL `max_connections` 掩盖泄漏。

### 5.2 生产容器必须由 Compose 接管并显式注入服务端点

- **现象**：容器在运行但没有 Compose 标签、`DATABASE_URL` / `REDIS_URL` 为空；程序回退到 localhost/占位密码，数据库持续认证失败，Docker healthcheck 也一直 unhealthy。
- **原因**：手工 `docker run` 或不完整的 Compose 命令绕开了项目的环境变量、网络和健康检查定义。
- **做法**：先保留并备份现有 PG volume，再用单一 Compose 文件重建应用容器；启动后核对容器标签、环境变量是否存在、容器网络和 `/health` 的依赖探针。不要把真实密码写回 Compose 或源码。

### 5.3 `leads.yixiua.com` 是独立测试管理入口，不是生产采集入口

- **实际拓扑**：同一 Ubuntu 上有两个逻辑平面。现有 `xiansuo` 继续承担四台 VM、Worker/Beat、LLM 和正式同步；独立 `xiansuo-staging` 只运行测试 PostgreSQL、Redis、Backend。`leads-tunnel.service` 的 SSH `-R` 将云端 `47.93.170.68:7080` 转发到测试 Backend `127.0.0.1:18000`。
- **误判风险**：SSH 隧道只是测试管理域名入口，不能据此判断真实采集链路健康。`wxsearch_nginx` 停在 `Created` 也不是故障；直接执行生产或测试全量 Compose 会引入无关入口，甚至误启 Worker。
- **做法**：排障 `leads.yixiua.com` 时检查测试 Backend 18000、`leads-tunnel.service` 和云端 7080；排障采集时独立检查生产 Redis/PG、Worker/Beat、四台 VM 心跳、LLM 与 Outbox。测试只启动明确列出的 `postgres redis backend`，Nginx 仍只保留为显式 profile 备用。
- **回滚**：切换隧道前备份 unit。测试入口失败时只把本地目标恢复到原 8000，不得重建或停止生产采集容器。

### 5.4 数据恢复后序列未对齐会持续主键冲突

- **现象**：采集链路恢复后，`articles_core`、`collect_tasks` 等表连续报 `duplicate key value violates unique constraint ..._pkey`，冲突 ID 每次递增。
- **原因**：导入数据时显式写入了 `id`，但对应 serial/identity sequence 没有推进到表内最大 ID。服务恢复后 `nextval()` 继续生成已存在的编号。
- **做法**：恢复完成后遍历当前 schema 的 serial/identity 列，将 sequence 校准到各表 `MAX(id)`；校准前先做数据库备份。不要通过删除冲突记录或反复重试来“等序列追上”，那会丢数据并制造大量失败任务。

### 5.5 复用 PostgreSQL 数据卷时环境变量不会重置角色口令

- **现象**：容器里的 `DATABASE_URL` 完全一致，PostgreSQL 也显示 healthy，但 Backend/Worker 均报 `password authentication failed for user admin`。
- **原因**：`POSTGRES_PASSWORD` 只在空数据目录首次初始化时生效；恢复或复用旧 volume 后，数据库角色仍使用卷内保存的旧口令，重建容器不会自动更新。
- **做法**：先备份数据库，再通过容器内 Unix socket 连接执行 `ALTER ROLE`，把数据库角色口令对齐服务器 `.env`；随后重启所有数据库客户端容器并用真实 `SELECT 1` 验证。不要删除 volume 试图让环境变量“重新生效”。

### 5.6 Compose 硬编码口令会让 `.env` 变成无效配置

- **现象**：服务器 `.env` 看起来配置正确，但重建 Redis 后四台采集 VM 同时出现 `WRONGPASS` / result backend 重试耗尽；服务端容器内部仍可能正常，因此容易误判为 VM 网络问题。
- **原因**：Compose 在 `command` 和 `REDIS_URL` 中直接写死了口令，完全没有引用 `.env`。重建之前的容器可能沿用另一套历史配置，一旦重建便立即发生全链路漂移。
- **做法**：真实值只放服务器 `.env`，Compose 统一使用 `${REDIS_PASSWORD}` / `${POSTGRES_PASSWORD}` 插值。修复时先以当前正常运行容器为临时事实来源对齐 `.env`，运行 `docker compose config` 比对后停止；不要顺手执行全量 `up`。采集 VM 配置必须从同一密钥源下发。

### 5.7 libvirt DHCP 地址不能当作采集节点身份

- **现象**：文档中的 `win10-01`~`04` IP 与实际机器错位，按旧 IP 下发配置会把 `vm_instance_id` 写到错误节点，造成租约冲突或监控串线。
- **原因**：链接克隆增加了网卡，DHCP 租约会变化；IP 只是当前连接地址，不是稳定身份。
- **做法**：以虚拟机名和唯一 MAC 为身份，通过 `virsh domiflist` + `net-dhcp-leases` 动态解析当前 IP，再核对 guest 内 `vm_instance_id`。标定清单记录的 IP 仅供当日排障参考。

### 5.8 幂等迁移也可能产生“升级路径不同、最终结构不同”

- **现象**：测试库数据导入新生产库时报缺少 `channels_jsonb_legacy`，但两边都已执行同一组迁移。
- **原因**：迁移 001 只有在检测到旧 `channels` 为 JSONB 时才把它重命名为兼容列；从较新基础 schema 起步时 `channels` 已是 TEXT[]，条件分支不执行，最终少一列。
- **做法**：数据库同步前对源/目标运行 `information_schema.columns` 全量列级比较；用后续迁移显式补齐最终态。迁移验收不能只看“脚本成功”，还要验证不同起始版本收敛到同一 schema。

### 5.9 已执行的迁移文件不能原地修改，迁移器跳过不等于校验通过

- **现象**：恢复生产快照后运行迁移器显示 20 个版本全部 `Skipped`，但把 `schema_migrations.checksum` 与镜像内 SQL 重新计算后，018～020 存在漂移。
- **原因**：当前迁移器只按版本号判断“已执行”，不会在跳过时比较 checksum；历史迁移执行后又被补改，数据库仍保存首次执行内容的 MD5。
- **风险**：从旧库升级与从空库新建可能得到不同的视图、列、表、函数或触发器；直接把数据库 checksum 改成新值只会掩盖差异，不能证明新 SQL 真正执行过。
- **做法**：已发布迁移永久只读，任何补充都新增下一编号的收敛迁移。发布门禁必须对已执行版本重新计算 checksum，并对列、约束、索引、视图、函数和触发器做最终态断言。发现历史漂移时先记录例外并验证最终 schema；不得盲改 `schema_migrations`，也不得为“补执行”直接重跑可能包含非幂等操作的旧文件。

### 5.9 CSV 的 HEADER 不会按列名自动映射

- **现象**：源表和目标表的列名/类型完全一致，`COPY target FROM ... CSV HEADER` 仍报数组字段收到普通字符串。
- **原因**：PostgreSQL 的 `HEADER` 只负责跳过首行，不按表头名称重排；迁移后新增列在两条升级路径中的物理顺序不同，`COPY` 仍按位置写入。
- **做法**：读取并校验 CSV 表头，执行 `COPY target (col_a, col_b, ...)` 显式列清单。应用同步协议使用字段名对象，SQL 禁止跨系统使用 `INSERT ... SELECT *`。

### 5.10 Compose 项目名写错会制造同名容器冲突

- **现象**：容器本来由 Compose 管理，执行 `up` 却提示 `/wxsearch_backend` 已存在，并额外创建一张新网络。
- **原因**：命令手工指定了错误的 `-p`；正式容器标签中的项目名为 `wxsearch`，测试才是 `xiansuo`。Compose 只能识别同项目标签的旧容器。
- **做法**：操作前读 `docker inspect <container>` 的 `com.docker.compose.project` 和 `com.docker.compose.project.config_files`，沿用标签值。不要凭目录名或另一台服务器的命令猜项目名。

### 5.11 docker-compose 1.29 与新版 Docker 重建时可能报 `ContainerConfig`

- **现象**：旧版 Python `docker-compose 1.29.2` 在 recreate 阶段抛 `KeyError: 'ContainerConfig'`，且已先把旧容器停止并改名，导致 Backend 短暂中断。
- **原因**：Compose v1 读取新版镜像元数据的兼容问题，不是应用或 Compose YAML 语法错误。
- **做法**：先立即 `docker start` 被改名的原无状态容器恢复服务；核对数据库/日志均为外部持久化后，精确移除该旧 Backend 容器，再由 Compose 干净创建。长期应升级到 Compose v2，并在影子/非核心服务上验证后再替换生产工具链。

### 5.12 宿主机监听 `0.0.0.0` 不能由云安全组“兜底算安全”

- **现象**：正式 PostgreSQL、Redis、Backend 均显示 `0.0.0.0:<port>`，业务虽从 Nginx 访问，但数据端口实际在宿主所有网卡监听。
- **风险**：安全组误改、临时放通或旁路网络会直接暴露数据库/队列；Redis 泄露还可伪造 Celery 任务。
- **做法**：正式 Compose 绑定 `127.0.0.1`，容器内部用私有 Docker 网络。发布后用 `ss -ltn` 和外部连通性复核；测试 Redis 因 VM 需要访问，应只允许 libvirt 网段而非公网。

### 5.13 临时部署包和采集循环曾包含真实凭据

- **现象**：`_deploy_tmp/`、交接文档和 `sogou_loop.py` 默认值中出现 SSH、Redis、PostgreSQL 明文口令。
- **风险**：即使文件未提交，工作区同步、压缩打包或误执行 `git add -A` 都可能泄漏；已进入 Git 历史的凭据仅删除当前行并不能失效。
- **做法**：服务端数据库连接使用 `DATABASE_URL`；采集节点只强制要求实际使用的 `REDIS_URL`、`API_BASE` 和日志令牌，绝不下发数据库口令。临时目录/诊断输出加入 `.gitignore`。发现过的口令按已泄漏处理并轮换，必要时清理 Git 历史和旧部署包。

### 5.14 共享规则配置不能覆盖环境角色开关

- **现象**：正式容器里 `LLM_CLEAN_ENABLED=false`，但 worker 仍每分钟执行 LLM 清洗。
- **原因**：旧实现先读取环境变量，却把它只当作缺省值；共享 `rule_config.json` 中的 `llm.clean_enabled=true` 最终覆盖了正式环境配置。
- **做法**：部署角色开关采用“显式环境变量 > 规则文件 > 默认值”的优先级。本地生产采集平面负责 LLM，云端正式业务平面硬关闭；发布后必须分别在容器内检查最终判定结果，不能只看 `.env` 文本。

### 5.15 模型探测与采集日志不能把凭据放进可控 URL

- **现象**：普通登录用户可调用模型探测并传任意 `base_url`；不传临时 key 时客户端回退服务器已保存 key。搜狗日志令牌又放在 query，容易进入代理和访问日志。
- **风险**：攻击者可诱导服务端把 `Authorization` 发到其控制的端点；URL query 会留在浏览器历史、隧道和 Web 日志。
- **做法**：模型探测只允许 super，以 POST JSON 接收临时 key；自定义主机必须显式 allowlist 且不得继承服务器 key。机器令牌统一放 Header，query 只做有期限的旧节点兼容，完成滚动升级后删除兼容并轮换令牌。

### 5.16 原始文件 checksum 会把 CRLF/LF 误判为迁移篡改

- **现象**：相同 SQL 在 Windows 工作树与 Linux 镜像得到不同 MD5；历史审计曾把 019、020 报为漂移，但规范化 LF 后与数据库记录一致，只有 018 是已知真实历史差异。
- **原因**：Git checkout 换行策略改变原始字节，旧迁移器没有规定 canonical form。
- **做法**：迁移 SQL 通过 `.gitattributes` 固定 LF，校验器再按 UTF-8/LF 规范化后计算 SHA-256；历史 MD5 只能逐项精确登记。不能通过关闭 checksum 或批量改 ledger 消除误报。

### 5.17 Compose 必填变量语法会让简单 URL 凭据扫描器误报

- **现象**：Compose 使用 `postgresql://${APP_DATABASE_USER:?required}:${APP_DATABASE_PASSWORD:?required}@...`，实际没有字面量凭据，Secret 门禁却把用户名表达式内部的 `:` 误认成 URL 用户名/密码分隔符。
- **原因**：简单 URL 正则不了解 `${VAR:?message}` 是一个完整插值 token，会从 token 内部的冒号开始错误分组。
- **做法**：URL 扫描规则应把 `${...}` 作为不可拆分的用户名或密码组件，并用回归测试同时证明必填插值放行、真实 URL 字面量仍被拦截。不能为消除误报而降低 Compose 的 fail-closed 要求，也不能把真实值加入扫描白名单。

### 5.18 FastAPI 重复注册同一路径会让后声明的权限检查失效

- **现象**：`/admin/feedback` 同时注册了 admin 和 super 两个处理函数，看源码容易误以为后面的 super 检查更严格，实际请求先命中先注册的 admin 路由。
- **原因**：FastAPI/Starlette 不会用后声明路由覆盖前一条；相同 method/path 会并存并按注册顺序匹配。
- **做法**：每个敏感 method/path 只允许注册一次，页面权限应与菜单和对应 API 的 capability 保持一致，并用路由唯一性测试阻止回归。不能靠“后面再声明一个更严格路由”修补权限。

### 5.19 FastAPI 应用与 APIRouter 的生命周期注册入口不同

- **现象**：代码用 `app.add_event_handler('startup', ...)`，静态检查正常，但当前 FastAPI 在测试收集时直接报 `FastAPI object has no attribute add_event_handler`；同时 Pydantic 2 对 class-based `Config` 产生弃用警告。
- **原因**：此版本把生命周期 handler 注册接口暴露在 `app.router`；Pydantic 2 的模型配置入口已改为 `ConfigDict/model_config`。仅做 `py_compile` 无法发现运行时对象 API 差异。
- **做法**：使用 `app.router.add_event_handler` 并在真实依赖镜像中完成 import/pytest 收集；新 Pydantic 模型使用 `ConfigDict`。框架相关改动不能只靠语法编译验收。

### 5.20 新版 FastAPI 的 include_router 不再把路径扁平暴露在 app.routes

- **现象**：独立 `tenant_session.router.routes` 中 method/path 完整，最终 OpenAPI 也有接口，但遍历顶层 `app.routes` 时看不到 `/api/v2/session`，测试误报为“路由未注册”。
- **原因**：当前 FastAPI 用懒加载 `_IncludedRouter` 保存 include 结果；顶层对象的 `path` 为 `None`，有效路径在内部 candidate 中，和旧版本直接展开 APIRoute 的表现不同。
- **做法**：独立 Router 断言自身 method/path，最终应用使用 `app.openapi()['paths']` 断言可达契约，再按 `original_router` 身份确认只 include 一次。不要依赖 FastAPI 私有 candidate 结构，也不能只用顶层 `app.routes.path` 判断可达性。

### 5.21 远端 `docker exec psql -c` 不要嵌套拼接含单引号的 SQL

- **现象**：SSH 命令外层、容器 `sh -lc` 和 `psql -c` 三层引号叠加时，SQL 字符串字面量会提前终止 shell 引号，被 Bash 当成命令；终端出现多条 `command not found`，SQL 实际未送入 PostgreSQL。
- **原因**：这不是数据库语法错误，而是远端 shell 在 `docker exec` 之前完成了错误插值。继续增加反斜杠既难审查，也可能把凭据或可控文本带进命令行。
- **处理**：把固定 SQL 在客户端编码为 base64，经标准输入 `base64 -d | docker exec -i ... psql` 传入；SQL 内显式 `BEGIN TRANSACTION READ ONLY`、statement timeout 和 `ROLLBACK`。不要在输出中打印容器环境或连接串。
- **验证**：必须同时看到 `BEGIN/SET/.../ROLLBACK` 与预期只读结果；只看到 shell 报错或空输出不算数据库查询成功。

### 5.22 Windows `bsdtar` 解包 Git 归档可能损坏中文路径

- **现象**：用 `git archive | bsdtar -x` 构造临时 QA 快照时，中文文件名被解码成乱码或非法路径，导致快照不完整、测试结果失真。
- **原因**：Windows 自带 `bsdtar`、当前控制台编码与 Git 归档中的 UTF-8 路径处理并不总是一致。
- **做法**：Windows 上先由 Git 生成 ZIP，再用 PowerShell `Expand-Archive` 解压；解压后核对迁移和中文知识文件数量。QA 快照只能来自 Git 索引或已确认的提交，不能顺手包含用户未提交文件。

### 5.23 离线镜像回退只能修改临时 QA 快照

- **现象**：Docker Hub 元数据/鉴权域名解析到不可达 IPv6，拉取项目指定的 Python 基础镜像失败，但本机已有另一兼容小版本的缓存镜像。
- **风险**：为绕过网络故障直接修改仓库 Dockerfile，会把临时 QA 条件伪装成正式运行时升级，并使验证环境与部署契约发生无记录漂移。
- **做法**：只在一次性、可删除的 Git 索引快照中替换为缓存镜像，验收记录必须注明实际 Python 版本、失败原因及仓库 Dockerfile 未变；网络恢复后仍应在项目指定版本上复验。不得把临时回退提交为生产配置。

### 5.24 授权撤销不能回写已完成审核的 Candidate 终态

- **现象**：撤销 Grant 的触发器若使用 `candidate_status <> 'withdrawn'` 作为更新条件，会把已经完成审核的 `closed` Candidate 也改成 `withdrawn`；Review 虽保持 completed，但 Candidate 的终态语义和后续 reopen 门禁被破坏。
- **原因**：撤权处置把“尚未开始/正在审核”和“已经形成不可覆盖结论”混成一个更新范围。授权失效应阻止后续新写，不能反向改写已经完成的业务事实。
- **做法**：撤权只允许 `open/in_review → withdrawn`，同时取消当前 active Review；`closed` Candidate 和 completed Review 保持不变。已发布迁移不得回改，使用下一编号向前替换触发函数，并测试撤权前后 `closed` 行字节级不变以及重审因 inactive Grant 被拒绝。

### 5.25 PL/pgSQL 返回列名与查询列名会产生运行时歧义

- **现象**：`RETURNS TABLE(batch_id, ...)` 的函数内使用未限定的 `SELECT id, status`，静态 SQL 检查和迁移执行都能通过，首次调用时却报列引用歧义。
- **原因**：PL/pgSQL 把 `RETURNS TABLE` 输出列当作函数变量；它们会与查询表中的同名列同时参与名字解析。只执行 DDL 不会编译到所有运行路径。
- **做法**：函数内的表列统一用明确 alias 限定，并在一次性 PostgreSQL 中真实调用每个公开函数。迁移验收必须同时包含“全量执行 + `--check` + 业务路径集成测试”，不能以迁移成功代替运行时证明。

### 5.26 不可变源码挂载会遮蔽源码目录里的运行密钥

- **现象**：Worker 切到 `/home/m/releases/<sha>/wxsearch:/app/wxsearch:ro` 后，旧源码目录中的 `wxsearch/config/secrets.json` 不再可见，LLM 每分钟返回 401；宿主机文件本身仍存在，容易误判为“密钥已经配置”。
- **原因**：容器看到的是发布目录而不是 `/home/m/xiansuo/wxsearch`；密钥跟源码同路径也会让发布、回滚和权限治理互相耦合。
- **做法**：真实密钥复制到仓库与 release 之外的 0700 目录，文件固定 0600，再以只读目录挂载并由 `WXSEARCH_SECRETS_PATH` 定位。发布验收只输出路径、权限、存在性和长度，绝不回显值；LLM 默认保持关闭，合成数据验证通过后再显式开启。

### 5.27 Docker Compose 1.29 原地重建可能因 ContainerConfig 崩溃

- **现象**：正式机用 Compose 1.29.2 为已有 Backend 合并新的 volume override 时，在 recreate 阶段抛 `KeyError: 'ContainerConfig'`，旧容器已被停止并改名，8000 暂时无监听。
- **原因**：Compose v1 与新版 Docker 生成的镜像元数据不兼容，读取旧容器 image config 时假定存在已废弃的 `ContainerConfig` 字段。
- **做法**：优先升级并验证 Compose v2。升级前若必须发布，只能针对已确认无状态、可由 Compose 完整重建的单个应用容器：先记录并验证精确名称与挂载，删除容器记录后用 base + Git release override 新建，并内置 base-only 自动回滚和内外网健康检查。数据库、Redis、卷以及整栈 `down` 均不在该操作范围。

### 5.28 测试 Compose 与已部署环境文件必须按版本成对升级

- **现象**：把最新 `docker-compose.staging.yml` 配合旧发布的 `.env.staging` 执行 `config`，因新引入的运行角色变量缺失而 fail closed；现有测试栈仍健康，但不能直接套用最新 Compose。
- **原因**：021～025 的安全地基增加了运行 LOGIN 配置，旧测试发布只保存较早的管理员型变量。代码镜像升级与 Compose/数据库角色升级不是同一个发布边界。
- **做法**：纯应用验证可沿用已部署版本的 Compose 契约，只替换由当前 Git SHA 构建的镜像；完整 Compose 升级必须另开批次，先配置仓库外 0600 环境文件、执行角色 provision/check 和迁移门禁，再切服务。不得临时补假变量或跳过 `config --quiet`。

### 5.29 分布式落库改造后必须回归本地 SQLite 契约

- **现象**：采集节点关闭 `distributed.enabled` 做隔离 canary 时，程序在操作微信前报 `Database.__init__() takes 2 positional arguments but 3 were given`；即使只去掉多余参数，首次重复文章还会因缺少 `last_reason` 再次报错。
- **原因**：`Collector` 为分布式 Sink 统一了 `save/count/close/last_reason` 接口并把去重配置传给本地库，但 SQLite `Database` 没有同步构造参数和判定原因契约；只做 import/静态自检无法触发实例化路径。
- **做法**：本地 `Database` 接受可选去重配置并始终维护 `last_reason`（新增为 `new`、指纹冲突为 `exact_duplicate`）。采集发布门禁必须至少实例化一次关闭分布式的 `Collector`，并用临时 SQLite 验证新增、重复、计数和关闭路径；不能只验证分布式 worker 或模块导入。

### 5.30 清洗器异常不能默认放行文章

- **现象**：PC UIA 的轻量 `Article` 没有 `account_id`，规则清洗器直接访问该属性后抛异常；采集编排又把清洗异常当作放行，导致所有文章绕过广告、长度、时效和列表页规则。
- **原因**：服务端富模型与采集端轻模型的字段契约没有对齐，且“清洗失败放行”把代码缺陷转化成了数据污染。
- **做法**：可选字段统一用 `getattr(..., 默认值)` 读取；清洗启用时异常必须对当前文章 fail closed（记录原因并跳过），不能以可用性为由写入未经判断的内容。回归测试必须证明缺少可选字段仍可完成规则判断，以及清洗器抛异常时落库层零调用。

### 5.31 已停用的宽泛关键词必须在搜索前拒绝

- **现象**：`全国 先进 推荐` 的结果中，多数杂质会被入口语义门禁拒绝，但“教练报名流程”因含“报名”等通用行动词仍可能通过粗筛。
- **原因**：文章粗筛追求高召回，不能可靠替代关键词治理；被业务明确停用的宽泛词若仍被旧调度、旧配置或人工参数送入，事后语义规则仍存在误放概率。
- **做法**：对业务明确停用的精确关键词及纯停用词组合在采集器共用的 `_collect_one` 入口搜索前 fail closed，确保手工 `run()` 与无人值守 `collect_keyword()` 都是零 UI 操作、零文章读取、零入库；服务端文章准入再次按同一词表拒绝。含明确业务语义的长词（如“推荐申报”）不能用子串误伤。服务端调度仍应移除/停用这些关键词，代码门禁只作为旧配置和调度漂移的第二道保护。

### 5.32 Windows 的 `core.autocrlf` 会让发布归档偏离 Git blob

- **现象**：归档整体 SHA-256 上传前后一致，但解包后的 Python 文件比 `git cat-file blob` 多出每行一个 `CR`，单文件 SHA 校验失败。
- **原因**：宿主 Windows 全局 `core.autocrlf=true`；普通 `git archive` 在该环境下导出了 CRLF 文本。代码可运行不等于发布物可复现，不能跳过 blob 校验继续部署。
- **做法**：发布统一使用 `git -c core.autocrlf=false archive ... <已推送SHA>`；同时核对归档整体 SHA、归档内关键文件 SHA 与 Git blob SHA。校验失败的 release 未挂载前即停止，确认未被容器引用后删除半成品并从同一 Git SHA 重建，禁止另起平行源码副本。
