# 需求登记（产品路线与实施队列）

> 本文件登记已经确认的业务目标、当前能力与待实施事项。目标架构以 `docs/总体架构与演进路线.md`、`docs/决策记录.md` 为准；任务进入开发前还需拆成可验收的迭代。

---

## 1. 已确认的业务边界

- 服务对象是需要举办评选、投票、征集活动的主办方。
- 当前有 **3 家相互竞争的独立公司** 使用系统；每家公司现有 1 名资源审核员、8 名业务员。
- 同一条公开资源可分发给三家公司分别审核和跟进，不做跨公司抢占；但公司内部同一 `event_edition` 只保留一个有效商机，防止内耗。
- 微信搜一搜是当前主渠道，架构必须预留网站、公众号、新闻、搜索引擎等全网渠道连接器。
- 实时线索和近 3 年历史活动采用不同任务优先级与产品入口；历史数据用于建设主办方库、活动届次和联系证据，不直接淹没实时审核队列。
- 范围覆盖采集、标准化与去重、AI 研判、租户审核、业务协作、CRM 跟进、结果反馈闭环；OA 先做销售协作能力，不扩展成人事、考勤、薪资等通用 OA。

---

## 2. 当前已具备（兼容运行能力）

- 登录鉴权、团队/角色、成员管理和个人操作状态隔离。
- 微信搜一搜/搜狗采集、Celery 调度、文章去重、LLM 清洗、线索看板。
- 公海库、AI 活动库、收藏/反馈等基础能力。

> 当前的“团队 + 个人状态隔离”不等于目标的公司级多租户隔离。现有表和页面在迁移期间继续服务，不能据此宣称三家公司数据已完全隔离。

---

## 3. P0：稳定现网与多租户地基

**目标**：保持正式环境持续接收采集数据，同时为三家公司独立运营建立不可绕过的隔离边界。

- 建立真实的 `tenant/company`、租户成员、角色和数据访问策略；现有团队数据完成映射。
- 所有租户业务表带 `tenant_id`，请求上下文强制注入租户；关键表启用 PostgreSQL RLS，并增加越权回归测试。
- 公共事实与租户私有业务分层：公开文章、活动、主办方、公开联系证据可共享；审核结论、补充联系人、商机、跟进记录、报价和成交结果必须隔离。
- 建立 `event_edition -> tenant_resource_grant -> tenant_candidate -> tenant_review -> opportunity -> activity/outcome` 主链路；兼容现有 `qualified_leads`，采用影子写入、回填、校验、切读、回滚的渐进迁移。
- 为真实开发/预发布建立独立环境；本地 Ubuntu 采集节点是生产采集平面，不再被当作可随意试验的“测试库”。
- 固化日志、指标、告警、备份恢复、幂等投递和 LLM 处理状态，确保故障可发现、可重放、可回滚。

**验收重点**：三租户越权测试为零；现网采集不中断；重复消息不产生重复商机或重复 LLM 计费；迁移有可演练回滚路径。

**2026-08-22 实施裁决**：先完成采集端独立心跳与关键词租约稳定性，再进入租户/审核迁移；核心结构契约已冻结在 `docs/核心领域契约_v1.md`。近三年口径、原因码、分配/SLA、成交口径和正式租户映射在对应业务流编码前确认，不阻塞 RLS 与 expand-only 地基。

## 4. P1：资源审核与销售工作台

**目标**：让每家公司形成“资源审核员先核实，再交业务员”的闭环。

- 每个通过全局门槛并获得 `tenant_resource_grant` 的 `event_edition`，为对应租户幂等生成候选，保留独立审核状态和评分；不是所有公开活动都无条件进入三家公司队列。
- 审核拆分为状态、决定和业务去向：决定为 `qualified`、`rejected`、`needs_more_info`，去向为销售、培育、竞品监控或归档，并记录结构化原因和证据。
- 审核员可保存本公司的字段覆盖或提交共享事实纠错申请；活动/主办方/公共联系人合并拆分必须由平台数据管理员审批，不能让公司 A 的判断直接改变 B/C 所见事实。
- 审核通过后在本租户内生成或合并商机，可按规则/负载/区域分配给业务员。
- 业务员工作台提供待办、电话记录、提醒、下一步动作、商机阶段、联系人、报价与结果。
- 设定首审、首次联系、超期回收等 SLA；所有分配、转交、修改保留审计日志。
- 租户内防重复跟进：同一租户、同一 `event_edition` 最多一个活跃商机；明确转交和重开流程。

---

## 5. P1：主办方与历史活动情报库

**目标**：把近 3 年已举办活动转化为辅助销售判断的长期资产。

- 建模主办方、活动系列、活动届次、承办/协办关系和联系证据，不再把“文章”直接等同于“线索”。
- 聚合同一活动的多篇来源，保留原文、发布时间、抓取时间、来源渠道和可信度。
- 计算主办方举办次数、最近一次举办、常见月份、周期、地区、活动类型和历史联系人。
- 历史回溯使用低优先级、可暂停、可续跑的任务；实时信号优先进入审核队列。
- 联系方式保存来源、发现时间、验证状态和有效期；公开证据可共享，租户人工补充内容隔离。

---

## 6. P2：多渠道采集平台

**目标**：保持微信搜一搜主渠道优势，同时降低对单一采集方式的依赖。

- 定义版本化的标准采集文档契约，连接器只负责领取任务、采集和提交原始证据。
- 新增外部/移动采集节点通过签名、限流、幂等的 HTTPS Ingestion API 接入；不向外暴露 Redis、Celery 或数据库凭据。
- 建立连接器注册、能力声明、设备心跳、租约、速率限制、失败重试和渠道质量指标。
- 所有渠道共用标准化、实体解析、活动聚合、AI 研判和租户分发链路。
- 对每个渠道统计有效活动率、重复率、时效、成本和故障率，用数据决定投入。

---

## 7. P2：人在回路的智能闭环

**目标**：利用审核、跟进和成交结果提升排序与清洗质量，同时控制模型漂移。

- 采集审核驳回原因、商机阶段、有效联系、报价、成交/流失及原因，形成版本化训练/评估样本。
- 规则、黑名单、Few-Shot 和模型版本只通过候选评审后发布，不允许单个用户反馈自动改变全局规则。
- 先做离线评估和影子评分，再小流量发布；记录模型/提示词版本、输入哈希和输出，避免同版本重复清洗。
- 分开评估三个层面：公开事实抽取、全局相关度、租户个性化排序；租户私有反馈不得泄漏给竞争公司。

---

## 8. 资源可见策略（现在与未来）

- 当前默认：`shared_competition`，符合条件的公开活动可同时进入三个租户的候选队列。
- 租户自建关键词：默认 `tenant_private`，结果仅本公司可见，不再采用“个人私有关键词”作为正式业务边界。
- 预留：`selected_tenants`（指定公司）和 `exclusive`（独占）策略，只有明确商业规则后启用。
- 一条公开文档命中全局词时可进入共享情报层，但能否成为某租户候选仍需经过租户分发规则和幂等键判断。

---

## 9. 暂不实施

- 一次性推倒重写、过早拆分微服务、Kafka/Kubernetes/Elasticsearch 等与当前规模不匹配的基础设施。
- 通用舆情驾驶舱、情感传播分析等偏离获客闭环的功能。
- 人事、考勤、薪资、行政审批等通用 OA。
- OA 或第三方直接读取内部业务表；跨系统一律走版本化、租户受控的 API 或事件契约。
