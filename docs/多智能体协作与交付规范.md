# 多智能体协作与交付规范

> 状态：生效中
> 适用范围：本仓库的 Codex sub-agent、独立 Codex 窗口、人工开发者、测试与发布操作
> 上位约束：`AGENTS.md`、`docs/决策记录.md`，尤其是 D-016、D-017、D-018、D-019、D-020

## 1. 目标与基本原则

本规范的目标不是让更多 Agent 同时写代码，而是让互不重叠的工作并行，让公共契约、数据库和生产变更有序串行。最终交付必须表现得像一个人完成：只有一套事实、一个接口语义和一条可回滚的发布链路。

必须遵守以下原则：

1. Git 仓库是代码、迁移、架构决策和交付证据的唯一事实来源；不得建立手工复制的平行源码。
2. `main` 始终保持可部署。任何未评审、未验证的代码不得直接进入 `main`。
3. 并行单位是“边界明确、验收独立、文件不重叠”的任务，不是功能名称相近的一组模糊要求。
4. 同一文件同一时刻只能有一个写入者；数据库迁移序号、公共 API、事件 payload、状态机和生产发布始终串行。
5. 共享工作区的 sub-agent 不切分支、不提交、不推送；独立窗口使用独立 Git worktree 和独立 `codex/*` 分支，不得让两个窗口在同一个 worktree 切换分支。
6. 先冻结契约，再让上下游并行；契约改变必须重新确认影响范围，不能靠合并冲突发现设计分歧。
7. Agent 的“完成”只表示候选成果完成；通过质量门禁并由集成负责人验收后才算仓库交付完成。
8. 生产环境禁止直接改源码。发布物必须能定位到 Git SHA，并具备健康检查和回滚方案。

## 2. 当前工程事实与建设目标

当前仓库已经有 `pytest` 配置、少量 LLM 开关测试、环境检查脚本和一个历史的综合测试脚本，但测试覆盖仍很薄；目前没有 `.github/workflows`，也没有可供破坏性验证的共享测试/预发布环境。本地 Ubuntu 是生产采集与智能加工平面，不是测试环境。数据库采用 `docs/migrations/NNN_*.sql` 和 `schema_migrations` 串行执行。

因此质量门禁分两层：

- **立即执行的临时门禁**：基于当前已有命令，由集成负责人本地运行并把结果写入交接/PR；失败不得合并。
- **目标 CI 门禁**：阶段 0 优先落地自动化工作流，此后用分支保护强制执行，人工口头声明不能替代 CI 结果。

不得把本规范中的目标能力描述成已经存在。CI、测试夹具、覆盖率基线和影子数据库尚未落地时，要作为显式任务排期。

## 3. 六类角色与职责边界

“窗口”代表职责角色，不代表六个 Agent 必须同时在线。同一 Agent 在不同批次可以承担不同角色，但一个任务期间不得同时担任作者和最终批准者。

### 3.1 总负责人 / 集成窗口

默认常驻，拥有集成责任，不包揽所有代码实现。

职责：

- 将需求拆成任务，标记依赖、验收条件、风险和文件租约。
- 维护总体架构、决策记录、当前开发批次和公共契约版本。
- 分配迁移序号，裁决跨域设计，决定哪些任务可以并行。
- 检查所有 Agent 的 diff、测试证据和交接说明。
- 在共享工作区统一提交；评审并合并独立窗口的 PR。
- 维护集成分支可运行，组织测试环境部署、生产发布和发布后验收。
- 发生冲突或事故时冻结相关工作，指定唯一恢复负责人。

默认所有权：

- `AGENTS.md`
- `docs/决策记录.md`
- `docs/总体架构与演进路线.md`
- 公共契约、跨域状态机和开发批次清单

集成负责人不是公共文件的永久唯一作者。需要别人实现时，必须授予短期文件租约并在交接后收回。

### 3.2 采集与边缘节点窗口

职责：

- 微信 PC UIA 驱动、搜狗及后续 Connector。
- Windows VM 无人值守、标定、设备心跳、错误分类、恢复策略。
- 采集侧协议实现、采集质量、可观测性和 canary 验证。
- 发现新的 VM/UIA 坑位时先更新 `docs/坑位手册.md`。

默认所有权：

- `wxsearch/wechat_driver.py`
- `wxsearch/collector.py`
- `wxsearch/collectors/`
- `wxsearch/unattended.py`
- `wxsearch/sogou_loop.py`
- `docs/标定清单.md`
- 采集专用测试和文档

边界：不得自行改变标准文档 schema、任务名、同步 payload 或服务端字段语义。`distributed_sink.py`、`config.py` 和 `tasks.py` 属跨界文件，必须申请租约。

### 3.3 数据与智能窗口

职责：

- 原始文档规范化、去重、活动聚合、主办方/活动系列/届次模型。
- 规则筛选、LLM 调用、Prompt/模型版本、缓存、评分和离线评测。
- 历史三年回填的数据处理、证据链、预测和数据质量指标。
- 数据回填、对账、幂等和 AI 成本控制方案。

默认所有权：

- `wxsearch/smart_dedup_store.py`
- `wxsearch/content_hasher.py`
- `wxsearch/ai_filters/`
- `wxsearch/llm_cleaner.py`
- `wxsearch/organizer_aggregator.py`
- 新增的数据/智能领域模块及对应测试

边界：不能自行创建未登记的迁移号，不能直接修改租户 CRM 状态；公共事件 schema 和 `production_sync.py` 必须经集成负责人冻结。

### 3.4 多租户业务后端窗口

职责：

- 租户、用户、角色、权限和 PostgreSQL RLS。
- 租户资源审核、商机、客户、联系人、跟进、OA 待办和 CRM API。
- 同租户防重复、跨租户隔离、操作审计和状态机。
- 业务服务、repository 和 API 的边界清理。

默认所有权：

- `wxsearch/api/` 中的业务路由与鉴权模块
- 新增的多租户、审核、商机、OA/CRM 领域模块
- 相应的服务端测试和 API 契约测试

边界：不得直接复用共享公开联系人作为租户私有联系人；不得只靠前端隐藏实现隔离。涉及活动、主办方共享模型时，必须与数据窗口确认字段所有权。

### 3.5 前端工作台窗口

职责：

- 资源审核、电销工作台、客户/商机详情、运营和管理看板。
- 组件、交互状态、错误态、权限可见性和可访问性。
- 基于冻结 OpenAPI/契约夹具开发，不反向定义后端字段语义。
- 保持现有页面兼容，按页面逐步迁移，不复制一套平行前端。

默认所有权：

- `wxsearch/templates/`
- `wxsearch/static/`
- 未来经决策确认的前端应用目录
- 前端单元、组件和端到端测试

边界：权限判断必须由后端最终执行；前端可以隐藏按钮，但不能把隐藏视为授权控制。接口缺失时使用版本化 mock，不得临时改后端响应。

### 3.6 QA / 安全与发布窗口

职责：

- 从需求和风险出发设计测试，不只验证作者提供的成功路径。
- 建设单元、契约、集成、端到端、迁移、权限、性能和安全测试。
- 检查 Secret、依赖、日志脱敏、越权、注入、重放、幂等与回滚。
- 对测试环境做独立验收，形成发布清单和证据。
- 发布后检查同步、队列、数据库、租户隔离和关键业务漏斗。

默认所有权：

- QA 自己创建的黑盒、跨租户、契约、迁移和端到端测试文件（具体到任务租约）
- 未来 CI 工作流
- 测试夹具、契约快照、测试与发布检查文档

边界：QA 可以阻止合并和发布，但不得在验证时顺手修改业务实现；发现问题要回给原作者，除非集成负责人重新分配修复任务和文件租约。

## 4. 任务拆分与并行规则

### 4.1 任务进入并行前必须具备的信息

每个任务必须有唯一 ID，并写清：

- 业务目标和非目标。
- 输入、输出和可观察行为。
- 依赖的契约版本、迁移版本和前置任务。
- 允许修改的文件/目录及明确禁止修改的文件。
- 测试要求和验收样例。
- 数据、权限、同步、部署和回滚风险。
- 负责人、评审人和预计交接点。

缺少上述信息的任务只能由一个窗口探索，不能同时分给多个 Agent 实现。

### 4.2 可以并行的典型组合

- 采集驱动稳定性与独立的业务前端页面。
- 数据聚合算法与基于已冻结 mock 的前端组件。
- 业务后端实现与 QA 编写黑盒契约/越权测试。
- 历史数据分析探针与多租户领域设计，只要不同时修改迁移和公共模型。
- 文档、测试夹具准备与互不相交的模块实现。

### 4.3 必须串行的工作

- 数据库迁移编号分配、迁移合并和正式执行。
- 公共 Pydantic/schema、OpenAPI、事件 payload、Celery 任务名和状态机变更。
- `config.py`、`tasks.py`、`models.py`、`db_connector.py`、`distributed_sink.py`、`production_sync.py` 和 Compose 文件的交叉修改。
- 用户/租户身份、RLS 策略和跨租户数据迁移。
- 同一页面/模板或同一核心函数的重构。
- 测试环境的共享服务部署和所有生产变更。

串行不等于只能由集成负责人编码，而是同一时刻只有一名获得租约的作者，其他窗口可做只读评审和测试设计。

## 5. 文件所有权租约

### 5.1 租约登记

每个开发批次由集成负责人维护唯一活动任务清单，固定使用 `docs/开发批次/ACTIVE.md`。该文件只允许集成负责人修改，表格至少包含：

| 任务 ID | 负责人 | 分支/工作区 | 可写路径 | 交界文件 | 契约版本 | 状态 | 到期/交接条件 |
|---|---|---|---|---|---|---|---|
| 示例 `TENANT-001` | 业务后端 | `codex/backend-tenant-scope` | `wxsearch/opportunity/` | `api/auth.py` | `tenant-api-v1` | 开发中 | PR 可评审 |

规则：

1. 租约必须精确到文件或最小目录，不能写“整个 `wxsearch/`”。
2. 一个路径有写租约时，其他 Agent 只能读取；发现必须修改时先申请转移，不得“顺手改”。
3. 交界文件采用短租约，一次只完成一个可审查目的，完成后立即交回。
4. 共享工作区 Agent 发现未授权变化时立即停下并通知集成负责人，不自行 reset、checkout、stash 或覆盖。
5. 租约结束以“diff 已交接且集成负责人确认”为准，不以 Agent 自称完成为准。
6. 功能作者拥有其任务明确列出的白盒测试文件；QA 另领黑盒/越权/契约测试文件。不得用“领域默认写测试”和“QA 默认拥有 `tests/`”形成重叠租约。

### 5.2 跨界改动协议

跨界改动按以下顺序执行：

1. 提出变更说明：问题、受影响消费者、兼容性和备选方案。
2. 若存在两种可行实现，先在 `docs/决策记录.md` 形成裁决。
3. 集成负责人指定契约作者和唯一文件作者。
4. 先更新契约、样例和契约测试，获得所有消费者确认。
5. 冻结契约版本后，上游、下游和前端才能并行实现。
6. 如开发中必须改契约，原任务全部进入“等待重新冻结”，不得各自猜测继续。

## 6. Git、提交与 PR 规则

### 6.1 两种协作形态

共享工作区 sub-agent：

- 只改任务授权路径。
- 不运行 `git switch`、`git checkout`、`git stash`、`git commit` 或 `git push`。
- 交付 diff、测试命令、结果和风险，由集成负责人统一检查与提交。

独立 Codex 窗口：

- 必须使用独立 Git worktree；禁止手工复制项目目录，禁止两个窗口共享一个 worktree。
- 开工从最新 `origin/main` 创建 `codex/<领域>-<事项>` 分支。
- 一任务一分支，提交并推送自己的分支，通过 PR 交付。
- 不直接合并，不直接推送 `main`，不在分支内混入无关清理。

### 6.2 提交要求

- 提交信息用中文，说明为什么改和影响面。
- 一次提交只解决一件事；驱动、迁移、契约和业务实现尽量分开提交。
- 不得提交凭据、运行日志、数据库快照、构建产物和临时部署副本。
- 已在任何环境执行的迁移不得重写；修正必须新增向前迁移。
- 合并前将分支更新到最新 `main`，由原作者解决语义冲突并重新运行门禁。

### 6.3 PR 必填内容

- 任务 ID、背景、变更范围和明确非目标。
- 关键文件及字段所有权是否变化。
- API/事件/状态机变化及契约版本。
- 数据库迁移号、锁表风险、数据回填和新旧兼容方式。
- 测试命令、输出摘要、样例或截图。
- 多租户隔离与安全影响。
- 部署顺序、是否重启、监控项和回滚方案。
- 已知限制和后续任务。

至少需要一名非作者评审；涉及迁移、鉴权/RLS、同步、凭据、生产数据或 UIA 驱动时，还必须经过对应领域负责人和 QA/安全评审。

## 7. 数据库迁移串行化

1. 迁移号只由集成负责人分配；作者不得猜测下一个编号。
2. 任一时刻只有一个“待合并迁移槽”。后续任务可以设计 schema，但必须等待前一个迁移合并后领取编号。
3. 采用 expand → migrate/backfill → switch → contract：先加兼容结构，再回填和切流，最后在独立发布中清理旧结构。
4. 禁止在同一发布中直接删除旧列并让所有消费者同时切换。
5. 每个迁移必须验证：
   - 空库从基线顺序升级。
   - 已有测试库升级。
   - 脱敏生产快照或等价规模影子库升级。
   - 重复执行/已执行跳过行为。
   - 最终 schema 一致性、关键行数和约束。
   - 锁表时长、索引创建方式、回填批次和磁盘余量。
6. 迁移必须提供回滚或明确的向前修复方案。删除/覆盖数据前必须有已验证可恢复的备份。
7. 生产执行前冻结新的迁移合并；同一发布窗口只有一个迁移操作者。
8. 迁移失败时不得手工删除 `schema_migrations` 记录后盲目重跑。先确认事务状态、实际 schema 和数据，再由集成负责人决定回滚或向前修复。

## 8. API 与事件契约冻结

契约包括：HTTP 路径和方法、请求/响应 schema、错误码、分页、权限语义、Celery 任务名和参数、同步事件 payload、幂等键、枚举/状态机、时间和 ID 格式。

冻结规则：

1. 契约必须有版本标识、样例和机器可执行的契约测试。
2. 消费者开始实现后，字段只能做向后兼容的新增；删除、改名、类型/含义变化必须发布新版本。
3. 未提供字段与显式 `null`、空列表与未授权、UTC 与本地时间等语义必须写清。
4. 所有写接口明确租户作用域、幂等策略、审计字段和重试行为。
5. 事件消费者按白名单读取，未知字段应可忽略；生产者不能复用旧字段表达新含义。
6. 前端、采集、同步或第三方接入方必须对冻结版本明确确认；未确认不得进入并行实现。
7. 契约变更先更新测试夹具，再更新实现，最终由集成负责人统一切换版本。

## 9. 测试金字塔与证据要求

### 9.1 测试层级

| 层级 | 目标 | 责任与触发 |
|---|---|---|
| L0 静态检查 | 语法、导入、格式、类型、Secret、危险配置 | 每次提交/PR，快速必跑 |
| L1 单元测试 | 状态转换、评分、去重、权限规则、幂等计算 | 作者必写，数量最多 |
| L2 契约测试 | API、任务、事件、前端 mock 与 schema 兼容 | 契约作者和消费者共同维护 |
| L3 集成测试 | PostgreSQL、Redis、Celery、同步、迁移、RLS | 后端/数据改动必跑 |
| L4 端到端测试 | 采集事件到审核、商机、反馈的最小闭环 | 集成批次和发布候选必跑 |
| L5 环境/canary | 微信 VM、隧道、容器、真实模型、生产只读核验 | 驱动或发布相关变更按风险运行 |

测试要求：

- 新业务规则必须先有正常、边界、失败和重试测试。
- 所有租户业务表都要测试：同租户可见、跨租户不可见、伪造 `tenant_id` 无效、平台管理员敏感读取有审计。
- 所有同步/采集写入要测试重复提交、乱序、部分失败和重放。
- LLM 测试默认使用假客户端和固定样例；真实模型只做受预算控制的离线评测，不能成为普通 CI 的不稳定依赖。
- UIA 变更必须记录微信版本、VM 标定、复现步骤和 canary 结果。
- 修复缺陷必须增加回归测试，防止相同问题再次出现。
- 新增或修改的核心业务代码目标行覆盖率不低于 80%；权限、状态机、计费/同步和数据隔离规则目标不低于 90%。历史代码总覆盖率逐步提高，不用虚假的低价值测试追求一次达标。

### 9.2 当前临时门禁

在正式 CI 建成前，按变更范围运行并记录以下最低检查：

```text
python -m compileall wxsearch
pytest -q tests/test_llm_clean_switch.py
docker compose --env-file .env.example config
docker compose --env-file .env.example -f docker-compose.prod.yml config
```

Compose 配置检查在干净 worktree/CI 中必须显式使用已跟踪的安全占位配置，例如 `docker compose --env-file .env.example config`；禁止依赖或打印开发者真实 `.env`。除此之外必须运行受影响模块的针对性测试。当前 `tests/run_tests.py` 会访问运行中的服务并改变测试数据，不能当作无副作用的 PR 单元测试；只能在未来建立的隔离测试环境按其前置条件执行。

当前迁移运行器会写 checksum 但尚未核对已应用文件是否被修改。在第一个新迁移进入评审前，必须先增加“数据库记录 checksum 与仓库文件不一致即失败”的只读校验，并纳入临时门禁；在此之前不得声称“已执行迁移不可修改”已被自动保障。

## 10. CI 质量门禁

阶段 0 建立以下工作流，并将必需检查绑定到 `main` 分支保护：

### 10.1 PR 快速门禁（必须全部通过）

- 语法/导入、格式和静态检查。
- Secret 扫描与敏感文件检查。
- 单元测试、契约测试和变更代码覆盖率。
- Compose 配置渲染检查。
- 迁移命名、顺序、checksum 和“已执行迁移不可修改”检查。
- 公共契约快照差异检查；存在差异时必须带契约版本和批准记录。

### 10.2 PR 集成门禁（后端/数据改动必须通过）

- 临时 PostgreSQL/Redis 环境集成测试。
- 空库全量迁移和已有库增量迁移。
- RLS/跨租户越权测试。
- 事务发件箱、正式接收端幂等和字段所有权测试。
- 最小 API 健康与业务闭环测试。

### 10.3 发布候选门禁

- 从 Git SHA 构建不可变镜像并生成构建清单。
- 测试环境升级、健康检查、关键数据对账和回滚演练。
- 依赖/镜像漏洞检查、日志脱敏和配置检查。
- 性能基线：关键查询、队列积压、迁移锁时长和批处理吞吐不明显退化。
- QA 签署验收证据，集成负责人确认发布清单。

以下情况一律不得以“先合并再补”为由绕过：测试失败、Secret 命中、跨租户泄露、迁移不可验证、生产无回滚路径、契约消费者未确认。

## 11. 部署权限与生产审批

### 11.1 权限矩阵

| 环境 | 可执行者 | 前置条件 |
|---|---|---|
| 本地/临时测试 | 任务作者 | 仅使用隔离数据，不影响共享服务 |
| 真正的开发/预发布环境（当前尚未建立） | 集成负责人或指定 QA | 隔离数据、合并提交、部署锁、备份/健康检查、通知其他窗口 |
| 本地生产采集平面 | 采集负责人或集成负责人 | 禁止通用测试/清库；只做已批准 canary、只读诊断和可回滚运维 |
| 采集 VM canary | 采集负责人，集成负责人知情 | 指定一台 VM、版本/配置记录、明确回退 |
| 正式环境 | 集成负责人指定的唯一发布操作者 | 已评审 Git SHA、发布清单、审批和回滚准备 |

任何 Agent 不得因为拥有 SSH 凭据就自动获得部署授权。凭据不等于审批。

### 11.2 必须获得业务负责人明确批准的生产变更

- 数据删除、批量覆盖、历史回填影响正式业务数据。
- 数据库迁移、RLS/权限、租户归属、认证和凭据轮换。
- 正式同步字段所有权、幂等规则、LLM 执行环境或模型成本策略变化。
- 公网入口、隧道、端口、防火墙和第三方接入变化。
- 预计停机、不可逆迁移或回滚需要恢复数据库。
- 大范围采集 VM 发布、自动联系客户或任何对外写操作。

已批准发布批次内的向后兼容代码修复，可由集成负责人按约定发布窗口执行，但必须在发布前给出 SHA、影响面和回滚点。

### 11.3 生产发布顺序

1. 冻结发布范围和 Git SHA。
2. 验证备份可用、容量充足、迁移和回滚命令已复核。
3. 在真正的开发/预发布环境部署并完成数据对账；环境尚未建立时不得拿本地生产采集库替代，发布批次保持阻塞。
4. 获得所需审批，建立发布锁，只保留一个操作者。
5. 按兼容顺序执行：扩展 schema → 兼容后端/worker → 前端/消费者 → 回填/切流。
6. 检查健康、错误率、队列积压、同步延迟、关键行数和租户隔离。
7. 观察期结束后记录结果；未达到阈值立即停止扩量并执行回滚/向前修复。

## 12. 完成定义（Definition of Done）

任务只有同时满足以下条件才可标记完成：

- 业务验收条件逐条通过，非目标没有被偷偷扩大。
- 代码位于权威目录，没有 `_new`、临时副本或服务器独有修改。
- 单元、契约、集成或环境测试按风险完成，证据可复现。
- API、事件、状态机、配置和迁移文档与实现一致。
- 多租户、权限、幂等、并发、错误和重试路径已验证。
- 数据迁移/回填有对账指标，旧字段的权威写入方明确。
- 日志、指标、告警和审计足以定位故障，且不泄露凭据/租户私密数据。
- 部署、兼容、回滚和是否重启已写清。
- 新坑位、架构裁决和标定变化已进入对应文档。
- diff 只含授权范围，已由非作者评审；所有门禁为绿色。
- 集成负责人确认合并或提交，发布后关键指标验收完成（若该任务包含发布）。

“代码写完”“本机可运行”“Agent 返回完成”均不等于完成。

## 13. 上下文交接模板

每个 Agent/窗口结束、暂停或被轮换前必须提供以下内容：

```markdown
## 任务交接

- 任务 ID / 目标：
- 当前状态：未开始 / 进行中 / 待评审 / 已验证 / 阻塞
- 分支、worktree 或共享工作区：
- 基线 Git SHA：
- 已修改文件：
- 未修改但相关文件：
- 关键设计与理由：
- 使用的契约/迁移版本：
- 已运行测试及结果：
- 未运行测试及原因：
- 数据/租户/安全影响：
- 部署与回滚方式：
- 已知问题和风险：
- 下一步唯一建议动作：
- 需要集成负责人裁决的问题：
```

交接中不得写入密码、Token 或客户私密内容。测试失败必须原样说明，不能只报告“基本通过”。

## 14. 冲突与失败恢复

### 14.1 文件或语义冲突

1. 发现重叠修改立即停止相关写入，不继续扩大 diff。
2. 集成负责人确认两边基线、文件租约和业务意图。
3. 指定一名原领域作者作为唯一冲突解决者；另一方提供说明和测试，不同时编辑。
4. 以最新冻结契约和决策记录为准，不能仅以“能自动合并”为成功。
5. 合并后重跑双方测试和跨域契约测试。

共享工作区出现非本人改动时，不得 reset、checkout、clean 或 stash。先用只读 diff 确认归属，再由集成负责人处理。

### 14.2 Agent 中断或上下文丢失

- 没有完整交接时，接手者先读任务、diff、测试和相关决策，不从记忆猜测。
- 未确认字段所有权和契约前，只能只读分析。
- 同一阻塞连续尝试两次仍无新证据时，停止重复执行，升级给集成负责人重新拆分或裁决。

### 14.3 质量门禁失败

- 失败分支不得合并；由原作者修复，QA 复验。
- 不能通过删除测试、放宽断言、跳过 RLS/迁移检查来制造绿色。
- 如发现历史基线本身失败，建立独立基线修复任务，记录失败与本变更是否相关；高风险门禁仍不可豁免。

### 14.4 测试或生产部署失败

- 立即停止后续步骤和其他共享环境部署，保留日志、SHA、迁移状态和关键指标。
- 应用优先回退到上一不可变镜像；数据库按已批准方案向前修复或恢复，不盲目执行逆向 SQL。
- 同步/回填失败先停生产者，确认幂等和字段所有权后再重放。
- 生产事故必须补充根因、影响、恢复过程和防复发测试，再恢复并行开发。

## 15. 四个并发槽的轮换方案

当前最多四个并发槽，不同时启动六个角色。固定原则是：

- **槽 1 始终为总负责人/集成窗口**：拆分、答疑、只读审查、契约和集成；不长期占用大块实现任务。
- **槽 2、3 为当期两个主要实现窗口**：只选择依赖已冻结、文件互斥的任务。
- **槽 4 为质量/风险窗口**：设计测试、审查或做第三个独立任务；进入集成期时必须切换为 QA，不再开新功能。

推荐轮换：

| 批次阶段 | 槽 1 | 槽 2 | 槽 3 | 槽 4 |
|---|---|---|---|---|
| 架构/契约冻结 | 集成 | 数据与智能 | 业务后端 | QA/安全 |
| 多租户数据地基 | 集成 | 业务后端 | 数据与智能 | QA/迁移验证 |
| 审核/商机闭环 | 集成 | 业务后端 | 前端 | QA/契约/E2E |
| 采集稳定专项 | 集成 | 采集 | 数据与智能 | QA/VM canary |
| 历史主办方专项 | 集成 | 数据与智能 | 采集 Connector | QA/数据对账 |
| 发布候选 | 集成/发布 | 原作者待命 | QA/安全 | 只读监控或回滚待命 |

轮换规则：

1. 每个槽只接一个小任务，建议 0.5–2 天可形成可审查交付；超大任务继续拆分。
2. 槽位按依赖解锁，不按角色平均分配。没有可独立边界时宁可空一个槽，也不制造重叠修改。
3. 紧急采集故障需要插队时，替换一个实现槽，不挤掉集成和 QA；暂停任务先完成上下文交接。
4. QA 从设计阶段参与，但在集成期拥有独立槽，不能把全部测试留到六个模块都写完之后。
5. 一个批次最多同时存在两个生产代码作者；第三个执行槽优先做测试、契约、数据验证或只读评审。
6. 合并节奏按“一个 PR 绿色 → 合入 → 下游更新基线”推进，不积压多个修改同一契约的长寿命分支。
7. 每日/每轮由集成负责人清理已完成租约、重新排序阻塞项；休眠角色依靠交接文档恢复，不要求常驻占槽。

## 16. 建议的首批协作落地任务

在大规模功能并行前，先完成以下保护网：

1. 集成窗口：冻结第一条端到端闭环及 `tenant/event/review/opportunity` 最小契约。
2. QA 窗口：建立 CI、测试分层目录和 PostgreSQL/Redis 隔离测试环境。
3. 数据与后端窗口：共同设计、由一个迁移作者串行落地第一批 expand-only 表结构。
4. 前端窗口：契约冻结后用固定 mock 构建审核工作台骨架。
5. 采集窗口：在不触碰公共 schema 的前提下继续处理微信成功率和第四台 VM；需要 Connector 契约时等待冻结后接入。

完成保护网后，再同时推进“多租户审核闭环”和“采集稳定性”；不要一开始同时开发完整 CRM、历史三年回填、全网渠道和新前端。
