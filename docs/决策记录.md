# 决策记录

> 记录"两种做法之间怎么选"的裁决，避免两个智能体各自演进出不同实现。
> 格式：结论 / 理由 / 被否方案 / 适用边界。发现新的"两种做法"时，先在这里写一条再动手。

---

## D-001 唯一权威源码包为 `wxsearch/`，部署包是构建产物

- **日期**：2026-08-18
- **结论**：`wxsearch/` 是唯一权威源码。推给 VM 的 `wxg01` 精简包属**构建产物**，改动必须回改 `wxsearch/`，不允许在部署包里长期演进。
- **理由**：本仓库曾累积 **6 份驱动副本**（34.4K / 34.4K / 42.8K / 50.7K / 53.9K / 60.9K），两个智能体各自改各自那份，导致同一个问题解决两遍、成果只有一边有。
- **被否方案**：让部署包独立演进、定期"对齐"——实测对不齐，人工比对成本高且易漏。
- **适用边界**：若将来采集端与服务端依赖冲突到无法共包，再考虑拆成两个包，但那时也必须**各有唯一来源**。

## D-002 采集端与服务端共用 `wxsearch/`，靠 config 开关区分行为

- **日期**：2026-08-18
- **结论**：不拆包。采集端与服务端共用同一个 `wxsearch/`，用 `distributed.enabled` / `unattended.enabled` 等配置开关切换行为。
- **理由**：`models.py`、`logger.py`、`unattended.py`、`config.py` 双方完全一致，拆包会立刻产生同步负担。采集端只是**不 import** 服务端模块（`tasks.py`、`db_connector.py` 等），不装 `psycopg2` 即可。
- **注意**：`db.py`（SQLite，采集端）与 `db_connector.py`（PG，服务端）是**两个不同用途的模块，不是新旧关系**，别互相覆盖。同理 `smart_dedup_store.py` 服务端版（38K）远大于采集端版（14K），属正常。

## D-003 采集循环统一用 `unattended.py`，废弃自写的本地循环

- **日期**：2026-08-18
- **结论**：无人值守循环统一走 `wxsearch/unattended.py`（领词 → 采集 → 上报 → 心跳 → 休眠）。Ubuntu 侧智能体自写的 `run_loop.py`（本地模式）仅保留为**离线技术验证工具**，不用于生产。
- **理由**：`run_loop.py` 不含 Celery/Redis/心跳调用，关键词写死在本地 config，导致：数据落 guest 本地 SQLite 不进 PG、设备监控看不到节点、无法参与服务端派词与租约调度。实测 4 台 VM 采了约 348 条全部滞留本地。
- **被否方案**：给 `run_loop.py` 补心跳/上报——等于把 `unattended.py` 重写一遍，两套并存必然再分叉。
- **适用边界**：需要脱网单机验证驱动时可用 `run_loop.py`，但**不得开启自启、不得长期运行**。

## D-004 设备状态唯一来源是 `devices` 表，废弃文件式心跳

- **日期**：2026-08-18
- **结论**：节点在线状态、当前采词、采集量一律以服务端 `devices` 表（经 `heartbeat_device_task` 上报）为准，看板 `/admin/devices` 是唯一视图。Ubuntu 侧的 `guest/inbox/hb-*.txt` 文件心跳降级为**调试辅助**。
- **理由**：两套心跳并存导致"一边看文件、一边看看板"，对同一台机器的状态判断不一致。
- **被否方案**：把文件心跳汇总进看板——多一层转换，且文件通道无鉴权、易被误改。

## D-005 远程控制采用"guest 常驻 agent + 拉模式"，但必须收口为命令白名单

- **日期**：2026-08-18
- **结论**：采纳 Ubuntu 侧已实现的思路——guest 内常驻 agent **主动轮询**宿主取命令并回传结果（拉模式）。但**必须**改为：命令白名单（枚举动作）+ 共享密钥鉴权 + 审计日志。
- **理由**：拉模式天然穿透 NAT、无需给 VM 开入站端口、IP 变化也不影响；键盘模拟只适合首次拉起 agent（弹窗抢焦点会吃掉按键）。
- **被否方案（安全红线）**：原实现用 `Invoke-Expression` 直接执行下发内容，且通道为**明文 HTTP 无鉴权**——等于任何能访问该端口的进程都能在 4 台 VM 上任意执行代码。**不得留存到长期运行。**
- **分层认知**：① 软开关（暂停/恢复采集，复用每轮配置拉取，最省）② 进程级（agent 拉起/重启采集进程）③ 平台级（`virsh` 控制 VM 电源，唯一能救卡死/关机的手段）。

## D-006 筛选未生效时"宁缺毋滥"，不退化为采集全部

- **日期**：2026-08-18
- **结论**：筛选项（排序/类型/时间）经面包屑回读校验，任一项未确认生效即抛 `FilterNotApplied`，重开搜索重试；重试耗尽则**跳过该关键词**，下轮再来。
- **理由**：旧实现在筛选失败时"按默认结果采集"，等于把「全部」视图的视频/无关内容混入线索库，污染下游 AI 研判与去重。数据正确性优先于采集量。
- **被否方案**：失败即采默认结果（原实现）；或直接抛 `DriverError` 终止（过于激进，瞬时 UIA 抖动很常见，应可重试）。
- **实现要点**：`FilterNotApplied` **不是** `DriverError` 子类——`_open_and_filter` 中 `except DriverError: raise` 会直接上抛，而 `except Exception` 才会重试。

## D-007 逐台差异参数一律走 `config.json`，不写死在代码

- **日期**：2026-08-18
- **结论**：每台 VM 可能不同的参数（搜索框/聊天图标坐标等）全部作为 `Selectors` 字段暴露，通过 `config.json` 覆盖。
- **理由**：原先 4 个坐标用 `getattr(self.sel, "...", 默认值)` 读取，但 `Selectors` dataclass 里**没有这些字段**——一旦写进 `config.json` 就 `TypeError` 崩溃，等于只能改代码来标定。5 台机各改一次代码不可维护。
- **落地**：`searchbox_chat_icon_x/y`、`searchbox_entry_x/y` 已补入 `Selectors` 与 `_DEFAULTS`，缺省为 win10-0 实测值（40/120/167/65），不填则行为不变（向后兼容）。

## D-008 SimHash 近似去重阈值定为 1.0

- **日期**：2026-08（沿用）
- **结论**：`dedup.simhash_threshold = 1.0`，即仅汉明距离 0（指纹完全相同）判近似重复。
- **理由**：目标语料多为同质公文（征集/评选通知），SimHash 区分度不足。阈值 0.9（dist≤6）大量误杀语义无关文章；0.95（dist≤3）实测 194 篇语料误杀率仍约 12%，且距离 4~6 段不携带有效信号。真转载实测均落在距离 0。
- **兜底**：规范化后完全一致的转载由第②层 SHA256 精确哈希捕获；部分改写只能依靠 SimHash/活动聚合等近似规则，放宽标题阈值也不能稳定解决，故收紧标题门槛。

## D-009 服务端连接池按“异常必归还 + 每进程限额”治理

- **日期**：2026-08-22
- **结论**：`DatabaseConnector` 使用线程安全连接池；查询和写入无论成功或失败都在 `finally` 归还连接，断开的连接丢弃；默认每进程最多 8 条连接，可通过 `DB_POOL_MAX` 调整。
- **理由**：本地生产采集平面（历史上曾称“测试环境”）出现数据库仍健康而 worker 池耗尽，根因是异常路径遗漏 `putconn`。Celery 的 4 个 prefork 子进程会放大泄漏；仅提高 PostgreSQL `max_connections` 只能延后故障，不能消除根因。
- **被否方案**：继续使用非线程安全的 `SimpleConnectionPool` 并把最大连接数调大；或依赖每个调用点手工 `close()`。前者会掩盖泄漏，后者容易遗漏且已在生产流程中失效。
- **适用边界**：批处理或连接数确有需求时，优先通过 `DB_POOL_MAX` 按实例规模调参，并确保总和低于 PostgreSQL `max_connections`；不得绕开连接池直接长持有连接。

## D-010 生产容器统一由 Compose 接管，数据卷名称显式配置

- **日期**：2026-08-22
- **结论**：数据库、Redis、worker、beat 和 backend 必须由同一份 `docker-compose.prod.yml` 管理；已有服务器通过 `PGDATA_VOLUME` / `REDISDATA_VOLUME` 指向原数据卷，新部署使用稳定的默认卷名。
- **理由**：手工 `docker run` 的应用容器没有 Compose 标签，也未注入 `DATABASE_URL` / `REDIS_URL`，导致容器表面运行、实际持续认证失败。直接执行 Compose 又会创建新命名卷，让原数据看似“丢失”。显式卷名兼顾可重复部署和旧数据保留。
- **被否方案**：继续手工补 `docker run -e ...`；或先复制整个 Docker volume 再切换。前者会再次配置漂移，后者增加停机和数据复制风险。
- **适用边界**：切换前必须先 `pg_dump`，核对实际挂载卷和表行数；只移除容器，不删除原 volume。真实口令只留在服务器 `.env`。

## D-011 本地生产采集平面的外部入口统一使用 SSH 反向隧道

- **日期**：2026-08-22
- **结论**：本地生产采集平面以 systemd 管理的 `leads-tunnel.service` 为唯一外部入口，云端 7080 转发到本地 Backend 8000；本机 Nginx 不属于默认运行栈。
- **理由**：现网已经由 SSH 隧道完成跨局域网访问。本机再启 Nginx 不参与云端访问链路，只增加端口冲突、配置漂移和错误健康判断。
- **被否方案**：把 `wxsearch_nginx` 纳入默认 `docker compose up`；或同时维护 SSH 隧道与本机 Nginx 两条等价入口。
- **适用边界**：Nginx 配置仅作为显式 profile 的备用方案。若以后正式切换入口，必须先更新本记录和部署文档，再停用隧道。

## D-012 服务端凭据以服务器 `.env` 为唯一运行配置源

- **日期**：2026-08-22
- **结论**：Compose 只引用 `POSTGRES_PASSWORD`、`REDIS_PASSWORD` 等环境变量，真实值只保存在服务器未跟踪的 `.env`；采集节点配置由同一来源生成，禁止在 Compose、脚本或部署包中硬编码口令。
- **理由**：本地生产采集平面的 Compose 曾硬编码一套 Redis 口令，而服务器 `.env` 保存另一套。一次无关的容器重建使 Redis 改用硬编码值，四台 Windows 节点同时认证失败、采集全面中断。配置文件存在不代表它已被运行栈使用。
- **迁移规则**：先从当前正常运行容器核对实际端点并把 `.env` 对齐，再执行 `docker compose config` 验证；不得为了“验证配置”重建数据库或 Redis。迁移后以 `.env` + Compose 渲染结果为准，不再从容器反向抄写凭据。
- **安全边界**：`.env` 权限设为 `0600` 且不得提交。任何历史明文凭据脚本必须退出长期运维链路；日志和文档只记录变量名，不记录真实值。

## D-013 本地生产采集数据通过幂等事件同步到正式业务库

- **日期**：2026-08-22
- **结论**：本地继续承担采集、去重和 AI 加工；正式库是公海/OA/CRM 唯一业务源。两者通过事务发件箱和带 HMAC 的 HTTPS 批量接口同步，不共享数据库、不把 Redis/PostgreSQL 暴露为公网数据通道。
- **字段所有权**：本地拥有原文与 AI 建议层；正式环境独占分配、跟进、成交、个人状态、人工标签与人工覆盖层。现有 `updated_by_human=true` 只是过渡期整行保护，目标模型必须按字段保存 provenance/人工覆盖，允许自动侧补充未被人工锁定的字段而不能覆盖人工决定。
- **幂等键**：文章使用 UUID/内容指纹，业务活动使用稳定 `event_edition_id`，传输消息使用全局 `message_id`（旧 v1 字段 `event_id` 仅作兼容别名）；不得假设本地和正式的自增 ID 长期一致。
- **被否方案**：定时整库覆盖会删除/回退业务员状态；直接连接正式 PostgreSQL 会扩大攻击面并耦合两端 schema；仅按最大自增 ID 拷贝会漏掉 LLM 后更新和重试记录。
- **过渡边界**：首次上线可在完整备份和影子库演练后做固定快照导入；该方式只用于初始化，不作为长期同步机制。

## D-014 正式宿主机只公开 Nginx，应用与数据端口绑定本机

- **日期**：2026-08-22
- **结论**：正式环境公网只保留 80/443（Nginx）和必要的 SSH；Backend 8000、PostgreSQL 5432、Redis 6379 的 Compose 端口绑定 `127.0.0.1`。容器间仍通过内部网络互通。
- **理由**：正式宿主机曾在 `0.0.0.0` 监听 5432/6379/8000。即使云安全组可能拦截，也不应把数据服务安全依赖于单层外围规则；Redis/PG 不是采集同步入口。
- **适用边界**：本地生产采集平面的 Redis 需要供 libvirt NAT 网段内 VM 使用，不能照搬本条绑定 localhost；应通过宿主防火墙只允许 VM 网段。正式如新增受控内网消费者，应走私网/隧道并显式登记，不恢复公网监听。

## D-015 LLM 只在本地生产采集平面清洗，正式环境只接收清洗结果

- **日期**：2026-08-22
- **结论**：本地生产采集平面负责采集、规则处理和 LLM 清洗，正式环境设置 `LLM_CLEAN_ENABLED=false` 作为硬开关，只接收本地端同步后的 AI 字段。显式环境变量优先于共享 `rule_config.json`。
- **理由**：两端使用同一份规则配置时，若规则文件优先，`clean_enabled=true` 会覆盖正式环境的关闭配置，造成同一批线索被两台服务器重复调用模型，增加费用且可能产生不一致结果。
- **被否方案**：允许两端各自清洗并依赖 `llm_status=done` 去重。两库写入和同步存在时间差，状态不能构成跨库互斥锁，也无法保证模型输出一致。
- **适用边界**：若未来迁移 LLM 执行节点，应先切断旧节点并确认队列清空，再在新节点开启；任何时刻只能有一个环境拥有清洗职责。

## D-016 采用渐进式重构，不重写整套系统

- **日期**：2026-08-22
- **结论**：保留已经运行的微信采集、Celery/Redis、PostgreSQL、去重、LLM 和事务发件箱；在同一仓库内新增目标领域模型和模块，以“加表与回填 → 新旧兼容 → 按模块切流 → 旧写入退役”的方式演进。不得另建 `v2` 平行仓库或复制整套源码。
- **理由**：现有采集链路承载真实数据且 UIA 适配成本高，整体重写会重新引入已解决的故障；另一方面，继续把多租户、审核和 CRM 字段堆进 `qualified_leads` 会让职责继续失控。
- **被否方案**：一次停机替换全部系统；或维持现有表结构不断追加字段和页面判断。
- **验收边界**：每一步都必须可回滚，旧页面在兼容期继续运行；每个字段任一时刻只有一个权威写入方。

## D-017 共享情报中台服务三个相互竞争的独立公司租户

- **日期**：2026-08-22
- **结论**：三个现有业务团队按三个独立公司租户建模。文章、公开活动届次、公开主办方和通用 AI 结果共享；审核结论、私有联系人、商机、跟进、报价、成交和绩效按 `tenant_id` 严格隔离。同一共享 `event_edition` 通过门槛并授权后可为每个租户各生成一条独立审核任务和商机，公司之间允许竞争，公司内部同一 `event_edition` 只能有一个有效商机。
- **可见策略**：当前公共资源默认 `shared_competition`；同时预留 `tenant_private`、`selected_tenants` 和未来 `exclusive`，改变商业模式时只切策略，不重构核心表。
- **理由**：共享上游可避免三次采集、去重和 LLM 成本；租户业务数据隔离符合三家公司独立经营事实。将三个公司继续当作普通 team 会导致 CRM 泄露和权限边界错误。
- **安全边界**：跨租户隔离必须由服务端查询作用域和 PostgreSQL RLS 双层保障，并有自动化越权测试；平台管理员读取租户 CRM 明细需独立授权和审计。

## D-018 全网采集采用连接器架构，实时与近三年历史回填分流

- **日期**：2026-08-22
- **结论**：微信搜一搜是当前主渠道，但所有信源实现统一 Connector/标准文档契约；内部节点通过受控任务通道运行，外部采集器和第三方数据只通过带鉴权、签名和幂等键的 HTTPS ingestion API 接入。实时商机使用高优先级队列，近三年历史使用低优先级、可断点恢复的 backfill 队列。
- **处理规则**：所有渠道共用规范化、文档去重、活动聚合、主办方识别、AI 研判和租户分发；多来源只增强同一活动证据，不生成重复销售线索。历史结果进入主办方/活动系列/届次库，不直接污染今日公海。
- **被否方案**：每个渠道各建一套库和清洗逻辑；外部节点长期直连 Redis/PostgreSQL；把历史文章批量当成当前线索。
- **适用边界**：第一期用微信 PC 和现有搜狗连接器验证契约，再接一类官方网页信源；不提前建设与销售无关的通用情感舆情大屏。

## D-019 以“活动事件—租户审核—商机”替代文章即线索

- **日期**：2026-08-22
- **结论**：原始文章只是来源证据；跨文章聚合后的活动/活动届次才是共享业务对象。每个租户对活动独立审核，审核通过后创建租户商机；主办方、联系人证据、活动系列、届次、审核、商机和跟进分别建模，不再让 `qualified_leads` 同时承担全部职责。
- **理由**：同一活动可能有公众号、官网和新闻多篇转载；按文章生成销售线索会重复计数和重复联系。近三年主办方举办次数也必须按独立届次而不是文章数计算。

## D-022 采集节点心跳独立于关键词采集生命周期

- **日期**：2026-08-22
- **结论**：`unattended.py` 在采集进程内启动独立守护线程，按固定周期上报当前关键词与本批活跃租约。租约协议 v2 以 `(channel, keyword, lease_id)` 为身份：Redis key/集合成员包含渠道，续租和结果上报必须同时匹配 owner、channel 与不可复用的 `lease_id`。设备 `online/offline` 仍以 `devices.last_heartbeat` 为准，`current_keyword` 非空临时派生忙碌，不新增第二套状态存储。Celery 任务只追加可选参数；旧 VM 的三参数领取、四参数心跳和六参数结果上报继续按 legacy 协议运行。
- **理由**：微信单个关键词采集可能超过 `DEVICE_ONLINE_TIMEOUT=600` 秒。旧实现只在一轮开始和每个关键词开始前上报，导致仍在采集的 VM 被标记离线并提前释放租约；即使单独修心跳，原租约仍会在 `SCHEDULER_STALE_CLAIM_MINUTES=15` 后回收。把心跳绑在 UIA 采集步骤上或只放大超时都不能证明进程及租约仍有效。
- **故障边界**：首次心跳成功前禁止领词；连续失败达到阈值或最近成功心跳超过安全年龄（硬上限 540 秒）后，完成已领批次但停止领取新批次，即使心跳线程仍 alive 也不例外。每个关键词开始前必须重新确认整批剩余 lease，并先把 `current_keyword` 写入本次确认；Redis 丢失或 owner 变化时允许当前词收尾，但原 VM 不得继续本地批次的后续词。关键词结束无论结果是否确认都停止续租；结果按同一 lease 有界重试，最终失败才停止续租。v2 stale recovery 只看续租时间；legacy 长任务临时用在线心跳保护，但领取初始化失败的 `recovery_only` marker 不受保护。结果提交在同一 PG 事务完成全局/渠道状态后才释放 Redis owner；PG 写失败保留租约重试。领取、续租、结果和回收共用生命周期锁，批量 Redis I/O 使用 pipeline，锁内 PG/Redis I/O 均有短超时；stale recovery 总预算 40 秒，为单次最坏操作预留 20 秒，Redis stale 与 PG orphan 各最多处理 10 条、持久游标轮转扫描，并逐轮交换优先阶段，必须在 60 秒 Redis 锁 TTL 前退出。回收失败的坏 marker 额外写 5 分钟短退避，覆盖 Redis 小 Set 忽略 `SSCAN COUNT` 并一次返回 `cursor=0` 的情况。领取 Redis 半失败时先补偿 PG；补偿失败则保留 marker，并周期对账 `PG running / Redis missing`。
- **被否方案**：单纯放大在线超时——只能推迟误判且延长真实故障发现；只按设备在线保护所有旧租约——会让已停止续租的失败任务永久 running；全渠道共用 `wxsearch:kw:{keyword}`——会互相覆盖；首次离线立即释放且没有代次校验——会让旧执行者与新执行者并发；新增文件式心跳——违反 D-004 的唯一状态来源。
- **发布边界**：逻辑调度渠道统一为 `souyisou`（`wechat_pc` 只表示采集实现/设备类型）。迁移 008 与所有实际渠道的 `keyword_channel_state` **完整**播种是硬前置（不只是渠道存在任意一行）；缺表、渠道无状态或部分回填时拒绝领取，不再回退到缺少 owner 的 `keywords.status`。新增关键词必须在同一 PG 事务内同步创建其全部渠道状态，避免一个新词触发全渠道停领。严格先完整升级服务端 worker（兼容旧协议），确认旧 VM 正常后再替换单台 v2 VM；新 VM 不能先连旧 worker。legacy 领取继续使用原始 keyword member/hash，只有 v2 使用渠道键；若回滚服务端，必须先停 v2 canary 并等待/核对 v2 租约清空，禁止新旧 worker 混跑同一队列。Redis marker 全丢时，当前仍明确采同一关键词的在线设备先保守完成，`current_keyword` 清空或设备离线后再回收。

## D-025 单 VM 协议升级使用不可变最低版本门禁

- **日期**：2026-08-23
- **结论**：领词协议从 legacy v1 升级到租约 v2 时，服务端先以不可变 Worker 发布环境变量 `CLAIM_PROTOCOL_FLOORS` 对目标 `vm_instance_id` 设置最低协议。门禁在渠道领取锁内、任何 PG/Redis 领取写入之前校验；非法配置对所有设备 fail closed。
- **两阶段切换**：Phase A 使用 `win10-01:3`，当前 v1/v2 都只能返回空，旧进程仅完成已持有关键词；只有当 Redis 跨渠道 owner 为零、`devices.current_keyword` 为空且注册渠道匹配时才停止旧进程。候选文件、进程、心跳校验通过后，Phase B 切为 `win10-01:2`，放行 v2 且持久拒绝 v1。
- **理由**：已投入 Celery 但尚未执行的旧领词消息没有可证明的排空时间上限；数秒 Redis 锁或短 TTL 门禁都可在旧进程死亡后误放行并创建孤儿租约。发布配置不依赖 Redis AOF 持久性，并同时覆盖该 Worker 内的所有并发消费进程。
- **回滚边界**：Phase B 成功后 v2 门禁保留。候选失败可恢复旧文件和进程，但保持 Phase A 安全停领；禁止为恢复单机产能直接去掉门禁。如必须回到无代次的 v1，必须先隔离并证明旧队列排空，或换用新设备 ID；未证明前宁可单机暂停。任何服务端回滚仍必须满足 D-022/D-024 的“先停 v2、再换 Worker”。

## D-026 迁移以规范化 SHA-256、连续前缀和最终态断言为发布门禁

- **日期**：2026-08-23
- **结论**：迁移 SQL 按 UTF-8 与 LF 规范化后计算 SHA-256，并由 `checksum_baseline.json` 冻结；数据库历史必须是仓库版本的连续前缀。正常 migrate 在执行 pending 前先验旧历史并取得 PostgreSQL advisory lock；`--check` 只读且遇 pending、断档、缺文件、空/非法 checksum 或漂移一律失败。
- **历史兼容**：001～020 的首次执行记录是 MD5，只接受基线逐项登记的精确值。只读核验确认 019、020 与规范化当前内容一致；018 的历史 MD5 为已知漂移，只有同时满足精确 MD5 和 `kw_stat_value` 最终态断言才兼容，禁止按版本通配或改数据库 ledger。
- **理由**：只按版本跳过会允许旧文件被改；直接按工作树字节计算又会把 Windows CRLF 当成内容变化。连续前缀和 advisory lock 分别防止乱序补跑与两个发布者并发迁移。
- **发布边界**：已发布 SQL 永久只读，修复一律增加新编号。业务进程不自动迁移；发布使用一次性 job，先在隔离 PostgreSQL 15 上完成空库、重复执行和篡改失败验证。

## D-029 租户运行时必须同时跨过数据库角色与事务授权两道门

- **日期**：2026-08-23
- **角色分离**：PostgreSQL 初始化/迁移 owner 只进入一次性 `schema-init/migrate/provision` 管理任务；Backend、Worker、Beat 的 `DATABASE_URL` 必须显式使用环境注入的运行 LOGIN，禁止默认或回退到 `admin`。运行角色必须 `NOSUPERUSER NOBYPASSRLS`、不是业务表 owner、不能在 `public` schema 创建对象，也不能写 `schema_migrations`。
- **发布方式**：角色名和密码不进入迁移 SQL、Compose 默认值或 Git；参数化工具从 `MIGRATION_DATABASE_URL` 与独立运行时环境变量读取，安全引用标识符，可重复 provision/check。先迁移、再授权、再用运行身份预检，最后才允许启动应用；本批只交付并验证工具，不修改已部署角色。

## D-032 通用运行角色对租户身份表只读

- **日期**：2026-08-23
- **结论**：普通 Backend runtime 对 `public.tenants`、`public.tenant_memberships` 只保留 SELECT，显式撤销 INSERT、UPDATE、DELETE、TRUNCATE、REFERENCES、TRIGGER，并用真实拒绝探针复核。租户发现和业务事务的成员授权统一调用已精确授权的 022 `app_list_active_tenants(UUID)` 窄函数，不再用要求 identity UPDATE 权限的直接 `SELECT ... FOR SHARE`；必须先匹配数据库返回的候选 tenant/membership/role，成功后才设置事务级 tenant GUC。
- **对 D-029 的修订**：D-029 中“先设置候选 tenant 上下文、再校验 membership”的顺序被本条替代为“先用当前 cursor 的 022 窄入口授权、成功后再 SET LOCAL”。禁止调用会另借连接的公共列表 helper；public UUID 仍只能来自已验签 legacy user 查询。
- **理由**：原 provision 先给 public 全表宽 DML，再只撤销 identity 表 DELETE，导致被攻陷的普通应用连接可能在当前 RLS 租户内新增成员或修改角色。RLS 约束行范围，不能替代成员管理授权。未来成员管理必须走独立管理身份或经过能力校验、审计和固定 `search_path` 的窄命令，不能恢复全表 UPDATE。
- **默认权限边界**：public 的兼容默认 DML 只服务普通数据面表；身份/控制面对象必须显式覆盖。未来映射台账放入 runtime 无 USAGE 的 `platform_control` schema，不允许依赖 public 默认权限；创建该 schema/台账属于后续独立迁移，不在本批提前落表。
- **一致性边界**：窄函数在每次请求事务中重新检查 enabled user、active tenant 与 active membership；撤销对下一次授权立即生效。已通过授权、正在执行的事务允许按其已取得的快照收尾；未来若业务要求“撤销必须中止在途写”，需另建带审计的授权锁/会话撤销协议，不能为此把通用 identity UPDATE 权限还给 runtime。
- **兼容与发布**：本批同步修改 `tenant_transaction` 并在隔离 PG15 证明 SELECT-only runtime 可完成授权与业务事务，不修改已部署数据库角色；实际授权变更仍须独立发布、预演和回退。

## D-033 审核写入使用窄授权行锁，撤权形成事务屏障

- **日期**：2026-08-23
- **结论**：普通只读发现仍使用 D-032 的请求快照；资源审核写入改走独立的窄 `SECURITY DEFINER` 授权函数。函数以已验签 legacy user id 和候选 tenant UUID 为唯一输入，在同一查询中校验 enabled user、active tenant、active membership，并对三者 `FOR SHARE`，返回数据库确认的 public user、membership 和 role；成功后才设置事务级租户上下文。
- **理由**：审核结论会形成不可覆盖历史与 outbox，撤销审核资格需要明确的事务屏障。共享锁使撤权更新等待已经取得写权限的短事务完成；撤权一旦提交，后续写事务立即拒绝，避免非锁定列表检查与撤权并发时仍落入新审核结论。
- **权限与锁序**：函数固定 `search_path=pg_catalog`、使用全限定对象、无动态 SQL、对 PUBLIC 撤销 EXECUTE，runtime 只获得该函数的精确 EXECUTE，身份表继续 SELECT-only。业务请求先锁身份授权，再按 Grant → Candidate → Review 顺序锁业务行；撤权管理路径不得反向先锁业务行再锁 membership。设置较短 lock/statement timeout，禁止事务跨 `await` 或访问外部系统。
- **测试**：真实非 owner runtime 必须证明无身份表 UPDATE 仍能授权写入；并发测试必须证明撤权被在途审核阻塞、审核提交后撤权完成、撤权完成后的下一事务零写拒绝。函数、角色或锁门禁缺一项，`TENANT_REVIEW_ENABLED=true` 必须启动失败。

## D-035 审核规则内容不可变，租户激活、评分与审核快照分层

- **日期**：2026-08-23
- **规则与激活**：规则集使用语义版本和 canonical JSON SHA-256，发布后禁止 UPDATE/DELETE；归一化原因行只能从同版本 JSON 中逐项精确发布，activation 前校验集合完整，不能在摘要不变时追加原因。租户通过独立、带审计历史的 activation 显式选择一个版本。没有唯一 active activation、规则未知或摘要不符时全部 fail closed，不回退到代码默认值或最近版本。运行角色对规则目录和 activation 只读，审核写事务只能通过固定 `search_path` 的窄函数锁定本租户 active activation，形成规则切换事务屏障。

## D-037 Windows 采集节点控制采用逐机密钥与签名动作信封

- **日期**：2026-08-23
- **结论**：淘汰共享 `cmd.txt` 与 `Invoke-Expression`。每台 VM 通过虚拟控制台一次性写入唯一控制密钥；其后的控制消息必须包含 `device_id`、递增 `sequence`、短期 `issued_at/expires_at`、枚举 `action`、固定结构参数及 HMAC-SHA256 签名。agent 仅接受匹配本机身份、未过期、序号更大的有效消息，并将审计结果独立回传。
- **动作边界**：只允许 `status`、`stage_release`、`activate_release`、`stop_after_current`、`rollback`；发布包必须按 SHA-256 校验，配置保留在节点私有路径，切换仅发生在关键词边界。不存在 shell、PowerShell 文本或任意脚本动作。
- **理由**：旧通道的 HTTP 明文、全节点共享文件与 `Invoke-Expression` 使任意可访问者都可能控制全部 VM，且无法单机灰度或追溯命令。逐机密钥和重放保护将攻击面收敛到单台节点；白名单将发布行为变为可审计状态机。
- **初始信任边界**：私钥绝不进入 Git、HTTP 下载目录、日志或回执。首次写入仅允许通过目标 VM 的虚拟控制台或其他带外介质完成；不得借旧广播 agent 下发密钥。旧 agent 在单机 v2 `status` 验证和审计回执成功后立即停止。
- **目标资格**：目标只能从平台批准的租户分发设置、active tenant、`shared_competition` 默认策略和 active 审核规则 activation 的交集生成并冻结。迁移不播种三家公司设置；新增 active tenant、membership 或旧 team 不能自动扩大分发范围。v1 只接受精确关联同一 Edition 的 `realtime_signal`，并拒绝 `result_published/ended/cancelled`；历史回填零 Target、零 Grant、零 Candidate。
- **事务与重试**：展开只生成 batch/target 计划；Worker 每次以独立事务 claim 一个 target，取得数据库生成的 fencing token，再以 `target_id + token` apply。apply 内部解析租户并按 target → 设置/tenant/ruleset → tenant+edition advisory lock → Grant → Candidate → outbox 固定锁序执行。单租户失败只更新自己的 retry/dead 状态，其他租户可独立提交；过期 token 与迟到完成一律拒绝。
- **幂等与历史**：`(tenant_id,event_edition_id)` 在 target 和 Candidate 层永久唯一。已有 active Grant/Candidate 只返回既有结果且不重复发事件；revoked/superseded Grant、withdrawn/closed Candidate 不自动复活、改绑或新授权，统一进入 `blocked_regrant_required`，另开 regrant/rebind 批次。首次创建 Candidate 与 `candidate.created.v1` 及 target succeeded 必须同事务提交。
- **角色隔离**：使用独立 Distributor LOGIN，必须 `NOSUPERUSER NOBYPASSRLS`、非 owner、无角色继承；对 `platform_control` 和业务表零直接权限，只直接授权四个固定 `search_path=pg_catalog`、全限定对象、无动态 SQL且已撤销 PUBLIC 的窄函数，并校验有效可执行的应用域 `SECURITY DEFINER` 集合严格等于这四个。历史 PUBLIC `SECURITY INVOKER` 辅助函数不视为直接授权，且在零表权限下不能扩大数据能力。普通 Backend runtime 不获得四个分发函数权限，迁移 owner 凭据不进入常驻容器。
- **发布边界**：本批只交付默认关闭的迁移、角色校验工具、服务层、契约和隔离测试；不部署、不创建真实 eligibility/Inbox、不接 Celery 公共 broker、不启用 Review、不创建 Opportunity，`sales_handoff` 继续 fail closed。

## D-038 未完成 LLM 清洗的规则候选必须停在隔离区

- **日期**：2026-08-23
- **结论**：`articles_core` 继续实时保存并可同步为来源证据；`qualified_leads` 的同步负载只有在 `llm_status='done'` 后才允许发送。发送端把旧的 `pending/fail` lead outbox 事件本地确认为质量门禁抑制，不向正式环境传输；接收端再次拒绝任何非 `done` 的 lead payload，形成双重 fail-closed。后续 `done + has_lead_value=false` 仍可同步为历史活动/资源证据，但默认公海只展示 `done + has_lead_value=true`。
- **页面边界**：普通线索列表和导出默认只读清洗完成且有价值的数据；`pending/fail` 只能经显式管理员诊断入口查看。资源池必须显式要求 `llm_status='done'`、`has_lead_value=false` 和有效活动阶段，不能靠放开全部质量状态实现。
- **迁移裁决**：正式与采集库当前只发布到 020，021～025 是尚未获准上线的休眠地基。不得为修改 020 触发器而原地改历史迁移，也不得越序单独执行 026；本批先在 sender/receiver 应用层实施门禁并保留 outbox 审计。未来切换领域事件协议时再以新迁移增加明确的 `suppressed`/tombstone 状态。
- **密钥边界**：LLM 密钥必须位于仓库和不可变 release 目录之外的 0600 文件，通过 `WXSEARCH_SECRETS_PATH` 指向容器内只读挂载。发布目录重建、代码回滚和 Web 配置均不得覆盖或遮蔽密钥；启动验收只检查是否存在和最小权限，不回显值。
- **恢复顺序**：先部署展示/同步门禁，再恢复密钥并用少量 dry-run 验证模型，最后只把未人工编辑的失败记录重新排队。模型、密钥或网络再次失败时允许积压，不允许规则草稿进入业务员视图或正式 lead 表。
- **模型预算**：当前 `deepseek-v4-flash` 会同时返回 `reasoning_content` 与结构化正文。合成验收中 2048 上限以 `finish_reason=length` 截断，4096 上限以 `stop` 完成并得到 23 字段 JSON，因此本批把输出预算固定为 4096；未来换模型必须重新做合成契约验收，不能沿用该数值或以 HTTP 200 代替完整性证明。
