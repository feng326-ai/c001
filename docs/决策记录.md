# 决策记录

> 记录"两种做法之间怎么选"的裁决，避免两个智能体各自演进出不同实现。
> 格式：结论 / 理由 / 被否方案 / 适用边界。发现新的"两种做法"时，先在这里写一条再动手。

---

## D-001 唯一权威源码包为 `wxsearch/`，部署包是构建产物

- **日期**：2026-08-18
- **结论**：`wxsearch/` 是唯一权威源码。推给 VM 的 `wxg01` 精简包属**构建产物**，改动必须回改 `wxsearch/`，不允许在部署包里长期演进。
- **理由**：本仓库曾累积 **6 份驱动副本**（34.4K / 34.4K / 42.8K / 50.7K / 53.9K / 60.9K），两个智能体各自改各自那份，导致同一个问题解决两遍、成果只有一边有。
- **被否方案**：让部署包独立演进、定期"对齐"——实测对不齐，人工比对成本高且易漏。
- **适用边界**：若将来采集端与服务端依赖冲突到无法共包，再考虑拆成两个包，但那时也必须**各有唯一来源**。

## D-002 采集端与服务端共用 `wxsearch/`，靠 config 开关区分行为

- **日期**：2026-08-18
- **结论**：不拆包。采集端与服务端共用同一个 `wxsearch/`，用 `distributed.enabled` / `unattended.enabled` 等配置开关切换行为。
- **理由**：`models.py`、`logger.py`、`unattended.py`、`config.py` 双方完全一致，拆包会立刻产生同步负担。采集端只是**不 import** 服务端模块（`tasks.py`、`db_connector.py` 等），不装 `psycopg2` 即可。
- **注意**：`db.py`（SQLite，采集端）与 `db_connector.py`（PG，服务端）是**两个不同用途的模块，不是新旧关系**，别互相覆盖。同理 `smart_dedup_store.py` 服务端版（38K）远大于采集端版（14K），属正常。

## D-003 采集循环统一用 `unattended.py`，废弃自写的本地循环

- **日期**：2026-08-18
- **结论**：无人值守循环统一走 `wxsearch/unattended.py`（领词 → 采集 → 上报 → 心跳 → 休眠）。Ubuntu 侧智能体自写的 `run_loop.py`（本地模式）仅保留为**离线技术验证工具**，不用于生产。
- **理由**：`run_loop.py` 不含 Celery/Redis/心跳调用，关键词写死在本地 config，导致：数据落 guest 本地 SQLite 不进 PG、设备监控看不到节点、无法参与服务端派词与租约调度。实测 4 台 VM 采了约 348 条全部滞留本地。
- **被否方案**：给 `run_loop.py` 补心跳/上报——等于把 `unattended.py` 重写一遍，两套并存必然再分叉。
- **适用边界**：需要脱网单机验证驱动时可用 `run_loop.py`，但**不得开启自启、不得长期运行**。

## D-004 设备状态唯一来源是 `devices` 表，废弃文件式心跳

- **日期**：2026-08-18
- **结论**：节点在线状态、当前采词、采集量一律以服务端 `devices` 表（经 `heartbeat_device_task` 上报）为准，看板 `/admin/devices` 是唯一视图。Ubuntu 侧的 `guest/inbox/hb-*.txt` 文件心跳降级为**调试辅助**。
- **理由**：两套心跳并存导致"一边看文件、一边看看板"，对同一台机器的状态判断不一致。
- **被否方案**：把文件心跳汇总进看板——多一层转换，且文件通道无鉴权、易被误改。

## D-005 远程控制采用"guest 常驻 agent + 拉模式"，但必须收口为命令白名单

- **日期**：2026-08-18
- **结论**：采纳 Ubuntu 侧已实现的思路——guest 内常驻 agent **主动轮询**宿主取命令并回传结果（拉模式）。但**必须**改为：命令白名单（枚举动作）+ 共享密钥鉴权 + 审计日志。
- **理由**：拉模式天然穿透 NAT、无需给 VM 开入站端口、IP 变化也不影响；键盘模拟只适合首次拉起 agent（弹窗抢焦点会吃掉按键）。
- **被否方案（安全红线）**：原实现用 `Invoke-Expression` 直接执行下发内容，且通道为**明文 HTTP 无鉴权**——等于任何能访问该端口的进程都能在 4 台 VM 上任意执行代码。**不得留存到长期运行。**
- **分层认知**：① 软开关（暂停/恢复采集，复用每轮配置拉取，最省）② 进程级（agent 拉起/重启采集进程）③ 平台级（`virsh` 控制 VM 电源，唯一能救卡死/关机的手段）。

## D-006 筛选未生效时"宁缺毋滥"，不退化为采集全部

- **日期**：2026-08-18
- **结论**：筛选项（排序/类型/时间）经面包屑回读校验，任一项未确认生效即抛 `FilterNotApplied`，重开搜索重试；重试耗尽则**跳过该关键词**，下轮再来。
- **理由**：旧实现在筛选失败时"按默认结果采集"，等于把「全部」视图的视频/无关内容混入线索库，污染下游 AI 研判与去重。数据正确性优先于采集量。
- **被否方案**：失败即采默认结果（原实现）；或直接抛 `DriverError` 终止（过于激进，瞬时 UIA 抖动很常见，应可重试）。
- **实现要点**：`FilterNotApplied` **不是** `DriverError` 子类——`_open_and_filter` 中 `except DriverError: raise` 会直接上抛，而 `except Exception` 才会重试。

## D-007 逐台差异参数一律走 `config.json`，不写死在代码

- **日期**：2026-08-18
- **结论**：每台 VM 可能不同的参数（搜索框/聊天图标坐标等）全部作为 `Selectors` 字段暴露，通过 `config.json` 覆盖。
- **理由**：原先 4 个坐标用 `getattr(self.sel, "...", 默认值)` 读取，但 `Selectors` dataclass 里**没有这些字段**——一旦写进 `config.json` 就 `TypeError` 崩溃，等于只能改代码来标定。5 台机各改一次代码不可维护。
- **落地**：`searchbox_chat_icon_x/y`、`searchbox_entry_x/y` 已补入 `Selectors` 与 `_DEFAULTS`，缺省为 win10-0 实测值（40/120/167/65），不填则行为不变（向后兼容）。

## D-008 SimHash 近似去重阈值定为 1.0

- **日期**：2026-08（沿用）
- **结论**：`dedup.simhash_threshold = 1.0`，即仅汉明距离 0（指纹完全相同）判近似重复。
- **理由**：目标语料多为同质公文（征集/评选通知），SimHash 区分度不足。阈值 0.9（dist≤6）大量误杀语义无关文章；0.95（dist≤3）实测 194 篇语料误杀率仍约 12%，且距离 4~6 段不携带有效信号。真转载实测均落在距离 0。
- **兜底**：规范化后完全一致的转载由第②层 SHA256 精确哈希捕获；部分改写只能依靠 SimHash/活动聚合等近似规则，放宽标题阈值也不能稳定解决，故收紧标题门槛。

## D-009 服务端连接池按“异常必归还 + 每进程限额”治理

- **日期**：2026-08-22
- **结论**：`DatabaseConnector` 使用线程安全连接池；查询和写入无论成功或失败都在 `finally` 归还连接，断开的连接丢弃；默认每进程最多 8 条连接，可通过 `DB_POOL_MAX` 调整。
- **理由**：本地生产采集平面（历史上曾称“测试环境”）出现数据库仍健康而 worker 池耗尽，根因是异常路径遗漏 `putconn`。Celery 的 4 个 prefork 子进程会放大泄漏；仅提高 PostgreSQL `max_connections` 只能延后故障，不能消除根因。
- **被否方案**：继续使用非线程安全的 `SimpleConnectionPool` 并把最大连接数调大；或依赖每个调用点手工 `close()`。前者会掩盖泄漏，后者容易遗漏且已在生产流程中失效。
- **适用边界**：批处理或连接数确有需求时，优先通过 `DB_POOL_MAX` 按实例规模调参，并确保总和低于 PostgreSQL `max_connections`；不得绕开连接池直接长持有连接。

## D-010 生产容器统一由 Compose 接管，数据卷名称显式配置

- **日期**：2026-08-22
- **结论**：数据库、Redis、worker、beat 和 backend 必须由同一份 `docker-compose.prod.yml` 管理；已有服务器通过 `PGDATA_VOLUME` / `REDISDATA_VOLUME` 指向原数据卷，新部署使用稳定的默认卷名。
- **理由**：手工 `docker run` 的应用容器没有 Compose 标签，也未注入 `DATABASE_URL` / `REDIS_URL`，导致容器表面运行、实际持续认证失败。直接执行 Compose 又会创建新命名卷，让原数据看似“丢失”。显式卷名兼顾可重复部署和旧数据保留。
- **被否方案**：继续手工补 `docker run -e ...`；或先复制整个 Docker volume 再切换。前者会再次配置漂移，后者增加停机和数据复制风险。
- **适用边界**：切换前必须先 `pg_dump`，核对实际挂载卷和表行数；只移除容器，不删除原 volume。真实口令只留在服务器 `.env`。

## D-011 本地生产采集平面的外部入口统一使用 SSH 反向隧道

- **日期**：2026-08-22
- **结论**：本地生产采集平面以 systemd 管理的 `leads-tunnel.service` 为唯一外部入口，云端 7080 转发到本地 Backend 8000；本机 Nginx 不属于默认运行栈。
- **理由**：现网已经由 SSH 隧道完成跨局域网访问。本机再启 Nginx 不参与云端访问链路，只增加端口冲突、配置漂移和错误健康判断。
- **被否方案**：把 `wxsearch_nginx` 纳入默认 `docker compose up`；或同时维护 SSH 隧道与本机 Nginx 两条等价入口。
- **适用边界**：Nginx 配置仅作为显式 profile 的备用方案。若以后正式切换入口，必须先更新本记录和部署文档，再停用隧道。

## D-012 服务端凭据以服务器 `.env` 为唯一运行配置源

- **日期**：2026-08-22
- **结论**：Compose 只引用 `POSTGRES_PASSWORD`、`REDIS_PASSWORD` 等环境变量，真实值只保存在服务器未跟踪的 `.env`；采集节点配置由同一来源生成，禁止在 Compose、脚本或部署包中硬编码口令。
- **理由**：本地生产采集平面的 Compose 曾硬编码一套 Redis 口令，而服务器 `.env` 保存另一套。一次无关的容器重建使 Redis 改用硬编码值，四台 Windows 节点同时认证失败、采集全面中断。配置文件存在不代表它已被运行栈使用。
- **迁移规则**：先从当前正常运行容器核对实际端点并把 `.env` 对齐，再执行 `docker compose config` 验证；不得为了“验证配置”重建数据库或 Redis。迁移后以 `.env` + Compose 渲染结果为准，不再从容器反向抄写凭据。
- **安全边界**：`.env` 权限设为 `0600` 且不得提交。任何历史明文凭据脚本必须退出长期运维链路；日志和文档只记录变量名，不记录真实值。

## D-013 本地生产采集数据通过幂等事件同步到正式业务库

- **日期**：2026-08-22
- **结论**：本地继续承担采集、去重和 AI 加工；正式库是公海/OA/CRM 唯一业务源。两者通过事务发件箱和带 HMAC 的 HTTPS 批量接口同步，不共享数据库、不把 Redis/PostgreSQL 暴露为公网数据通道。
- **字段所有权**：本地拥有原文与 AI 建议层；正式环境独占分配、跟进、成交、个人状态、人工标签与人工覆盖层。现有 `updated_by_human=true` 只是过渡期整行保护，目标模型必须按字段保存 provenance/人工覆盖，允许自动侧补充未被人工锁定的字段而不能覆盖人工决定。
- **幂等键**：文章使用 UUID/内容指纹，业务活动使用稳定 `event_edition_id`，传输消息使用全局 `message_id`（旧 v1 字段 `event_id` 仅作兼容别名）；不得假设本地和正式的自增 ID 长期一致。
- **被否方案**：定时整库覆盖会删除/回退业务员状态；直接连接正式 PostgreSQL 会扩大攻击面并耦合两端 schema；仅按最大自增 ID 拷贝会漏掉 LLM 后更新和重试记录。
- **过渡边界**：首次上线可在完整备份和影子库演练后做固定快照导入；该方式只用于初始化，不作为长期同步机制。

## D-014 正式宿主机只公开 Nginx，应用与数据端口绑定本机

- **日期**：2026-08-22
- **结论**：正式环境公网只保留 80/443（Nginx）和必要的 SSH；Backend 8000、PostgreSQL 5432、Redis 6379 的 Compose 端口绑定 `127.0.0.1`。容器间仍通过内部网络互通。
- **理由**：正式宿主机曾在 `0.0.0.0` 监听 5432/6379/8000。即使云安全组可能拦截，也不应把数据服务安全依赖于单层外围规则；Redis/PG 不是采集同步入口。
- **适用边界**：本地生产采集平面的 Redis 需要供 libvirt NAT 网段内 VM 使用，不能照搬本条绑定 localhost；应通过宿主防火墙只允许 VM 网段。正式如新增受控内网消费者，应走私网/隧道并显式登记，不恢复公网监听。

## D-015 LLM 只在本地生产采集平面清洗，正式环境只接收清洗结果

- **日期**：2026-08-22
- **结论**：本地生产采集平面负责采集、规则处理和 LLM 清洗，正式环境设置 `LLM_CLEAN_ENABLED=false` 作为硬开关，只接收本地端同步后的 AI 字段。显式环境变量优先于共享 `rule_config.json`。
- **理由**：两端使用同一份规则配置时，若规则文件优先，`clean_enabled=true` 会覆盖正式环境的关闭配置，造成同一批线索被两台服务器重复调用模型，增加费用且可能产生不一致结果。
- **被否方案**：允许两端各自清洗并依赖 `llm_status=done` 去重。两库写入和同步存在时间差，状态不能构成跨库互斥锁，也无法保证模型输出一致。
- **适用边界**：若未来迁移 LLM 执行节点，应先切断旧节点并确认队列清空，再在新节点开启；任何时刻只能有一个环境拥有清洗职责。

## D-016 采用渐进式重构，不重写整套系统

- **日期**：2026-08-22
- **结论**：保留已经运行的微信采集、Celery/Redis、PostgreSQL、去重、LLM 和事务发件箱；在同一仓库内新增目标领域模型和模块，以“加表与回填 → 新旧兼容 → 按模块切流 → 旧写入退役”的方式演进。不得另建 `v2` 平行仓库或复制整套源码。
- **理由**：现有采集链路承载真实数据且 UIA 适配成本高，整体重写会重新引入已解决的故障；另一方面，继续把多租户、审核和 CRM 字段堆进 `qualified_leads` 会让职责继续失控。
- **被否方案**：一次停机替换全部系统；或维持现有表结构不断追加字段和页面判断。
- **验收边界**：每一步都必须可回滚，旧页面在兼容期继续运行；每个字段任一时刻只有一个权威写入方。

## D-017 共享情报中台服务三个相互竞争的独立公司租户

- **日期**：2026-08-22
- **结论**：三个现有业务团队按三个独立公司租户建模。文章、公开活动届次、公开主办方和通用 AI 结果共享；审核结论、私有联系人、商机、跟进、报价、成交和绩效按 `tenant_id` 严格隔离。同一共享 `event_edition` 通过门槛并授权后可为每个租户各生成一条独立审核任务和商机，公司之间允许竞争，公司内部同一 `event_edition` 只能有一个有效商机。
- **可见策略**：当前公共资源默认 `shared_competition`；同时预留 `tenant_private`、`selected_tenants` 和未来 `exclusive`，改变商业模式时只切策略，不重构核心表。
- **理由**：共享上游可避免三次采集、去重和 LLM 成本；租户业务数据隔离符合三家公司独立经营事实。将三个公司继续当作普通 team 会导致 CRM 泄露和权限边界错误。
- **安全边界**：跨租户隔离必须由服务端查询作用域和 PostgreSQL RLS 双层保障，并有自动化越权测试；平台管理员读取租户 CRM 明细需独立授权和审计。

## D-018 全网采集采用连接器架构，实时与近三年历史回填分流

- **日期**：2026-08-22
- **结论**：微信搜一搜是当前主渠道，但所有信源实现统一 Connector/标准文档契约；内部节点通过受控任务通道运行，外部采集器和第三方数据只通过带鉴权、签名和幂等键的 HTTPS ingestion API 接入。实时商机使用高优先级队列，近三年历史使用低优先级、可断点恢复的 backfill 队列。
- **处理规则**：所有渠道共用规范化、文档去重、活动聚合、主办方识别、AI 研判和租户分发；多来源只增强同一活动证据，不生成重复销售线索。历史结果进入主办方/活动系列/届次库，不直接污染今日公海。
- **被否方案**：每个渠道各建一套库和清洗逻辑；外部节点长期直连 Redis/PostgreSQL；把历史文章批量当成当前线索。
- **适用边界**：第一期用微信 PC 和现有搜狗连接器验证契约，再接一类官方网页信源；不提前建设与销售无关的通用情感舆情大屏。

## D-019 以“活动事件—租户审核—商机”替代文章即线索

- **日期**：2026-08-22
- **结论**：原始文章只是来源证据；跨文章聚合后的活动/活动届次才是共享业务对象。每个租户对活动独立审核，审核通过后创建租户商机；主办方、联系人证据、活动系列、届次、审核、商机和跟进分别建模，不再让 `qualified_leads` 同时承担全部职责。
- **理由**：同一活动可能有公众号、官网和新闻多篇转载；按文章生成销售线索会重复计数和重复联系。近三年主办方举办次数也必须按独立届次而不是文章数计算。
- **迁移边界**：`qualified_leads` 和现有 `organizers` 在兼容期保留，通过回填和兼容视图逐步退出核心写入，不直接删除存量。

## D-020 多智能体并行以文件所有权和串行集成为前提

- **日期**：2026-08-22
- **结论**：集成负责人统一拆分任务、冻结公共契约、分配文件所有权、审查和发布。共享工作区 sub-agent 只改授权文件且不提交；独立窗口使用独立 `codex/*` 分支。数据库迁移编号、公共 API/schema、状态机和生产部署必须串行协调。
- **理由**：并行的收益来自互不重叠的可独立工作；若多个窗口同时修改核心文件、迁移或契约，合并冲突和语义分叉会抵消全部速度收益。
- **质量边界**：任何并行成果只有通过测试、迁移、租户隔离、安全、契约和回滚门禁后才能由集成负责人合入 `main`；详细流程见 `docs/多智能体协作与交付规范.md`。
