# 评选业务线索智能系统：总体架构与演进路线

> 版本：2026-08-22。本文是采集、研判、正式公海及未来 OA/CRM 的统一演进基线。

## 1. 业务目标

系统不以“采到多少文章”为最终目标，而以“单位成本产生多少可联系、可转化的评选业务机会”为目标。完整漏斗是：

`全网信号 → 原始文章 → 去重事件 → 有效线索 → 优先线索 → 联系 → 有效商机 → 成交/失单 → 反馈模型与关键词`

核心北极星指标：

- 每周有效商机数、有效商机率、成交线索数；
- 从首次发布到进入正式公海的 P50/P95 延迟；
- 每条有效商机的采集成本、模型成本和人工处理时长；
- P0/P1 精确率、漏判率，以及业务员“首联有价值”反馈率。

## 2. 目标运行架构

### 2.1 本地采集与加工平面

- 四台 Windows KVM 节点只负责驱动 PC 微信搜一搜并回传原始结果；节点不直连 PostgreSQL。
- 本地 Ubuntu 的 Redis/Celery 接收采集任务，PostgreSQL 保存原始文章、去重结果、规则评分和 LLM 清洗结果。
- 本地环境是采集与算法试验场，不再作为业务员工作的权威公海。
- UIA 节点保持可替换、可观测；任何一台 VM 故障不得阻断另外三台和正式公海。

### 2.2 正式业务平面

- 云端 PostgreSQL 是线索公海、主办方库、用户状态和未来 OA/CRM 的唯一业务事实源。
- FastAPI 只通过内部网络访问 PostgreSQL/Redis；数据库和 Redis 不向公网作为同步入口开放。
- 正式环境保存账号、团队、分配、跟进、成交/失单、个人备注和人工反馈；这些字段只能由正式业务流程修改。

### 2.3 采集到正式环境的同步网关

采用“事务发件箱 + HTTPS 幂等接收”模型：

1. 本地文章/线索事务提交时写入 `production_sync_outbox`，事件包含全局事件 ID、实体键、版本和源字段快照。
2. 本地同步 worker 分批发送到正式 `/api/v1/internal/sync/batch`，失败指数退避，超过阈值进入死信但不丢记录。
3. 正式接收端使用 HTTPS、HMAC 签名、时间戳和重放保护；按事件 ID 幂等落库。
4. 文章以 `uuid` 为主同步键、`content_hash` 为辅助键；线索以文章 UUID/归一事件键定位，禁止依赖两库自增 ID 永久相同。
5. 正式端逐事件返回已写入/已存在/冲突/拒绝，发送端只有收到确认才标记完成。

首期目标：同步 P95 延迟小于 2 分钟，24 小时事件成功率大于 99.9%，积压和死信可在管理页告警。

## 3. 字段所有权契约

| 数据域 | 本地采集侧可写 | 正式业务侧可写 | 同步规则 |
|---|---|---|---|
| 原文/来源 | 标题、正文、URL、公众号、发布时间、渠道、关键词、内容指纹 | 不直接修改 | 按文章 UUID 幂等补充，以非空和较完整版本为优先 |
| AI 研判 | 意图、分数、优先级、活动信息、主办方抽取、模型版本 | 人工修订 | 正式行已 `updated_by_human=true` 时不得覆盖人工字段 |
| 公海流转 | 不写 | 状态、分配人、跟进期限、最近联系、转化备注 | 永不从本地覆盖 |
| 个人状态 | 不持续同步 | `lead_user_state`、个人备注、收藏、隐藏、人工标签 | 正式环境独占 |
| 反馈/CRM | 只读取聚合后的训练信号 | 有效/无效、成交/失单及原因、金额、阶段 | 正式产生，脱敏后回流模型与关键词优化 |
| 主办方档案 | 自动抽取和保守聚合 | 人工合并、修订、CRM 主体关联 | 人工编辑过的档案受保护，仅追加新证据 |

## 4. 智能化闭环

### 4.1 两级判断降低成本

- 一级规则：时间、活动阶段、征集/报名/投票信号、明确结束信号、广告/教程/回顾等硬负例；用于高吞吐预筛。
- 二级模型：只处理规则不确定或高潜记录，抽取活动名称、主办方、联系人、截止时间、举办层级、是否需要评选系统。
- 相同事件跨公众号聚合后再评分，避免“转载次数多”被误当成“商机更优”。

### 4.2 线索优先级应预测业务价值

目标分数由以下维度组成，并保留版本与明细：

- 需求意图：正在征集/筹备/报名高于已经投票或已结束；
- 时间窗口：距截止日、预计启动日、首次发现时间；
- 主体质量：政府、协会、学校、企业规模和历史举办次数；
- 可联系性：电话、邮箱、微信、报名入口、联系人完整度；
- 竞争与可服务性：是否已有投票平台、是否疑似竞品、是否需要系统搭建；
- 历史转化：同类关键词、地区、主办方、活动类别的有效/成交率。

模型优化使用正式 CRM 结果，而不是仅用 AI 自己生成的标签训练自己。

### 4.3 关键词自动运营

- 每个“关键词 × 渠道”记录采集成功率、文章数、去重后事件数、有效线索数、P0/P1 数和最终转化。
- 高转化且新鲜的词提高频率；低产/低转化词降频或进入观察；探索流量固定保留，避免只采历史热门词。
- UIA 失败、无结果和真正低价值必须分开统计，不能把采集故障误判为关键词无价值。

## 5. 可观测性与安全底线

- 采集：每 VM 心跳、当前关键词、最近成功入库、筛选失败率、单词耗时、微信弹窗/UIA 错误类别。
- 加工：Celery 队列深度、任务成功率、去重率、规则命中率、LLM 成功率/耗时/费用。
- 同步：最后成功时间、同步延迟、待发送数、重试数、死信数、正式端拒绝原因。
- 业务：新线索、首联时长、有效率、阶段转化率、失单原因和负责人负载。
- Redis/PostgreSQL 不直接暴露公网；凭据只在服务器 `0600` 的环境文件中；VM 控制 agent 必须使用动作白名单、鉴权和审计。
- 生产每日备份并定期做恢复演练；所有 schema 变更先在生产快照影子库演练。

## 6. 分阶段路线

### P0：先做到稳定、可交付（1–2 周）

- 上线事务发件箱与正式幂等接收 API，替代人工数据库搬运；
- 统一 Compose/.env 密钥来源，完成采集节点配置生成和轮换；
- 将无鉴权任意命令 agent 替换为白名单 agent；
- 采集/加工/同步三段健康检查与告警，明确 15 分钟无新数据告警；
- 建立生产备份、恢复演练和发布回滚清单。

验收：四台节点任一掉线不影响其余节点；新线索 2 分钟内进入正式公海；同步重试不重复；生产业务字段不被覆盖。

### P1：提高有效线索率（2–4 周）

- 建立 200–500 条业务员金标集，统一“有效、优质、无效、已结束、竞品”口径；
- 重构评分为可解释维度，补活动阶段/截止时间/联系人完整度；
- 事件级聚合与主办方历史画像，识别周期活动和提前唤醒机会；
- 修复微信渠道当前高失败率，按错误类型做自动恢复而非盲目重试。

验收：P0/P1 精确率、有效商机率和首联时长相对基线持续改善。

### P2：接入 OA/CRM 形成学习闭环（4–8 周）

- 统一客户/主办方/活动/联系人/商机模型；
- 线索分配、跟进 SLA、阶段、成交金额和失单原因结构化；
- CRM 结果每日回流关键词价值和排序模型，支持版本对照与灰度发布；
- 重复主体、重复活动和跨渠道证据在业务界面合并展示。

### P3：规模化与降本（持续）

- 采集渠道插件化，增加公开网页、公众号外渠道和客户指定信源；
- 用单位有效商机成本动态分配 VM、关键词频率和 LLM 预算；
- 热点与常规采集分层，按业务季节性自动扩缩；
- 建立周度漏斗复盘：数据问题、模型问题、销售执行问题分别归因。

## 7. 2026-08-22 当前基线

- 四台微信采集 VM 已恢复在线并成功回传新文章；
- 首次同步后正式环境已拥有 13,184 篇文章、11,592 条线索和完整账号/个人状态；
- 当前人工有效性反馈极少，无法可靠训练转化模型，P1 金标机制优先级很高；
- 微信搜一搜近期任务失败率偏高，需按 UIA、筛选、微信状态、网络/认证拆因治理；
- 正式业务面已成为线索交付入口，后续禁止把测试库整库覆盖到生产。
