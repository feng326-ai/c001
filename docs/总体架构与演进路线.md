# 评选业务市场情报与商机系统：总体架构与演进路线

> 版本：2026-08-22。本文是采集、数据加工、主办方情报、资源审核、电销 OA、CRM 与智能反馈的权威目标架构。具体技术取舍以 `docs/决策记录.md` 为准；尚未实施的业务需求以 `docs/需求登记.md` 为准。

## 1. 系统定位与业务目标

系统不以“采到多少文章”为最终目标，而以“更早发现评选业务需求，用更低综合成本产生更多有效商机与成交”为目标。

完整业务链路为：

```text
全网信号
  → 原始文档与来源证据
  → 独立活动/活动届次
  → 主办方与联系人情报
  → AI 候选资源
  → 租户资源审核
  → 电销 OA 待办与首次联系
  → CRM 商机、报价、成交/失单
  → 周期活动唤醒与复购
  → 反馈采集、关键词、评分和模型
```

北极星指标是“每周新增有效商机数”和“每条有效商机的综合成本”。辅助指标包括：

- 从信号首次发布到进入租户审核队列的 P50/P95 延迟；
- 审核通过率、销售接受率、首联及时率、有效商机率、报价率与成交率；
- 每个“监测主题 × 渠道”的独立活动率、有效商机率和成交贡献；
- 每条有效商机的采集、模型和人工审核成本；
- 周期活动唤醒命中率、复购率与主办方长期价值。

文章数量、P0/P1 数量和模型分数只作为过程指标，不能替代业务结果。

## 2. 已确认的业务边界

### 2.1 三个相互竞争的独立公司

当前业务面由三个独立公司使用，每家公司有：

- 1 名资源审核员；
- 8 名电销业务员；
- 独立的审核结论、联系人补充、商机、跟进、报价、成交、绩效和管理视图。

三个公司可以同时跟进同一条公共资源并相互竞争，但不能看到彼此的审核结论和 CRM 数据。公司内部同一 `event_edition` 只能有一个进行中的有效商机，避免 8 名业务员重复联系。

因此系统采用“共享情报中台 + 多租户业务平台”，不能继续把三个公司仅建模为普通团队。

### 2.2 微信为主、全网能力预留

根据当前市场判断，微信搜一搜贡献约 90% 的可发现线索，是近期采集可靠性和覆盖率建设的第一优先级。这是当前资源配置依据，不是写死的长期渠道配额。

底层从第一天按统一连接器和标准文档协议建设，预留手机微信、搜狗微信、搜索引擎、政府/协会/学校/企业官网、采购与招投标、新闻媒体、公开内容平台、客户私有信源和第三方数据服务等入口。是否扩大某个渠道，应由最终有效商机与成交贡献决定，而不是文章数量决定。

### 2.3 实时商机与近三年历史情报并行

系统同时运行两个目的不同的引擎：

- **实时商机引擎**：发现正在筹备、征集、报名或尚未确定投票平台的活动，优先进入资源审核和销售流程；
- **历史主办方引擎**：采集近三年已经举办的评选活动，完善主办方、活动系列、每届详情、举办次数、公开联系方式、历史平台和周期规律，用于预测下一届并提前唤醒。

历史文章不直接进入今日销售公海，也不计入实时新增指标。历史价值最终体现在主办方画像、周期预测和未来商机上。

                                   │ 统一连接器/采集网关

目标形态仍采用 Python、FastAPI、PostgreSQL、Redis、Celery 和 Docker Compose。当前规模不引入 Kafka、Kubernetes、分布式数据库或 Elasticsearch；中文检索优先使用 PostgreSQL 规范化字段、组合索引与 `pg_trgm`。

## 4. 运行平面与事实来源

### 4.1 本地采集与智能加工平面

- Windows VM 驱动微信搜一搜等桌面渠道，节点不直连 PostgreSQL；当前内部节点继续按任务名经 Celery/Redis 领词、上报与心跳。
- 本地 Ubuntu 负责采集调度、文档入库、去重、活动加工、规则和 LLM 研判，并通过事务发件箱向正式环境同步。
- 虽然现有运维中常称其为“测试服务器”，它实际上承载正式采集与智能加工职责，不能随意清库、试验破坏性迁移或与开发环境混用。
- 需要另建真正的开发/测试环境，使用模拟数据或脱敏快照验证迁移、模型和接口。
- LLM 在任一时刻只能由一个加工环境执行；当前由本地侧执行，正式环境关闭清洗并只接收结果。

### 4.2 云端正式业务平面

- 云端 PostgreSQL 是租户审核、OA/CRM、人工修订、跟进、报价、成交/失单和个人状态的唯一业务事实源。
- 正式业务字段不得从本地整库覆盖；正式数据库也不反向成为采集节点的直接写入目标。
- FastAPI 通过内部网络访问 PostgreSQL/Redis；正式公网入口只暴露反向代理和必要的 SSH，数据端口不作为同步或采集入口开放。

### 4.3 本地到正式的事件同步

现网采用“事务发件箱 + HTTPS 幂等接收”模型：

1. 本地文章/线索事务提交时写入 `production_sync_outbox`；
2. 同步 worker 分批发送到正式 `/api/v1/internal/sync/batch`，失败指数退避并保留死信；
3. 正式接收端通过 HMAC、时间戳和重放保护鉴权，按全局事件 ID 幂等落库；
4. 文章使用 UUID/内容指纹，业务实体使用稳定实体键，禁止依赖两库自增 ID 相同；
5. 发送端收到逐事件确认后才标记完成。

目标保持同步 P95 小于 2 分钟、24 小时事件成功率大于 99.9%，积压、重试和死信必须可观测。

## 5. 全网采集与连接器契约

### 5.1 统一连接器

每个采集渠道只负责发现和获取原始信息，实现统一能力边界：

```text
health_check()   渠道健康检查
search()         按监测主题或关键词检索
fetch_detail()   获取正文与详情
normalize()      转为标准文档
checkpoint()     保存增量游标/历史回填断点
report_result()  上报成功、失败、数量和错误分类
capabilities()   声明渠道能力与限制
```

渠道不得自行维护另一套去重、AI、线索库或 CRM。所有结果进入统一的标准化、去重、活动聚合、研判和租户分发链路。

### 5.2 标准文档

标准文档至少包含：

- 来源渠道、渠道内唯一键、规范 URL、标题、正文、摘要和发布主体；
- 发布时间、采集时间、命中监测主题/关键词、媒体类型和地区；
- 原始内容指纹、原始载荷或其审计引用；
- `collection_mode`、受信任务租约/连接器身份和协议版本；资源作用域与授权租户由服务端从这些受信上下文推导，不能相信采集 payload 任意声明的 `tenant_id`；
- 渠道特有信息放入版本化的 `source_metadata`，避免为每个新渠道修改公共主表。

### 5.3 内部与外部接入边界

- 现有局域网微信 PC 节点可继续使用受控 Celery 任务通道，优先保证可靠运行；
- 新的外部采集器、手机采集器和第三方数据供应商，目标上通过版本化 HTTPS ingestion API 接入，使用设备/供应商令牌、请求签名、幂等键、批量提交、限流和审计；
- 外部采集器不得长期直连 PostgreSQL，新增外部节点不应默认获得 Redis 任意任务权限。

### 5.4 实时与历史队列

| 维度 | 实时商机 | 历史回填 |
|---|---|---|
| `collection_mode` | `realtime_signal` | `historical_backfill` |
| 目标 | 当前可联系机会 | 主办方画像与下一届预测 |
| 队列 | 高优先级 | 低优先级、限并发 |
| 时间范围 | 最新增量 | 近三年，按年/月/主题切片 |
| 中断处理 | 快速重试与告警 | 游标断点续跑，不从头采集 |
| 业务去向 | 租户审核队列 | 主办方/系列/届次库，命中唤醒窗口后再生成任务 |
| 指标 | 实时延迟、商机率 | 覆盖率、聚合准确率、周期预测价值 |

实时任务始终优先；历史任务使用独立配额和 LLM 预算，不能拖慢当前商机发现。

## 6. 共享情报领域模型

原始文章只是证据，活动届次才是共享业务对象。目标模型包括：

| 实体 | 职责 |
|---|---|
| `source_documents` | 全渠道原始文档、内容指纹和采集元数据 |
| `event_editions` | 某年/某届的独立活动，避免转载被算成多条商机 |
| `event_sources` | 活动与多来源证据的关联 |
| `event_series` | 跨年度活动系列、频率、通常月份和周期预测 |
| `organizations` | 主办方标准主体、别名、地区、行业和公开属性 |
| `organization_event_roles` | 主办、承办、协办、指导等角色及证据，只有主办角色计入举办次数 |
| `public_contacts` / `contact_evidence` | 公开联系人、联系方式、最近发现/验证时间和原文证据 |
| `ai_assessments` | 模型、Prompt、规则版本、输入哈希、输出、成本、耗时和错误 |

活动聚合遵循：同一届活动的公众号文章、官网公告、新闻转载、投票入口和结果公示只形成一个活动届次，多来源用于补全证据和提升置信度，不生成重复销售线索。

现有 `qualified_leads` 和 `organizers` 在兼容期保留，通过“新表回填 → 双读校验 → 新写入切换 → 兼容视图”逐步退出核心职责，不直接删除存量。

## 7. 主办方库与近三年历史情报

### 7.1 主办方画像

主办方库应能回答：

- 近三年真实举办了多少个独立活动/届次，而不是出现了多少篇文章；
- 有哪些活动系列、是否连续举办、通常在几月启动；
- 历届征集、报名、投票和结果公布时间，活动规模和线上投票倾向；
- 使用过哪些平台或竞品；
- 有哪些公开联系人、联系方式来自哪篇公告、最近何时出现或验证；
- 下一届预计何时启动、建议何时首次联系、预测置信度如何。

公开联系人证据属于共享情报；租户业务员补充的私人联系人、通话内容和内部备注属于该租户 CRM，不能回写为跨租户可见信息。

### 7.2 周期预测与销售唤醒

周期预测使用届次、年度/季度等周期词、历年启动月份、阶段间隔、主办方规律和同类活动季节性。只有同时满足以下条件的历史对象才进入未来唤醒：

- 仍具有复办可能和线上评选需求；
- 主办方价值达到租户或平台配置门槛；
- 预测时间进入提前联系窗口；
- 预测有可解释证据和置信度。

进入唤醒窗口后，共享活动可分别为三个租户生成独立审核任务，各租户自行决定是否跟进。

## 8. 多租户资源分发与数据隔离

### 8.1 共享与私有边界

平台共享：

- 原始公开文档、独立活动、活动系列和主办方公开事实；
- 公开联系人及其来源证据；
- 通用规则、AI 抽取与全局资源价值判断；
- 公开竞品信息和聚合后的渠道效果。

租户私有：

- 审核结论、修正意见和内部备注；
- 私有关键词、私有信源和私有联系人；
- 负责人、联系记录、客户意向、跟进计划；
- 报价、成交金额、失单原因、绩效和自定义标签。

所有租户业务表必须带 `tenant_id`，服务端查询作用域和 PostgreSQL RLS 双层隔离，并以自动化越权测试验证。平台管理员读取租户 CRM 明细需要独立授权与审计，不能因“超级管理员”身份默认获得全部内容。

### 8.2 可见策略

| 策略 | 含义 |
|---|---|
| `shared_competition` | 当前默认；三个公司分别收到资源、独立审核和跟进，彼此不可见 |
| `tenant_private` | 只对产生私有主题/信源的一个租户可见 |
| `selected_tenants` | 只对指定租户集合开放 |
| `exclusive` | 未来支持；资源只授权一个租户 |

可见策略属于资源分发关系，不复制原始正文。未来商业模式变化应切换策略，不重构共享活动和 CRM 核心表。

策略先生成带审计历史的 `tenant_resource_grant`，授权成立后才创建稳定唯一的租户审核候选。授权和候选不能混为一张状态记录；同一租户、同一活动届次的候选幂等键不包含策略版本，策略升级不得制造重复审核任务。

### 8.3 租户级唯一性

同一个共享活动允许三个租户各自生成审核任务和商机，但同一租户内必须满足：

```text
tenant_id + event_edition_id = 最多一个进行中的有效商机
```

租户内支持分配、领取、转交和管理员回收；其他业务员看到本公司已有人跟进，但不能看到其他公司的状态。

## 9. 资源审核、电销 OA 与 CRM 闭环

### 9.1 资源审核

每个租户的一名审核员只处理本租户队列。共享中台先完成基本信息整理，审核员负责公司适配判断，三个维度分开记录：

```text
review_status:   pending → in_review → completed
review_decision: qualified | rejected | needs_more_info
disposition:     sales_handoff | nurture | competitor_watch | archive
```

审核记录必须独立保存审核人、决定、去向、结构化原因、租户备注、当时 AI/规则版本和时间，不能只覆盖线索的一列状态。租户审核员可以保存本公司覆盖值，但不能直接合并/拆分共享活动、主办方或公共联系人；共享事实纠错必须提交 `data_correction_request`，由平台数据管理员审批并形成跨环境实体解析事件。系统按审核员实际处理能力生成优先队列，而不是把全部机器候选标成紧急。

### 9.2 电销 OA

审核通过后创建租户商机并进入电销协作流程：

```text
待分配/待领取
  → 今日待联系
  → 已联系/待再次联系
  → 需求确认
  → 有效商机
  → 方案/报价
  → 成交、失单或下一届唤醒
```

OA 范围包括今日待办、商机分配/领取/回收、首联 SLA、跟进提醒、周期唤醒、异常处理、站内通知、团队调度、工作量统计和操作审计。

### 9.3 CRM

CRM 以“主办方—联系人—活动—租户商机”为主线，管理租户私有的负责人、联系时间线、意向、跟进计划、报价、成交/失单、客户归属、交接和复购。

销售可按结构化原因退回资源组，例如联系人错误、主办方错误、活动重复、时间已晚、无线上需求、已有竞品或信息不完整。退回、有效、报价、成交和失单均成为质量反馈，但不能跨租户暴露业务详情。

### 9.4 反馈强度

```text
AI 候选 → 审核员确认（中等标签）
        → 销售联系验证（强标签）
        → 报价（高价值正标签）
        → 成交/明确失单原因（最高业务价值标签）
```

业务员完成正常跟进动作即产生反馈，不额外要求“训练 AI”。公共模型只消费允许聚合、脱敏的信号；租户报价、通话内容、客户名单和内部备注不跨公司共享。

## 10. 智能研判与运营闭环

### 10.1 分级处理与结果版本化

- 一级规则过滤明显广告、教程、回顾、无关内容和确定性低价值记录；
- 二级模型处理高潜或规则不确定记录，抽取活动、主办方、联系人、阶段、截止时间、线上投票和竞品证据；
- 相同“输入内容哈希 + 模型 + Prompt/规则版本”优先命中缓存，避免重复调用；
- 每次结果记录模型、Prompt、规则、输入哈希、输出、Token/费用、耗时和错误；
- 新模型先影子评测，再灰度切换；任何时刻只有一个环境承担正式清洗。

AI 输出分为全局资源价值和租户匹配判断。前者由本地生产智能加工平面执行，评估活动真实性、时效与需求可能；后者在云端正式业务平面内结合本租户行业、地区、产品能力和历史转化做私有排序，并受 RLS 保护。原始报价、联系人、通话和单租户转化明细不回传本地共享模型；未来如做跨租户学习，必须另立脱敏、最小聚合门槛、授权和审计契约。

### 10.2 人在回路

先建立 200–500 条人工金标并区分：AI 内容判断是否正确、审核员是否认可、销售是否确认需求、是否报价/成交。反馈用于生成候选规则和样例，由授权人员复核后发布，不能自动修改生产规则造成漂移。

### 10.3 监测主题与渠道运营

关键词逐步升级为版本化“监测主题”，包含核心词、需求阶段词、投票词、排除词、地区、行业、渠道和时间策略。同一主题可为不同渠道生成不同检索表达式。

每个“主题 × 渠道”追踪：

```text
采集任务 → 文档 → 独立活动 → 审核通过 → 有效商机 → 报价 → 成交
```

高价值主题和渠道升频，低产或低转化项降频，同时保留固定探索流量。采集故障、无搜索结果和业务低价值必须分开归因。

## 11. 字段所有权与集成边界

| 数据域 | 本地采集/智能侧 | 正式业务侧 | 约束 |
|---|---|---|---|
| 原始文档与来源 | 采集、标准化、补充证据 | 原则上只读 | 按稳定键幂等追加，不覆盖人工业务字段 |
| 活动/主办方自动抽取 | 保守聚合、AI 建议 | 人工合并、修订与确认 | 人工修订受保护，保留证据与审计 |
| AI 研判 | 单点执行、版本化结果 | 展示、人工反馈 | 正式不重复调用清洗模型 |
| 租户审核 | 不写 | 审核决定、原因、修正和备注 | `tenant_id` 隔离 |
| OA/CRM | 只消费脱敏反馈 | 分配、联系、阶段、报价、成交/失单 | 永不被上游同步覆盖 |
| 模型反馈 | 读取经授权的聚合信号 | 产生原始业务反馈 | 脱敏、最小化和审计后回流 |

对外系统统一通过版本化 API 或事件契约接入。旧版《对接规范》v1.0 属过渡契约；当前 v2.0 仍是 draft，手机外部接入、租户 OA/CRM 和反馈回写开工前必须冻结对应版本并提供兼容窗口。不得把外部 OA 长期绑定到内部表结构，也不得允许新采集器直连数据库。

## 12. 安全、可观测性与质量底线

### 12.1 可观测性

- 采集：节点心跳、当前主题、最近成功时间、单词耗时、筛选失败率、渠道错误分类；
- 加工：队列深度、标准化/去重/聚合率、LLM 成功率、延迟、Token 与费用；
- 历史回填：切片进度、游标、覆盖年份、失败重试和主办方聚合抽检；
- 同步：最后成功时间、P95 延迟、待发送、重试、死信和正式拒绝原因；
- 业务：审核积压、通过/退回、首联 SLA、阶段漏斗、失单原因和租户/个人负载；
- 数据质量：重复活动率、主办方误合并率、联系方式证据完整率、周期预测命中率。

### 12.2 安全与交付

- Redis/PostgreSQL 不直接暴露公网；真实凭据只在服务器 `0600` 环境文件中；
- VM 控制 agent 必须使用动作白名单、鉴权和审计，禁止任意远程命令；
- 生产每日备份并定期恢复演练，迁移同时验证空库与生产脱敏快照；
- 多租户越权、幂等同步、状态机、迁移与回滚必须有自动化测试；
- 生产发布只接受已提交、已评审且可定位到 Git SHA 的构建产物；
- 采集驱动先单节点 canary，业务迁移采用兼容窗口，禁止全量一次切换。

## 13. 渐进重构路线

系统不整体重写，也不把多租户、审核和 CRM 字段继续堆进 `qualified_leads`。采用同仓库内渐进重构：

```text
稳定现网采集与同步
  → 增加新领域表和兼容读取
  → 回填并校验存量数据
  → 跑通一条端到端最小闭环
  → 按模块切换新写入和页面
  → 旧字段转只读/兼容视图
  → 观察期后退役旧逻辑
```

任一时刻每个字段只有一个权威写入方，每阶段都必须可回滚，不建立 `v2` 平行仓库或另一份源码。

### 阶段 0：保护网与运行基座

- 固化关键 API、同步和数据库基线，补 CI、Secret 扫描、迁移校验和核心回归测试；
- 建立真正的开发/测试环境，完成备份恢复和发布回滚演练；
- 继续治理微信 UIA 错误分类、自动恢复和节点可观测性；
- 将生产部署收敛为可定位 Git SHA 的不可变构建产物。

验收：现网采集和同步不中断；生产重复 LLM 调用为 0；新变更可测试、可审计、可回滚。

### 阶段 1：新业务数据地基

- 建立租户、租户成员、角色权限、RLS 和审计；
- 建立文档—届次—来源、主办方—角色、联系人—证据、系列—届次模型；
- 建立租户资源队列、审核记录、租户商机和操作时间线；
- 从存量 `qualified_leads`/`organizers` 回填并完成数量、关联率和抽样质量校验。

验收：同一活动可生成三个互不可见的租户任务；跨租户越权测试全部通过；旧页面继续运行。

### 阶段 2：最小业务闭环

- 上线每租户独立资源审核工作台；
- 审核通过后创建租户商机，支持公司内分配、领取、首联 SLA、跟进和退回；
- 上线主办方、联系人、商机阶段、成交/失单和管理漏斗；
- 将审核与销售结果结构化为模型和关键词反馈。

验收：一篇微信文章可完成“活动聚合 → 三租户队列 → 某租户审核 → 商机 → 联系结果 → 反馈”的完整追踪，且不泄露其他租户状态。

### 阶段 3：近三年主办方情报

- 先用小范围关键词/行业和最近一年验证聚合与主体归一；
- 按最近年份向前回填近三年，低优先级断点续跑；
- 建立活动系列、举办次数、公开联系人证据、历史平台和周期预测；
- 上线下一届提前唤醒和销售辅助卡片。

验收：举办次数按独立届次计算；抽样主办方/角色/联系人证据可追溯；历史数据不污染实时公海。

### 阶段 4：全网连接器扩展

- 以微信 PC 和现有搜狗连接器验证统一契约；
- 接入一类高价值官方网页信源，验证 HTML/API 型连接器；
- 建设外部 HTTPS ingestion API，再接手机微信、第三方数据和租户私有信源；
- 按单位有效商机成本动态调整主题、渠道、节点和 LLM 预算。

验收：新增渠道不修改审核/CRM 核心；跨渠道同活动只生成一个共享事件；渠道效果可追踪到成交。

### 阶段 5：优化与规模化

- 用金标和 CRM 反馈持续校准全局价值与租户匹配排序；
- 完善复购、客户交接、公司自定义流程和租户经营报表；
- 根据容量和实际瓶颈评估分区、冷存储或独立服务，不提前拆微服务。

## 14. 明确不做的范围

近期不建设：

- 与评选销售无关的通用舆情情感分析、舆论传播大屏和泛热点展示；
- 考勤、工资、报销、行政审批等通用 HR/行政 OA；
- 一次性推倒重写、平行 `v2` 系统或每个渠道一套独立数据库；
- 为预期流量提前引入 Kafka、Kubernetes、Elasticsearch 和大规模微服务拆分；
- 让外部采集器长期直连 PostgreSQL，或让 OA 直接写内部业务表；
- 未经人工复核自动修改生产规则、Prompt 或模型策略。

OA 聚焦资源审核、电销协作、提醒、调度与审计；CRM 聚焦主办方、联系人、商机、跟进、报价、成交/失单与周期复购。

## 15. 已验证现网基线与当前缺口

2026-08-22 已验证基线（运行状态仍以最新健康检查/运行报告为准）：

- 四台微信采集 VM 已恢复在线并能回传新文章；单台节点异常不应影响其余节点；
- 本地到正式的事务发件箱同步已投入运行，正式业务数据不与本地数据库做整库复制；
- 正式环境是业务事实源，本地只同步源数据和 AI 字段，不覆盖账号、个人状态和跟进字段；
- LLM 由本地侧单点清洗，正式侧硬关闭清洗任务，避免重复调用；
- 本地生产采集平面的外部访问沿用 SSH 反向隧道，本机 Nginx 不是该链路的默认入口。

当前主要缺口：

- 微信搜一搜任务失败率仍需按 UIA、筛选、登录状态、网络和认证拆因治理；
- 当前数据仍以文章/`qualified_leads` 为中心，尚未完成活动届次和主办方证据模型；
- 现有团队/个人状态隔离不等于独立公司多租户隔离，不能直接承载三家公司 CRM；
- 人工有效性反馈稀疏，暂不足以可靠训练转化排序；
- 资源审核、电销 OA、CRM、三年历史回填和全网连接器均需按上述路线逐阶段落地。

以上基线用于持续演进，不代表全部目标能力已经上线。每个阶段的实际完成状态必须在需求登记、迁移记录、测试证据和发布记录中另行确认。
