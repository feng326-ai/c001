# 审核垂直切片契约 v1

> 状态：代码与隔离数据库验收阶段，生产开关必须保持关闭。本文补充《核心领域契约 v1》，冲突时以后者和《决策记录》为准。

## 1. 本批目标与非目标

首个切片只闭合以下链路：

```text
共享活动届次
  → 租户资源授权
  → 租户候选
  → 开始/重新审核
  → 完成审核
  → 同事务 domain outbox
```

本批不创建商机，不连接 OA/CRM，不自动分配销售，不回填三家公司，不迁移历史旧线索，也不部署生产数据库。

## 2. 采集模式与竞争规则

- `realtime_signal`：可以在有效 `shared_competition` 授权后生成 Candidate。
- `historical_backfill`：只进入共享主办方、活动系列和活动届次情报库，禁止生成即时 Candidate。
- 同一公开届次允许不同租户分别取得授权、候选和审核历史。
- 每个租户只能看到本租户授权、候选、审核和 outbox；共享实体不携带租户私有备注。
- `(tenant_id, event_edition_id)` 的 Candidate 永久唯一；撤销、重新授权、策略升级和消息重放都不能制造第二条。

## 3. 状态机

```text
Candidate: open → in_review → closed
                    ↑          │
                    └─ reopen ─┘

Review: in_review → completed
                  └→ cancelled  # Grant 撤销
```

- `start-review` 只接受 `open` 且尚无历史审核的 Candidate，创建第 1 轮 Review。
- 数据结构保留重新审核轮次与 `supersedes_review_id`，但首个 API 切片不开放 `reopen-review`；以后必须以独立幂等命令、版本检查和审计事件实现。
- `complete` 只接受当前 `in_review` Review；完成后 Review 和 Candidate 一起更新，并写入 `review.completed.v1` outbox。
- 已完成 Review 永不原地重写；修订必须重新开启下一轮。
- Grant 撤销时，未开始或正在审核的 Candidate 进入 `withdrawn`；正在审核的 Review 同事务进入不可覆盖的 `cancelled`，不能再正常完成。已完成审核不回写删除。
- 所有命令带期望版本，版本冲突返回 409；非法状态转换返回 422；跨租户或不存在统一返回 404，不暴露资源是否存在。

## 4. 角色与认证

- 每个请求先验证旧 `wxsess`，再解析绑定的 `wxscope` 候选租户，最后在同一物理数据库连接的 `tenant_transaction` 内重新验证 active membership。
- 只有 `resource_reviewer` 可开始、重新开启和完成审核；`tenant_admin`、`readonly_manager`、`sales` 和未映射的 platform 管理员均不能代替资源审核员落审核结论。
- `tenant_admin`、`readonly_manager` 可只读候选队列；`sales` 不读取或操作审核队列，后续只从正式销售交接/商机入口工作。
- Cookie 中的 tenant、membership 或 role 都不是数据库授权结论；服务端只使用事务内返回的 principal。
- 写接口必须校验与当前 scope 绑定的 CSRF token。

## 5. 完成审核的临时保护矩阵

| decision | 允许 disposition |
|---|---|
| `qualified` | `nurture`、`competitor_watch`；`sales_handoff` 暂时拒绝 |
| `rejected` | `archive`、`competitor_watch` |
| `needs_more_info` | `nurture` |

该矩阵用于防止测试代码产生自相矛盾状态，不代表已经批准正式运营口径。`sales_handoff` 必须等到完成审核时能够同事务幂等创建 Opportunity 后才能开放，不能出现“审核已交销售但没有商机”的断链状态。生产启用前仍须由业务负责人确认原因码、去向矩阵和分配方式。

## 6. 事务、并发与事件

- 审核命令必须是同步短事务，不得跨 `await`，不得在事务中调用模型、CRM、HTTP 或消息服务。
- Candidate 和当前 Review 在变更前使用行锁；请求版本不匹配时拒绝，不做最后写入覆盖。
- 每个写命令必须携带格式受限的 `Idempotency-Key`；同租户、同命令、同 key、同请求摘要返回首次保存的响应，同 key 不同摘要返回 409。不同租户可独立使用相同 key。
- `review.completed.v1` 使用唯一 `message_id`，并以事件类型、聚合 ID、聚合版本作为业务幂等键。
- Review、Candidate 和 outbox 要么全部提交，要么全部回滚。发送器以后独立读取 outbox，不能在审核请求内直接发送。
- 审核写入通过窄授权函数锁定 enabled user、active tenant 和 active membership；撤权会等待已获授权的短事务结束，撤权提交后的新写事务必须失败。普通候选只读仍可使用请求开始快照。

## 7. 开关与上线门槛

`TENANT_REVIEW_ENABLED` 默认 `false`。关闭时所有审核 v2 路由返回 404，旧 API、旧页面、采集、LLM 和生产同步行为不变。

开启前至少满足：

1. 021～023 在影子库和预发布通过迁移、备份恢复及 checksum 检查；
2. 应用使用非 owner、非 super、无 BYPASSRLS 的 runtime LOGIN；
3. 三家公司和 27 个一线账号的私有 roster 已逐项批准并 dry-run；
4. A/B/C 正反向 RLS、伪造 scope、角色越权、并发幂等和 outbox 原子性通过；
5. 审核原因码、决定与去向矩阵、销售交接方式已由业务负责人确认；
6. 单租户 canary、回滚开关和对账指标已经准备。

## 8. 历史届次的实时唤醒

`collection_mode` 属于来源证据，不属于活动届次本体。同一届次可以先由 `historical_backfill` 建档，之后再关联新的 `realtime_signal` 来源并进入审核队列。Grant 必须记录触发来源，数据库应证明该来源已经关联同一 Edition 且模式为 `realtime_signal`；历史来源本身不能作为即时授权的触发证据。
