# 受控资源分发契约 v1

> 状态：代码与隔离数据库验收阶段，生产开关必须保持关闭。本文补充《核心领域契约 v1》和《审核垂直切片契约 v1》；冲突时以《核心领域契约 v1》和 D-036 为准。

## 1. 目标与非目标

本契约只闭合正式共享域内的受控分发地基：

```text
受信 Inbox
  → 服务端校验实时来源与届次
  → 从平台设置推导并冻结租户 Target
  → 每个 Target 独立 claim + fencing + apply
  → 同事务 Grant + Candidate + candidate.created.v1
```

三个相互竞争的独立公司共享同一公开活动届次，但分别获得自己的 Grant、Candidate 和后续审核历史，彼此不可见。公司数量不得硬编码；初始三家公司以后仍通过平台设置显式批准。

本批明确不做以下事项：

- 不提供真实 Inbox writer，也不伪造测试入口冒充受信接收器；
- 不接 Celery、HTTP、公共 broker 或采集节点，不接受外部主动触发分发；
- 不播种三家公司或任何真实租户的分发设置、规则 activation、人员映射和历史数据；
- 不开始或完成审核，不创建 Opportunity，不连接 OA/CRM，不自动分配销售；
- 不实现 Grant regrant/rebind/supersede，不开放 `tenant_private`、`selected_tenants` 或 `exclusive`；
- 不部署 025，不打开审核或分发生产开关。

## 2. 入口信任边界

未来只有正式云端的受信接收器可以在应用共享实体的同一事务中写入不可变的 `platform_control.review_distribution_inbox`。Inbox 至少绑定：稳定 `upstream_message_id`、规范输入 `input_hash`、`event_edition_id`、`trigger_source_document_id` 和 correlation 信息。

- 同一 `upstream_message_id`、相同摘要是幂等重放；同一 ID、不同摘要必须拒绝并告警。
- Distributor 只接受 opaque `inbox_id`，再从数据库读取权威 Edition、Source 和上游消息绑定。
- 数据库函数、Python 服务和未来 Worker 消息均不得接受 `tenant_id`、`tenant_ids`、策略、`collection_mode`、评分或规则版本。
- `collection_mode`、来源与届次关系、活动阶段和租户范围都由数据库事实与平台配置确定，调用方声明没有授权效力。
- 运行 Worker 即使被误调用，也只能处理已经存在的受信 Inbox 和冻结 Target，不能扩大目标租户集合。

本批没有 Inbox 写函数。测试夹具可以在隔离数据库中以 migration owner 准备数据，但该路径不得进入应用服务、常驻容器或发布配置。

## 3. 分发资格与历史边界

展开时的目标集合只能取以下条件的交集：

1. Inbox 指向的 Source 已精确关联同一个 Edition；
2. 触发 Source 的权威 `collection_mode` 为 `realtime_signal`；
3. Edition 的 `activity_stage` 不是 `result_published`、`ended` 或 `cancelled`；
4. tenant 为 `active`；
5. `platform_control.review_distribution_tenant_settings` 对该 tenant 显式 `enabled`；
6. 设置的策略为 v1 唯一支持的 `shared_competition`；
7. tenant 存在唯一有效的审核规则 activation。

新增 active tenant、旧 `team`、membership 或普通用户不能自动扩大范围。展开时必须保存 tenant、设置版本、策略版本、规则 activation 和来源等资格快照；之后新增租户不回填到既有 Batch。

`historical_backfill` 只沉淀 Organizer、EventSeries、EventEdition 和证据，必须产生零 Target、零 Grant、零 Candidate、零租户事件。一个由历史来源建档的 Edition，后来关联新的合格 `realtime_signal` 时，可以由这个新的实时来源触发分发；历史来源自身永远不能冒充触发证据。

apply 前必须按固定锁序重新确认 tenant、设置和规则 activation 仍满足安全门禁。停用、撤权或不再满足冻结前提时不得替换为别的策略、规则或租户，也不得写业务表；应以稳定原因进入 `skipped` 或 `blocked`。

## 4. 控制面对象与状态

控制面对象统一位于 runtime 无直接访问权的 `platform_control` schema：

| 对象 | 职责 | 核心唯一性/不可变性 |
|---|---|---|
| `review_distribution_tenant_settings` | 平台批准的租户分发资格与策略 | 每 tenant 一个当前设置；普通租户用户和 runtime 不可写 |
| `review_distribution_inbox` | 受信上游触发事实 | `upstream_message_id` 唯一；已接纳业务字段不可改 |
| `review_distribution_batches` | 一次 Inbox 展开及汇总状态 | 一个 Inbox 最多一个 Batch |
| `review_distribution_targets` | 一个 Batch 内单租户执行单元 | `(batch_id, tenant_id)` 与 `(tenant_id, event_edition_id)` 均唯一 |

Batch 状态冻结为：

- `queued`：Inbox 已完成展开并冻结 Target，等待首次领取；
- `running`：已有未终结的 `pending/leased/retry` Target；
- `completed`：所有 Target 均为 `succeeded/skipped`，或合格实时来源因没有已批准租户而产生零 Target；历史/终态来源直接拒绝且不创建 Batch；
- `partial`：没有可运行 Target，至少一个成功，同时至少一个进入 `blocked/dead`；
- `dead`：没有可运行 Target、没有成功结果，且存在 `blocked/dead`。

Target 状态冻结为：

- `pending`：等待首次领取；
- `leased`：已领取并持有未过期 fencing token；
- `retry`：瞬时失败，等待有界退避后再次领取；
- `succeeded`：业务写入已原子完成，或确认已有一致的有效结果；
- `skipped`：当前租户或资源不再满足安全资格，且业务零写；
- `blocked`：发现需要人工或后续领域批次处理的业务冲突；
- `dead`：重试次数耗尽或不可恢复的执行错误。

`succeeded/skipped/blocked/dead` 均为 v1 终态。Batch 状态是 Target 状态的汇总投影，不是业务写入授权来源。

## 5. 固定数据库命令

Distributor LOGIN 只直接授权、且只允许有效执行以下四个特权窄函数：

| 函数 | 语义 |
|---|---|
| `app_expand_review_distribution(uuid)` | 输入唯一 `inbox_id`，校验来源并从平台设置推导、冻结 Batch 和 Target；不接受租户或策略参数 |
| `app_claim_review_distribution_target(text, integer)` | 输入受限 worker 标识和租约参数，原子领取最多一个可运行 Target，返回 opaque `target_id`、数据库生成的 fencing token 和租约信息 |
| `app_apply_review_distribution_target(uuid, uuid)` | 输入 `target_id + fencing token`，内部解析租户并以一个短事务应用该 Target |
| `app_report_review_distribution_failure(uuid, uuid, text)` | 只允许当前有效 token 报告规范化错误码，按有界重试规则转入 `retry/dead`；不得写入任意错误详情、凭据或业务字段 |

claim 必须使用数据库并发控制避免重复领取；租约到期后才可重新领取并生成新 token。apply 和 failure report 都必须比对当前 token、租约和状态，过期 token、旧 token、重复迟到完成一律拒绝且零业务写。worker 名称只是审计标签，不是授权凭据；租约时长和错误码必须由数据库限制范围。

服务层可使用 `expand_inbox`、`claim_target`、`apply_target`、`fail_target` 等内部方法封装四个函数，但不得增加可控租户列表或绕过 Inbox/Target 的快捷入口。本批不存在对应 HTTP 路由和 Celery task。

## 6. 单租户事务、锁序与失败隔离

展开只写计划，不写任何租户 Grant、Candidate 或 outbox。每次 apply 只能处理一个 Target，并按以下顺序锁定和校验：

```text
Target
  → tenant setting / active tenant / rules activation
  → tenant + Edition advisory lock
  → Grant
  → Candidate
  → domain outbox
  → Target succeeded
```

首次创建时，active Grant、`open` Candidate、`candidate.created.v1` 和 Target `succeeded` 必须在同一数据库事务提交；任一步失败全部回滚。禁止一个事务同时写多个租户，禁止一个租户的约束冲突回滚另外租户已经完成的事务。

并发和重放遵守以下规则：

- `(tenant_id, event_edition_id)` 的 Candidate 永久唯一；同一租户同一届次不能因重试、策略版本升级或不同实时文章产生第二条 Candidate。
- 已存在相互一致的 active Grant 与 `open/in_review` Candidate 时返回既有结果、Target 成功，不重复发送事件。
- 已有 active Grant 但缺 Candidate 时，只能在确认租户、届次和触发关系一致后补建唯一 Candidate。
- revoked/superseded Grant，或 `withdrawn/closed` Candidate，不自动复活、重绑、新授权或重新入队，Target 进入 `blocked_regrant_required` 对应的 `blocked` 终态。
- Candidate/Grant 租户、Edition、触发来源不一致属于数据冲突，必须零修复写入并进入可审计阻断状态。
- 瞬时锁、序列化或连接错误可以有界重试；业务冲突不得无限重试。

apply 是同步短事务，不得在事务内访问模型、HTTP、CRM、消息 broker 或其他外部系统。

## 7. `candidate.created.v1` 事件

只有首次创建 Candidate 才写一条 `candidate.created.v1`：

- 事件属于服务端确认的目标 tenant，`aggregate_type=tenant_candidate`、`aggregate_id=candidate_id`、`aggregate_version=1`；
- `correlation_id` 在同一上游实时信号的多租户扇出中保持一致；`causation_id` 指向受信 `upstream_message_id`；
- payload 只包含 `candidate_id`、`event_edition_id`、`grant_id`、`shared_competition`、策略版本、`trigger_source_document_id` 和必要的 opaque Batch 引用；
- payload 不得包含目标租户全集、其他公司标识、审核备注、联系人私密信息、分数或平台设置明细；
- 幂等返回已有 Candidate 时不补发、不重发；事件以类型、聚合 ID 和聚合版本保持业务唯一；
- 事件只写 `domain_outbox`，本事务不直接投递。平台 Batch 完成不需要广播租户域事件。

本事件表示“该租户出现一个待审核 Candidate”，不表示审核通过、销售交接或已创建商机。`sales_handoff` 在 Opportunity 能与完成审核同事务创建之前继续固定拒绝。

## 8. 数据库角色与权限

Distributor 使用独立常驻 LOGIN，与 Backend runtime 和 migration owner 分离。上线检查必须证明该角色：

- `NOSUPERUSER`、`NOBYPASSRLS`、非任何业务表/函数 owner，且不继承 migration owner 或其他高权限角色；
- 对 `platform_control`、Grant、Candidate、规则、租户身份和 `domain_outbox` 没有直接 SELECT/INSERT/UPDATE/DELETE/TRUNCATE 权限；
- 对 schema 没有 CREATE，对迁移 ledger 没有写权限；
- 只直接获得上述四个函数的精确 EXECUTE，并验证其有效可执行的应用域 `SECURITY DEFINER` 集合也只有这四个；数据库历史上向 PUBLIC 开放的无特权 `SECURITY INVOKER` 辅助函数不计作直接授权，且在零表权限下不能扩大数据能力；普通 Backend runtime 不获得四个分发函数权限；
- 不使用用户可控 GUC、Cookie membership 或旧 team 作为跨租户授权。

四个函数必须 `SECURITY DEFINER`、固定 `search_path=pg_catalog`、全限定引用对象、无动态 SQL，并对 PUBLIC 撤销 EXECUTE。migration owner 的连接串和凭据不得进入 Backend、Worker 或任何常驻容器。

## 9. 开关、上线前置与回滚

`REVIEW_DISTRIBUTOR_ENABLED` 默认且本批固定为 `false`。关闭时不得启动 claim/apply 循环；不得因为数据库已有 Inbox、Target 或 Candidate 自动运行。该开关不隐式打开 `TENANT_REVIEW_ENABLED`，两个能力必须分别审批。

真实启用前至少满足：

1. 025 已在影子库和预发布通过空库、增量迁移、checksum、备份恢复和权限复核；
2. 正式受信接收器与 Inbox 同事务写入、签名验证、幂等和同 ID 异载荷拒绝已经单独交付；
3. 三家公司真实 tenant、人员 roster、分发设置和审核规则 activation 已逐项批准，dry-run 目标集合与清单完全一致；
4. Distributor LOGIN 最小权限已在真实 PostgreSQL 角色上验证，migration owner 凭据未注入常驻进程；
5. 历史零分发、终态拒绝、三租户竞争隔离、重放幂等、单租户失败隔离、租约过期和 fencing 竞态测试全部通过；
6. Candidate/outbox 对账、Target 积压/重试/dead 告警、单租户 canary 和停机回滚步骤已经准备；
7. 审核页面确实可消费新增队列前不得持续制造不可运营的生产积压。

回滚时先关闭 `REVIEW_DISTRIBUTOR_ENABLED` 并停止 claim；已成功的 Grant、Candidate 和 outbox 属于正式业务历史，不删除、不跨租户回收。未完成 Target 保留供审计，恢复必须使用新租约和新 fencing token。回滚代码不逆向删除 025 对象，也不得为恢复旧代码而给常驻 Worker migration owner/BYPASSRLS 权限。

## 10. 最小验收矩阵

- 任一层额外提交 tenant、tenant list、policy、mode、score 或规则版本均被拒绝；
- `historical_backfill` 和 `result_published/ended/cancelled` 均为零 Target、零租户业务写；
- 同一实时 Edition 为三个获批租户分别创建一条 Candidate，A/B/C 正反向不可见；
- 一个租户冲突或失败时，另外租户仍可独立提交；
- 并发 expand/claim/apply 和消息重放不产生重复 Grant、Candidate 或事件；
- 租户或设置在 expand 后、apply 前停用时 fail closed，且不改用新租户或新策略；
- 旧 token、过期 token 和迟到 failure/success 均零业务写；
- revoked/superseded Grant、withdrawn/closed Candidate 进入阻断，不被自动复活；
- Distributor 直读写控制表/业务表、Backend 调四个函数、运行角色 SET ROLE 提权均失败；
- `candidate.created.v1` 不泄露其他租户或私有字段，Candidate、outbox 和 Target 成功态原子一致；
- 开关关闭时无 claim/apply 循环、无 HTTP/Celery 入口、无真实 settings/Inbox 种子。
