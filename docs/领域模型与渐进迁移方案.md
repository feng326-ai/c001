# 领域模型与渐进迁移方案

> 状态：设计基线，尚未执行数据库迁移。本文规定共享情报、三公司租户业务和现网兼容迁移的边界；具体 SQL 必须另领迁移编号、经过影子库验证和生产审批。

## 1. 迁移目标

将当前“文章/`qualified_leads` 即线索”的模型渐进演进为：

```text
source_document
  → event_edition → event_series / organizer / public_contact / contact_evidence
  → tenant_resource_grant → tenant_candidate
  → tenant_review
  → opportunity
  → opportunity_activity / opportunity_outcome
```

迁移期间必须同时满足：现网采集和本地到正式同步不中断；正式业务数据不被本地覆盖；三家公司 CRM 严格隔离；同一内容和同一模型版本不重复清洗；每阶段都可停止、校验和回退。

## 2. 共享域与租户域

| 领域 | 目标实体 | 权威写入方 | 可见范围 |
|---|---|---|---|
| 采集证据 | `source_documents`、`document_keyword_hits` | 本地采集/加工 | 公共或按来源策略授权 |
| 活动事实 | `event_series`、`event_editions`、`event_sources` | 自动抽取建议；正式人工可纠正 | 共享情报 |
| 主办方事实 | `organizations`、`organization_aliases`、`organization_event_roles` | 自动归一建议；正式人工可纠正 | 共享情报 |
| 公开联系人 | `public_contacts`、`contact_evidence` | 公开证据由加工侧追加，正式人工可纠正 | 公开证据共享 |
| AI 结果 | `ai_assessments` | 当前仅本地 LLM 执行方 | 共享事实抽取/基础判断 |
| 分发与审核 | `tenant_resource_grants`、`tenant_candidates`、`tenant_reviews` | 正式业务侧 | 租户私有 |
| 销售业务 | `opportunities`、`tenant_contacts`、`opportunity_contacts`、`opportunity_activities`、`opportunity_outcomes` | 正式业务侧 | 租户私有 |
| 租户评分 | `tenant_assessments` | 正式业务侧 | 租户私有并受 RLS 保护 |
| 私有补充 | 私有关键词、私有联系人、备注、报价和绩效 | 正式业务侧 | 租户私有 |

三个公司共享公开文章、活动、主办方和通用 AI 结果，以避免重复采集、去重和模型费用；审核结论、补充联系人、跟进、报价与结果不得跨租户共享。

## 3. 核心实体与约束

### 3.1 身份与租户

- `tenants`：一家公司一个租户；稳定 UUID，不以名称作外键。
- `tenant_memberships`：用户与租户的成员关系，租户角色至少包含租户管理员、资源审核员、销售和只读管理者。
- `platform_roles` 与租户成员分离；平台运维默认不能读取租户 CRM。确需排障时通过有期限、限定租户/字段并全程审计的 `support_grants` 授权。
- 身份令牌只声明已授权成员关系，当前请求的租户由服务端校验后写入数据库会话上下文；调用方传入的任意 `tenant_id` 不能扩大权限。
- 现有 `teams` 不能直接被宣布为安全租户。迁移前先建立显式映射、处理一人多团队和历史空值，再切换鉴权。

### 3.2 原始文档与采集幂等

`source_documents` 至少保存 `source_channel`、渠道内 ID、规范 URL、标题、正文/审计引用、发布时间、采集时间、内容哈希、`collection_mode`、连接器 ID 和原始元数据。

约束：

- `collection_mode` 首版只允许 `realtime_signal`、`historical_backfill`。
- 接收幂等优先使用 `(connector_id, idempotency_key)`；平台继续用规范 URL、渠道内 ID 和内容哈希做二次去重。
- 同一文档可命中多个监测主题，使用关联表保存，不复制文档。
- 原始证据原则上只追加；正文修订保留版本或哈希，不能无审计覆盖。

### 3.3 活动、届次与主办方

- `event_series` 表示可持续复办的活动系列；`event_editions` 表示某年/某届的独立业务事件。一届可以暂未归入系列，但不能用“系列”代替具体届次生成候选或商机。
- `event_sources` 把多篇公告、转载、投票入口和结果公示关联到同一届次，并保存匹配方法和置信度。
- `organizations` 保存标准主体，别名进入 `organization_aliases`；禁止仅凭相似简称自动合并高风险主体。
- `organization_event_roles` 保存主办、承办、协办、指导等关系及证据。举办次数只统计已确认的主办角色和独立届次，不按文章数计算。
- 机器合并必须可撤销；人工确认的拆分/合并优先级高于后续自动任务，并保留审计记录。
- 正式端是共享实体人工合并/拆分的裁决方：`entity_resolution_decisions` 保存版本、旧 canonical ID、新 canonical ID、重定向或 tombstone、证据分配和操作者。普通合并可将旧 ID 重定向到新 ID；一拆多必须 tombstone 原 ID 并显式列出子实体，后续新证据进入隔离复核，不能继续自动挂到已拆实体。

### 3.4 联系证据

- 公开联系人进入 `public_contacts`，按主办方归属并保存规范姓名/职务；具体电话、邮箱、微信等事实由 `contact_evidence` 关联到来源文档，至少包含原文片段/定位、首次与最近发现时间、验证状态和可信度。
- 联系人实体和证据分离：多个证据可指向同一联系人，过期或冲突证据不得静默覆盖；只有证据充分时才自动合并联系人。
- 业务员补充的私人联系人及联系方式进入带 `tenant_id` 的 `tenant_contacts`，通话内容和内部备注进入 CRM 时间线，不能反写成其他公司可见的公共联系人。

### 3.5 AI 结果与不重复清洗

`ai_assessments` 保存共享事实抽取/全局相关度的任务类型、输入哈希、模型、Prompt/规则/schema/执行配置版本、结构化输出、成本、耗时、状态和错误。租户偏好或转化画像产生的排序进入带 `tenant_id` 的 `tenant_assessments`，不得写入共享结果。

推荐幂等键：

```text
(assessment_type, input_hash, execution_config_version, prompt_version, rule_version, schema_version)
```

`input_hash` 基于字段排序、时间/空值规范化后的不可变输入快照；`execution_config_version` 同时冻结供应商、模型和温度等推理参数。相同幂等键只有一个成功结果；worker 必须原子 claim 任务、续期租约并携带 fencing token，只有当前 token 能提交结果。对于调用已发出但结果未知的任务，应优先使用供应商幂等能力或延迟核对，不能立即并发重试。只有输入或版本明确变化才能重新评估。当前本地环境是唯一正式清洗执行方，云端只消费结果；切换执行方必须先停旧 worker、清空/交接租约再开新 worker。

### 3.6 租户候选、审核与商机

- `tenant_resource_grants`：独立记录某租户对活动届次的可见/使用授权、策略、版本、来源、授予/撤销时间和审计。默认策略 `shared_competition`，预留 `tenant_private`、`selected_tenants`、`exclusive`；授权变化不能静默删除已启动的审核或商机。
- `tenant_candidates`：授权成立后生成的审核工作项，不承担长期授权职责。稳定幂等键为 `(tenant_id, event_edition_id)`；`policy_version` 只作为生成快照/历史记录，策略升级通过显式 supersede/重新开放规则处理，不得生成重复审核任务。
- `tenant_reviews`：分别保存审核状态、`qualified/rejected/needs_more_info` 决定、销售/培育/竞品监控/归档去向、结构化原因、租户覆盖值、备注、审核人、时间以及当时的 AI/规则版本。历史决定保留，不把一列状态当作全部审计。
- 租户覆盖只影响本公司视图；共享活动、主办方或公开联系人纠错进入 `data_correction_requests`，由平台数据管理员审批后生成 `entity_resolution_decisions`，租户审核员无权直接修改全局 canonical 实体。
- `opportunities`：租户内的负责人、阶段、下一步、SLA 和客户价值。使用部分唯一索引或等效事务规则保证 `(tenant_id, event_edition_id)` 最多一个活跃商机。
- `opportunity_activities`：电话、消息、备注、提醒、分配和转交采用追加时间线；重要更改有操作者与来源系统。
- `opportunity_outcomes`：成交、失单、无效、延期到下一届等结果及结构化原因，可作为租户私有反馈。

同一 `event_edition` 可以在三家公司各有一条候选和一个活跃商机；任何“已被其他公司领取”的状态都不能阻止当前租户跟进，也不能向当前租户暴露竞争公司的进度。

## 4. PostgreSQL 隔离模型

1. 所有租户业务表的 `tenant_id` 为非空外键，并进入主键/唯一键或相关索引。
2. API 在事务开始时根据已认证成员关系执行 `SET LOCAL app.tenant_id = ...`；连接归还池前不得残留会话租户。
3. 关键租户表启用并强制 RLS：普通租户角色只能访问 `tenant_id = current_setting(...)` 的行。
4. 共享情报表不带伪租户副本；租户通过 `tenant_resource_grants` 读取共享对象。私有来源需要显式授权，候选归档本身不等于撤销或延长授权。
5. 后台 worker 使用最小权限的专用数据库角色；平台运维绕过 RLS 的操作必须单独授权、记录原因并审计。
6. 每个查询和写接口都要验证：同租户成功、跨租户为空/拒绝、伪造租户参数无效、批量接口无漏行、导出和搜索不越权。

RLS 是服务端作用域的第二道防线，不能替代业务层授权；前端隐藏按钮不构成安全控制。

## 5. 实时与历史双引擎

| 项目 | `realtime_signal` | `historical_backfill` |
|---|---|---|
| 优先级 | 高 | 低、限并发 |
| 入口 | 最新增量与当前需求词 | 近三年按年份/月份/主题切片 |
| 断点 | 短租约、快速重试 | 持久 checkpoint、可暂停续跑 |
| AI 预算 | 时效优先 | 独立额度、批处理和缓存优先 |
| 结果 | 可生成租户候选 | 先完善主办方/届次；进入预测窗口后再生成候选 |
| 指标 | 发现延迟、审核通过、有效商机 | 覆盖率、聚合准确率、周期预测命中 |

两条链路共用标准化、去重、实体解析和 AI 幂等实现，但队列、配额、告警和产品入口分离。历史回填不得把三年文章批量标成今日新线索。

## 6. 本地到正式的数据所有权

- 本地只同步公开文档、自动活动/主办方建议、公开联系证据和版本化 AI 结果。
- 正式环境是租户候选、审核、商机、联系人补充、跟进、报价和结果的唯一事实源。
- 同步通过事务发件箱和 HTTPS 幂等接收；源事务与 Outbox 插入必须处于同一数据库事务。实体使用稳定 UUID/业务键，不假设两库自增 ID 一致。
- 每类事件声明字段所有权。上游更新只能补充自动字段，不能覆盖正式人工修订和任何租户 CRM 字段。
- 正式接收一个公共事件后，由正式侧按当前策略幂等生成 `tenant_resource_grant`，再生成 `tenant_candidate`；授权或候选生成失败可重试且不影响公共事件落库。
- 正式端的 `entity_resolution_decisions` 通过独立、版本化的控制事件回传本地；本地应用重定向/tombstone 后再关联新证据。正式接收端仍需解析旧 ID 重定向，并把拆分后歧义事件放入复核队列，不能依赖双向整库同步。
- 租户匹配和 `tenant_assessments` 只在正式业务平面计算。正式侧到本地智能侧默认不回传联系人、报价、通话或单租户结果；若未来使用聚合反馈改进共享模型，必须先冻结独立的治理契约、最小聚合门槛、脱敏字段白名单和审计，未冻结前不启用反向反馈同步。

## 7. 存量映射

| 当前对象 | 迁移目标 | 处理方式 |
|---|---|---|
| PostgreSQL `articles_core`（单机 SQLite `articles` 仅属 legacy） | `source_documents` | 保留原 ID 映射、补稳定 UUID/哈希和采集模式 |
| `qualified_leads` | `event_editions` + AI 结果 + 兼容视图 | 先一对一种子，再做多来源聚合；不直接删除 |
| `organizers` | `organizations` + 角色/别名 | 先保守映射，疑似重复进入人工复核队列 |
| 关键词关联 | `document_keyword_hits`/监测主题 | 保留多对多命中和可见来源 |
| `teams`/用户状态 | `tenants`/成员/租户业务表 | 明确三家公司映射，个人状态按租户归档 |
| 收藏、赞踩、回收站等 | 审核/反馈样本或个人偏好 | 不自动等同成交标签；保留原始信号和来源 |

回填表必须保存 `legacy_table`、`legacy_id`、`new_entity_id`、批次和校验状态，保证可对账和可重跑。

## 8. 渐进迁移步骤

### M0：基线与保护网

- 冻结当前 schema、同步契约和字段所有权；完成备份恢复演练、数据画像、异常值统计和脱敏影子库。
- 建立空库与存量库迁移测试、跨租户测试夹具、同步幂等测试和关键业务指标基线。

**门禁**：现网健康、备份可恢复、迁移演练环境与回滚负责人明确。此阶段不切业务读写。

### M1：Expand

- 只新增租户、共享情报、审核/商机、映射和审计结构；新增索引采用低锁方案。
- 旧表、旧列和旧 API 保持可用；迁移不得立即增加不满足存量数据的强制约束。

**回退**：应用继续只读写旧结构；未被业务引用的新表可保留等待修正，不做破坏性删除。

### M2：Backfill

- 按主键范围小批回填，记录 checkpoint、成功/跳过/冲突数量；重复执行结果一致。
- 先建立一对一兼容映射，再离线聚合活动/主办方；高风险自动合并进入人工复核。
- 对账总数、空值、孤儿关系、重复率、三家公司成员映射和抽样证据。

**回退**：停止回填 worker，旧链路继续服务；按批次重算新表，不修改旧源数据。

### M3：Shadow write and compare

- 旧表写入与 Outbox 插入必须在同一数据库事务提交；新模型消费者按事件 ID 幂等投影。禁止事后补写 Outbox，也禁止两个独立 worker 竞争成为权威写入方。
- 新页面/API 先做影子读取，与旧结果比较数量、状态、权限和延迟，不向业务员展示不一致结果。
- 同步接收、LLM、候选生成和商机创建分别验证重复、乱序和部分失败。

**门禁**：约定观察期内无不可解释差异；跨租户越权为零；重复 LLM 和重复活跃商机为零。

### M4：按租户/模块切读

- 先内部管理员，再一个 canary 租户，最后其余租户切换审核和商机读取；旧页面保留快速开关。
- 对比审核积压、分配数、活跃商机、首联 SLA 和错误率。

**回退**：关闭新读开关回旧页面；新表数据保留用于诊断，不反向覆盖旧表。

### M5：切换权威写入

- 每次只切一个聚合：候选、审核、商机或活动时间线；记录切换时间和最后旧写入水位。
- 新模型成为权威后，旧结构仅由兼容投影更新，禁止新旧两端各自接受修改。

**回退**：只有兼容投影已验证完整时才允许回旧写；否则停止入口并向前修复，避免两边分叉。

### M6：Contract

- 至少经过一个完整观察窗口且所有消费者完成迁移后，旧列转只读、兼容视图或归档。
- 删除表/列、清理映射和停止旧同步必须独立迁移、单独审批，并先验证可恢复备份。

**门禁**：代码搜索和运行指标证明无旧消费者；回滚窗口和归档查询方案已确认。

## 9. 每阶段验收指标

- 数据：源/目标总数、成功映射率、孤儿数、重复活动率、主办方误合并抽检、联系人证据可追溯率。
- 隔离：三租户查询、详情、搜索、导出、批量写入和后台任务的正反向越权测试全部通过。
- 幂等：重复采集、同步重放、并发清洗、候选重建和商机创建均不增加重复业务对象或重复模型费用。
- 性能：关键页面 P95、队列积压、同步 P95、数据库锁时长和磁盘增长不超过发布阈值。
- 业务：审核队列、分配、首联、商机阶段和结果数量可与切换前对账，历史回填不进入实时新增指标。
- 运维：日志可定位到 `correlation_id`、Git SHA、迁移批次和模型版本；健康检查、告警与回滚演练通过。

## 10. 实施约束与待冻结项

- 本文实体名是目标逻辑名；首个 SQL 前必须冻结最小 schema、枚举、状态机和 OpenAPI，并由集成负责人串行分配迁移号。
- 第一批只实现一条最小闭环：公共活动 → 三租户候选 → 一个租户审核 → 商机 → 联系结果。不要同时上线完整 CRM、三年全量回填和多个新渠道。
- 不创建平行仓库或 `v2` 副本，不在服务器直接改表/源码，不把 Redis/PostgreSQL 暴露给外部连接器。
- 未经业务确认不启用 `exclusive`；当前默认始终是 `shared_competition`。
- 数据保留期、联系人合规口径、平台管理员敏感读取范围、金额/绩效字段和租户定制流程需在对应功能进入开发前另行冻结。
- “近三年”在首个回填批次前必须由业务确认是滚动 36 个月还是“当前自然年 + 前两个自然年”；无论选择哪种，每个批次都固化 `as_of`、`range_start`、`range_end` 和 `backfill_batch_id`，不能随执行日期漂移。
