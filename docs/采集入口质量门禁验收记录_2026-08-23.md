# 采集入口质量门禁验收记录（2026-08-23）

## 一、结论

暂停采集是正确的安全动作。问题不是单一的微信 UI 筛选失效，而是“宽泛关键词召回当天无关文章 + 采集端过滤异常放行 + 服务端入库前无独立复核”叠加造成。代码侧已补齐采集端和服务端双层 fail-closed 门禁；本批未启动任何 VM、未部署生产容器、未删除或修改存量业务数据。

## 二、现网只读证据

- 暂停前最后 24 小时：`articles_core=2,567`，来源均为 `wechat_pc`。
- 发布时间：2,541 篇在采集时刻前两天内，26 篇缺失；没有“近三年历史批量误入”迹象。
- 明确业务信号：1,466 篇；缺少明确评选/投票/征集信号 1,101 篇，占 42.9%。
- 旧规则提升为候选：1,760 篇；其中已完成 DeepSeek 判断且有价值 745 篇。
- 同期 VM 任务失败：`win10-01=260`、`win10-02=41`、`win10-03=469`、`win10-04=303`。主要错误为微信窗口/COM/UIA 异常，失败任务已经是零文章，说明现有 `FilterNotApplied` 路径多数能 fail closed；无关文章主要来自成功搜索中的宽泛召回。

## 三、代码门禁

1. 新增 `wxsearch/ingest_quality.py`：
   - `realtime_signal` 强制要求可解析发布时间且默认不超过 72 小时；
   - “全国、先进、推荐、参与”等普通词不能单独构成业务意图；
   - 至少具备评选/投票/征集/赛事意图与行动信号；
   - 干部任免、先进事迹、扑克等已知噪声主题在无明确线上投票时拒绝；
   - `historical_backfill` 只放宽时间，不放宽业务相关性。
2. `collector.py` 不再使用 `filter_error_passthrough`；规则异常直接拒绝。
3. `tasks.py` 在打开数据库连接之前二次准入；永久业务拒绝不触发 Celery 重试。
4. `process_batch_articles` 与单篇入口使用同一策略，不能通过批量任务绕过。
5. 采集信封显式携带 `collection_mode=realtime_signal`；旧节点缺字段时仍按实时模式收紧，不自动放宽。
6. 已停用宽泛词在 `_collect_one` 共用入口和服务端文章准入双重拒绝，手工与无人值守路径均不能绕过。

## 四、影子评估与测试

- 用暂停前 2,567 篇做只读影子统计：预计接受约 1,730 篇，入口拒绝约 837 篇（32.6%），不写库、不调用模型。
- 用 1,251 条已完成 DeepSeek 判断的数据校准：宽门禁保留约 98.7% 的有效样本；未采用会明显降低召回的严格纯规则方案。
- 新增永久拒绝、历史分流、时间窗、噪声主题、规则异常、单篇/批量旁路和信封契约测试。
- 最终本地回归：`413 passed, 25 skipped`；改动模块通过 `py_compile`；`git diff --check` 无错误。

## 五、恢复条件

1. 先提交并推送本批代码，从 Git SHA 构建不可变 Worker/VM 发布包。
2. 服务端门禁先部署并保持 VM 停止，验证 Worker 健康和拒绝日志。
3. 仅恢复 `win10-01`，人工核对面包屑为“最新、文章、最近一天”。
4. 灰度 10 个关键词或 30 分钟，核对入口拒绝率、DeepSeek 有效率、错误分类和正式同步。
5. 低有效率关键词暂停并改写；达到门槛后再逐台恢复，禁止四台同时启动。

当前安全停止点：代码与测试完成，尚未部署、尚未恢复 VM。
